# Stats de concordance & proximité au gold

## Option A — Galerie de visualisations dédiée, server-driven (matrices + classements) sur la page de gestion GOLD
Une route /projects/[slug]/gold/stats (ou onglet « Stats » du module GOLD) avec trois blocs visuels : (1) MATRICE de concordance annotateur↔annotateur (heatmap κ symétrique, diagonale = soi), (2) MATRICE annotateur↔LLM (rectangulaire, annotateurs en lignes, juges en colonnes), (3) CLASSEMENT annotateur↔GOLD (barres triées « qui est le plus proche du gold » + médaille top-3). Tout calculé côté serveur dans un nouveau module projects/gold_stats.py qui RÉUTILISE _theme_vector / cohen_kappa / _intersection, en généralisant project_concordance pour boucler sur TOUS les annotateurs (pas seulement request.user) et en ajoutant un gold_vector tiré de la base GOLD. Exposé via un endpoint /projects/{slug}/gold-stats (camelCase), consommé par React Query. Visus « maison » SVG/CSS sans dépendance lourde, cohérentes avec IaaDashboard (Landis & Koch, tokens thème).

**Forces** : Réutilisation maximale du socle backend (cohen_kappa, _theme_vector, _intersection, alpha_masi) — la généralisation multi-annotateur est ~80 lignes, le gold_vector ~15 ; Les trois axes demandés sont traités au même endroit avec la bonne primitive visuelle (matrice pour les relations N×N/N×M, classement pour la proximité au gold) ; Server-driven = pas de N² téléchargements d'annotations côté client ; cohérent avec project_concordance/project_iaa_detail déjà server-side ; Heatmap κ + classement gold = lecture « top 10 mondial » immédiate pour un lead de campagne (qui diverge, qui est fiable) ; S'insère naturellement dans le module de gestion GOLD (onglet Stats) déjà prévu au cahier des charges

**Faiblesses** : Pas de temps réel : les stats reflètent le dernier gold matérialisé, pas la résolution en cours (acceptable pour un dashboard, mais il faut un état « gold périmé / recalcul ») ; Nouveau endpoint + nouveau module à tester (pytest matrice symétrique, gold ranking, support n) ; Heatmap κ pour beaucoup d'annotateurs (>10) peut devenir dense — besoin tri/regroupement

**Pertinence** : Très élevée : couvre exactement les 3 axes demandés (A↔A, A↔LLM, A↔GOLD) avec les bonnes visualisations, en réutilisant 90% du socle. C'est le cœur explicite du besoin « qui est le plus proche du gold ».

## Option B — Stats temps réel intégrées DANS l'atelier de résolution (panneau live, par document, calcul client)
Étendre concordance.ts pur en gold_stats.ts : à partir des vecteurs déjà chargés dans le store de résolution (annotations des pairs + préannotations LLM + gold provisoire en cours de construction), calculer en direct, POUR LE DOCUMENT COURANT, l'accord de chaque annotateur avec le gold provisoire et entre eux. Un panneau repliable dans l'InspectorPanel de résolution (à côté de ConcordanceWidget) montre des barres « proximité au gold » qui bougent à chaque décision d'arbitrage, plus un mini-classement « annotateur le plus fiable sur ce doc ». Réutilise themeVectorExact, intersectionAgreement, concordanceReport ; le gold provisoire est juste un vecteur de plus.

**Forces** : Temps réel natif : chaque clic d'arbitrage met à jour la proximité au gold (effet « waouh », très UX top-tier) ; Zéro nouvel endpoint, zéro round-trip — réutilise concordance.ts pur et le store déjà chargé pour la résolution ; Interconnexion forte panneaux ↔ sélection (exigence UX) : sélectionner une clause met en avant qui s'écarte du gold dessus ; Idéal pour l'arbitre pendant la session (feedback immédiat sur l'effet de ses choix)

**Faiblesses** : Portée DOCUMENT uniquement : ne donne pas la vue campagne « qui est globalement le plus proche du gold » (le cœur du besoin demande l'agrégat campagne) ; Pas de matrice A↔A ni A↔LLM agrégée — l'atelier n'est pas le bon endroit pour une heatmap N×N ; Calcul client de κ sur tous les annotateurs d'un doc = OK pour 1 doc, mais ne scale pas à l'agrégat campagne ; Redonde partiellement ConcordanceWidget sans répondre à l'axe « gold » au niveau campagne

**Pertinence** : Moyenne : excellent complément temps réel, mais à lui seul il manque l'agrégat campagne et les matrices/classements explicitement demandés. C'est une brique, pas la réponse complète.

## Option C — Couche analytique générique « matrice de concordance » réutilisable + export iaa_matrix, agnostique de la source
Créer une primitive unique côté backend concordance_matrix(vectors: dict[label -> vec], metric) qui prend N'IMPORTE quel ensemble de vecteurs étiquetés (annotateurs, juges LLM, gold) et renvoie la matrice complète d'accord paire-à-paire (κ ou %intersection) + classements. Annotateur, LLM et GOLD ne sont alors que des « sources » homogènes dans une même matrice unifiée (N+M+1 entités). Côté front, un seul composant ConcordanceMatrix générique (heatmap + tri + filtre par type de source) sert partout (page projet, module gold, et alimente le format d'export iaa_matrix déjà existant dans ExportJob). La proximité au gold = simplement la colonne/ligne GOLD de la matrice, triée.

**Forces** : Abstraction la plus élégante : une seule primitive testée couvre A↔A, A↔LLM, A↔GOLD, LLM↔LLM et LLM↔GOLD — factorisation maximale ; Branche directement le format d'export iaa_matrix existant (ExportJob) → gold intermédiaire/final exportable avec sa matrice, cohérent avec le besoin « export du gold » ; Un seul composant front à maintenir/tester, réutilisé sur la page projet ET le module gold ; Évite la dette de 2-3 endpoints quasi-jumeaux (project_iaa_detail vs project_concordance traitent déjà des vecteurs similaires séparément)

**Faiblesses** : Plus gros effort de conception/refactor en amont (unifier κ exact-vs-forward-fill : humain exact, LLM forward-fill, gold = à définir — mélanger les modèles dans une matrice demande une convention claire et documentée sous peine de mesures non comparables) ; Risque de sur-ingénierie si une seule des sources évolue différemment (le gold pourrait vouloir un scoring pondéré votes>LLM, pas un simple κ) ; Une matrice « tout-en-un » N+M+1 peut noyer la lecture métier « proximité au gold » si l'UI ne sépare pas visuellement les types de source ; Touche du code éprouvé (iaa/concordance) → risque de régression sur des mesures déjà validées en prod

**Pertinence** : Élevée sur le plan architecture/factorisation et parfaite pour l'export, mais le mélange des modèles de vecteurs (exact vs forward-fill) et le scoring gold pondéré (votes>LLM) rendent l'unification fragile ; risqué pour du code déjà validé.

## ✅ Recommandation : Option A, avec la brique temps réel de l'Option B en complément (panneau live dans l'atelier de résolution) et l'idée d'export de l'Option C limitée au format iaa_matrix existant

> Le besoin nomme explicitement trois axes (A↔A, A↔LLM, A↔GOLD) ET la question métier « qui est le plus proche du gold » — ce qui appelle deux primitives visuelles distinctes : la MATRICE (heatmap) pour les relations N×N/N×M, et le CLASSEMENT trié pour la proximité au gold. L'Option A les pose au bon endroit (l'onglet Stats du module de gestion GOLD), en réutilisant ~90% du socle déjà validé en prod (cohen_kappa, _theme_vector, _intersection, alpha_masi, IaaDashboard, llmJudgeColor/Label, tokens). La seule vraie nouveauté est (1) généraliser project_concordance pour boucler sur TOUS les annotateurs et non le seul request.user, et (2) introduire un gold_vector dérivé de la base GOLD du module de résolution — c'est petit et testable. J'ajoute la brique B (concordance.ts pur, déjà existant) comme panneau temps réel DANS l'atelier de résolution pour l'exigence de fluidité/temps réel, sans en faire l'agrégat campagne. Je REJETTE l'unification totale de C sur le code de prod : mélanger humain-exact et LLM-forward-fill dans une matrice unique, plus un scoring gold pondéré (votes annotateurs > votes LLM), rend les cellules non comparables et met en risque des mesures déjà validées ; je n'emprunte à C que le branchement sur le format d'export iaa_matrix d'ExportJob, sans refactorer iaa/concordance.

### Détails clés d'implémentation
- Backend : nouveau module backend/claire/projects/gold_stats.py qui RÉUTILISE from .iaa import _theme_vector, cohen_kappa et from .concordance import _intersection, _judge_vectors_for_document ; fonctions gold_concordance_matrix(project) (κ A↔A symétrique), annotator_llm_matrix(project) (%intersection A↔LLM, lignes=annotateurs cols=juges), gold_ranking(project) (proximité de chaque annotateur ET chaque juge au gold, trié desc).
- gold_vector : la base GOLD du module de résolution fournit, par document, un vecteur per-sentence du thème PRIMAIRE retenu (+ set multi-label pour cohérence avec _theme_set_vector/alpha_masi) ; A↔GOLD se mesure en κ exact côté humain (cohen_kappa sur _theme_vector vs gold) et en %intersection pour LLM↔GOLD — convention documentée pour ne pas mélanger les modèles.
- Endpoint : action DRF @action(detail=True, url_path="gold-stats") dans projects/views.py renvoyant {annotatorMatrix, annotatorLlmMatrix, goldRanking, goldStale, computedAt} (camelCase auto via drf-camel-case) ; gardé par rôle reviewer/lead (cf. ProjectMembership) ; flag goldStale si des arbitrages ont eu lieu après computedAt.
- Front — visualisations « maison » SVG/CSS (zéro dépendance, tokens, zéro hex) : <ConcordanceMatrix> heatmap κ avec échelle Landis & Koch réutilisée d'IaaDashboard (kappaStrength) et cellules colorées via getThemeToken/opacité ; <AnnotatorLlmMatrix> rectangulaire réutilisant llmJudgeColor/llmJudgeLabel en colonnes ; <GoldProximityRanking> barres triées + Trophy top-3 (réutilise le motif visuel de ConcordancePanel/ConcordanceWidget).
- Intégration gestion/dashboard : onglet « Stats » de la page module GOLD (à côté de la liste docs non résolus/en cours/résolus) ; React Query hook useGoldStats(slug) dans lib/api/hooks ; data-testids gold-stats-matrix-aa, gold-stats-matrix-allm, gold-ranking-row-<id>, gold-stats-stale.
- Intégration atelier de résolution (brique B, temps réel) : panneau repliable dans l'InspectorPanel de résolution réutilisant concordance.ts (themeVectorExact, intersectionAgreement) avec le gold PROVISOIRE en cours comme vecteur supplémentaire → barres « proximité au gold » du document courant qui bougent à chaque décision d'arbitrage ; interconnexion sélection↔panneau (clause sélectionnée = surbrillance des annotateurs qui s'écartent du gold dessus).
- Export : brancher gold_ranking + matrices sur le format iaa_matrix déjà présent dans ExportJob (backend/claire/exports/services.py) pour livrer le gold intermédiaire/final avec sa matrice de concordance, sans refactorer le code iaa/concordance de prod.
- Tests : pytest sur gold_stats.py (matrice symétrique diag=1.0, gold ranking ordre desc, support n explicite, gold vide → None) ; vitest sur les 3 composants (snapshot heatmap, tri du classement, états vides/goldStale) ; MSW handler /projects/:slug/gold-stats ; cohérence chiffrée avec project_iaa_detail (mêmes vecteurs, même cohen_kappa).
