# Moteur de scoring inter-annotateurs & niveaux d'auto-résolution pour le module GOLD

## Option A — Électorat pondéré branché sur le moteur de triage existant (extension du socle)
Réutiliser le `triage_engine` (claire/triage/engine.py + engine.ts, parité golden testée) en généralisant son entrée de `theme_votes: {judge: theme}` vers un électorat à poids: `weighted_votes: {voter: {theme, weight, kind: human|llm}}`. Le comptage Counter devient une somme pondérée (annotateur w≈3, LLM w≈1, configurables). On garde TEL QUEL l'arbre C1–C5, les clusters/refuges/precedence/priority et `reliability_kappa` par thème. On ajoute un signal `human_dissent` calculé à part: si le bloc humain (vote majoritaire pondéré des annotateurs) diffère du bloc LLM majoritaire, on force `needs_human=True` et on dégrade le niveau (jamais d'auto). Le multi-label primaire+secondaires sort déjà de `validate_set`/clusters. Sortie enrichie par phrase: `{level, action, score_confiance, risk, primary, secondaries, human_dissent, weighted_tally}`.

**Forces** : Réutilise une brique PURE déjà testée en parité Python/TS sur un golden partagé — zéro dette, l'UX (file C1-C5, cartes, raccourcis) et `useTriage` se rebranchent presque tels quels ; Les niveaux d'auto-résolution existent déjà sémantiquement: C1=batch_accept (1-clic/lot), C2=confirm, C3=validate_set, C4=verify, C5=arbitrate — il suffit de mapper auto/manuel dessus ; Multi-label natif déjà géré (clusters → primary+secondary via `_choose_primary`/precedence) — couvre l'exigence primaire+secondaires sans nouveau code ; `reliability_kappa` par thème est le crochet idéal pour moduler le risque (un thème refuge/peu fiable ne s'auto-résout pas) ; Aucune migration lourde: le score vit dans le scope JSON d'ExportJob et dans des champs dérivés

**Faiblesses** : L'arbre C1–C5 a été conçu pour des juges ÉGAUX (LLM): injecter des poids hétérogènes dans un Counter entier casse la sémantique 'unanime = top_support==total' — il faut redéfinir proprement unanimité/majorité en masse pondérée (risque de régression du golden) ; Le signal 'humain ≠ LLM = signal fort' est un greffon hors-arbre — coexistence de deux logiques de décision dans un moteur censé être une fonction pure unique ; Pas de score de confiance continu natif: l'arbre est catégoriel (C1–C5), il faut bolt-on une formule de confiance/risque à côté ; Le golden existant doit être ÉTENDU (cas annotateurs+LLM), ce qui re-ouvre une brique 'figée'

**Pertinence** : Très élevée: c'est la voie qui maximise la réutilisation du socle exigée et fait tomber gratuitement l'UX C1-C5 et le multi-label. Le risque est concentré sur une seule chose — redéfinir unanimité/majorité en masse pondérée sans casser le golden LLM existant (isolable derrière un flag d'électorat).

## Option B — Moteur de scoring GOLD dédié (couche neuve) avec score de confiance continu + politique d'auto-résolution déclarative
Nouveau module `claire/gold/scoring.py` (+ miroir `gold/scoring.ts`) indépendant du triage. Fonction pure `score_sentence(annotator_votes, llm_votes, theme_reliability, weights) -> GoldSentenceScore`. Calcule: (1) une masse pondérée par thème (somme des poids des votants), (2) un `confidence ∈ [0,1]` continu = marge entre le thème gagnant et le second, normalisée et amortie par `reliability_kappa` du gagnant, (3) un `risk_band ∈ {low, medium, high}`, (4) `human_llm_divergence` (le gold humain s'écarte-t-il du consensus LLM), (5) classe `agreement_class ∈ {absolute, majority, split}`. La POLITIQUE d'auto-résolution est une table déclarative SÉPARÉE (YAML versionné, comme 07-regles-routage.yaml): ex. `absolute_human+absolute_llm → auto`, `3 LLM unanimes + ≥2/3 annotateurs + low_risk → auto`, sinon `manuel`. Multi-label: on score primaire ET secondaires séparément (un secondaire s'auto-résout s'il est porté par ≥2 annotateurs OU cluster reconnu).

**Forces** : Modèle conceptuellement propre: scoring (mesure) séparé de la politique (décision) — exactement la séparation que demande l'énoncé (scoring vs niveaux d'auto-résolution configurables) ; Score de confiance CONTINU + bandes de risque explicites → alimente directement les stats de concordance et la priorisation de la file d'arbitrage ; La table d'auto-résolution déclarative en YAML versionné colle au pattern maison (rules.yaml) et rend la config de campagne (pondérations, seuils, qui arbitre) triviale à exposer ; Le signal humain≠LLM est un champ de PREMIÈRE CLASSE, pas un greffon — naturel à surfacer dans l'UI (badge 'attention') ; Liberté totale sur la pondération annotateur>LLM et la dégradation par fiabilité de thème

**Faiblesses** : Duplique une partie de la logique du triage (clusters, refuges, precedence pour choisir le primaire en multi-label) — risque de DEUX vérités divergentes sur le multi-label, ce que la consigne interdit ; Nouveau golden + nouvelle parité Python/TS à écrire et maintenir (coût de test réel) ; L'UX C1-C5 / file de triage / cartes ne se rebranche pas gratuitement: il faut mapper `agreement_class`/`risk` vers une présentation (ou réinventer une file) ; Plus de surface neuve = plus long avant un premier rendu en prod

**Pertinence** : Élevée sur la qualité du modèle et la config de campagne, mais en tension directe avec 'NE PAS dupliquer le socle': il faut absolument que le choix primaire/secondaire en multi-label réutilise les clusters/precedence du triage plutôt que de les recopier.

## Option C — Pré-calcul batch côté serveur + cache matérialisé (table GoldSentence) avec recalcul incrémental
Indépendamment de la formule choisie (A ou B), traiter le scoring comme un ARTEFACT matérialisé. Nouveau modèle `GoldSentence(project, document, index, primary_theme, secondaries JSON, agreement_class, confidence, risk_band, auto_resolved, resolution {voter_tally, human_dissent}, decided_by, decided_at, comment)` + `GoldRun` (snapshot horodaté, comme AnnotationVersion). Un job async (réutilise l'infra ExportJob: thread daemon, EXPORTS_RUN_INLINE en test, polling 202) recalcule tout le scoring d'un lot/campagne à la demande ou à la soumission d'un annotateur. Le moteur de scoring lui-même est appelé en batch. L'UI lit GoldSentence (pas de recalcul live), le temps réel ne porte que sur le VERROU d'arbitrage et l'invalidation de cache. Export gold = sérialisation directe de GoldSentence (intermédiaire/final) via un nouveau format ExportJob.

**Forces** : Scalabilité: une campagne = N docs × M phrases × K votants; recalculer côté client à chaque rendu (comme `useTriage`) ne tient pas à l'échelle campagne — un cache matérialisé oui ; Réutilise massivement l'infra async ExportJob déjà en prod (202 non bloquant, self-heal zombie, retry, download gated) — le scoring batch et l'export gold tombent dans le même tuyau ; Traçabilité/historique natifs (GoldRun = snapshots) répondant à l'exigence audit, et stats de concordance ↔GOLD calculables sur la table figée ; Découple le MOTEUR (A ou B) de la PERSISTANCE: on peut changer la formule sans toucher l'UI ; Le verrou d'arbitrage exclusif auto-expirant se pose proprement au niveau GoldSentence/document

**Faiblesses** : N'est PAS un moteur de scoring en soi — c'est une couche de persistance/orchestration; il faut quand même choisir A ou B pour la formule (donc à combiner, pas à opposer) ; Cache matérialisé = invalidation à gérer: une annotation re-soumise doit re-déclencher le scoring du document (risque de gold périmé si l'invalidation rate) ; Migration + nouveaux modèles + nouveau format export = surface backend conséquente avant valeur visible ; Le 'temps réel' du scoring est sacrifié (batch): un arbitre voit un score figé au dernier run, pas l'effet immédiat d'une re-soumission — acceptable mais à expliciter dans l'UI

**Pertinence** : Indispensable à l'échelle campagne et pour l'audit/export, mais orthogonale à la formule de scoring: c'est l'ossature de persistance/async qui DOIT accompagner A ou B, pas un concurrent du moteur.

## ✅ Recommandation : Option A pour le MOTEUR (électorat pondéré branché sur le triage_engine existant), structurée par l'ossature de l'Option C (table GoldSentence matérialisée + scoring batch via l'infra ExportJob), en empruntant à l'Option B la SÉPARATION scoring/politique: une table d'auto-résolution déclarative YAML versionnée distincte de l'arbre de décision.

> Le socle contient déjà ce que 90% des équipes réécriraient: un moteur de routage PUR, golden-testé, à parité Python/TS, qui produit exactement les niveaux demandés (C1=batch_accept 1-clic/lot, C2=confirm, C3=validate_set multi-label, C4=verify, C5=arbitrate), gère le multi-label via clusters/precedence et porte déjà une fiabilité par thème (`reliability_kappa`). La consigne interdit la duplication: reconstruire un moteur GOLD (Option B pure) recréerait une seconde vérité sur le multi-label primaire/secondaire et un second golden — c'est le piège. On généralise donc l'ENTRÉE du moteur de `{judge: theme}` vers un électorat pondéré `{voter: {theme, weight, kind}}` et on redéfinit proprement unanimité/majorité en MASSE pondérée (annotateur w≫LLM), derrière un flag d'électorat pour ne PAS toucher le routage LLM existant ni son golden. Le signal 'décision humaine ≠ LLM = signal fort' devient un champ de première classe `human_dissent` qui FORCE `needs_human` et interdit l'auto-résolution — c'est le garde-fou qui maximise la vitesse (auto sur l'accord) tout en minimisant le risque (jamais d'auto quand l'humain s'écarte des LLM). On emprunte à B la bonne idée structurante — politique d'auto-résolution déclarative en YAML versionné (comme 07-regles-routage.yaml) — pour rendre la config de campagne (poids, seuils '3 LLM unanimes + 2/3 annotateurs', qui arbitre) triviale sans recompiler l'arbre. Enfin C est non négociable à l'échelle campagne: `useTriage` recalcule live côté client, ce qui ne tient pas sur N docs × K votants; on matérialise `GoldSentence`/`GoldRun` et on recalcule en batch via l'infra ExportJob déjà en prod (202, self-heal, retry, gating), ce qui fait tomber AUSSI l'export gold et l'historique/audit dans le même tuyau. Ce montage livre vite (réutilisation UI C1-C5), reste sûr (un seul moteur de décision, golden étendu), et passe à l'échelle.

### Détails clés d'implémentation
- Backend moteur: ajouter `claire/gold/scoring.py` qui APPELLE `triage_engine` avec une entrée généralisée; introduire `weighted_tally(votes)` remplaçant le `Counter` entier par une somme de poids — redéfinir `top_support == total` en `human_mass == total_human_mass AND llm_mass == total_llm_mass` (unanimité par strate), et `has_majority` en masse pondérée; garder INTACTS clusters/refuges/precedence/priority/reliability_kappa de `claire/triage/rules.py`
- Poids par défaut: annotateur=3, LLM=1 (configurables par campagne); calculer `human_block` (vote pondéré majoritaire des seuls annotateurs) et `llm_block` (idem LLM); `human_dissent = human_block.primary != llm_block.primary` → set `needs_human=True`, plafonner le niveau à C4/C5, exclure de l'auto
- Score continu (emprunt B): `confidence = clamp01((w_top - w_second)/w_total) * reliability_kappa.get(primary, 0.5)`; `risk_band` = high si refuge gagnant OU human_dissent OU confidence<seuil_bas, low si C1 sans dissent, sinon medium — surfacé en badge dans la carte d'arbitrage
- Politique d'auto-résolution déclarative: nouveau `docs/pactiva/dossier-gold/auto-resolution.yaml` versionné (miroir du pattern 07-regles-routage.yaml) avec règles ordonnées: `absolute_all → auto_1click`; `llm_unanime>=3 AND annotators_majority>=2/3 AND risk=low AND NOT human_dissent → auto`; sinon `manual`. Chargé par scoring.py, exposé en lecture seule dans la config de campagne
- Multi-label primaire+secondaires: réutiliser `_choose_primary`/`precedence`/clusters du triage pour ordonner; un SECONDAIRE s'auto-valide s'il est porté par ≥2 annotateurs OU par un couple cluster reconnu, sinon il part en `validate_set` (C3) manuel — aligne sur `ClauseTheme.role` et `validate_clause_theme_set`
- Persistance (Option C): modèles `GoldSentence(project, document, index, primary_theme FK, secondaries JSON, agreement_class, confidence, risk_band, auto_resolved bool, resolution JSON {voter_tally, human_block, llm_block, human_dissent}, decided_by, decided_at, comment)` + `GoldRun` snapshot (calqué sur `AnnotationVersion`); contrainte unique (project, document, index)
- Async + invalidation: recalcul batch via l'infra ExportJob (thread daemon, `EXPORTS_RUN_INLINE` en test, 202 + polling adaptatif); re-déclencher le scoring du document à chaque (re)soumission d'`Annotation` du doc; un `GoldRun` horodaté par lot pour l'audit
- Parité & golden: ÉTENDRE le golden partagé (`frontend/src/lib/triage/golden.cases.json` + `backend/tests/test_triage_parity.py`) avec des cas électorat mixte annotateurs+LLM; le miroir TS `gold/scoring.ts` réutilise `engine.ts` exactement comme le backend réutilise `engine.py`
- Frontend: rebrancher `useTriage`/`TriageQueue`/cartes sur les niveaux C1-C5 du gold; bouton 1-clic 'Accepter le lot' sur les runs C1 contigus (regroupement des blocs d'accord continus, exigence mise en page contrat); badge `risk`/`human_dissent` riche en hover; navigation désaccord-à-désaccord déjà fournie par `byLevel`
- Export gold: nouveau format ExportJob (`gold_jsonl`/`gold_csv`) sérialisant `GoldSentence` (intermédiaire = run courant, final = run figé après verrouillage projet), réutilisant `ExportJob.scope` JSON et le download gated existant
- Stats de concordance ↔GOLD: réutiliser `intersectionAgreement`/`concordanceReport` (concordance.ts) et `_intersection`/`_theme_vector` (concordance.py) en passant le vecteur GOLD comme référence → 'qui est le plus proche du gold' (annotateur↔gold, LLM↔gold) sans nouveau calcul d'accord
