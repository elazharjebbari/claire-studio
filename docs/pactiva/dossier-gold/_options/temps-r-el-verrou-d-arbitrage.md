# Temps réel & verrou d'arbitrage

## A — Verrou DB-source-de-vérité + heartbeat REST, WS pour diffusion seule (lease model)
Le verrou d'arbitrage est une nouvelle ressource serveur durable (modèle GoldLock: doc/lot, holder, acquired_at, expires_at, optional note) avec POST acquire/heartbeat/release/steal, sur le modèle EXACT des actions lock/unlock déjà en place (annotations/views.py:278, projects/views.py:51). Acquisition atomique via select_for_update + comparaison expires_at: un seul arbitre gagne. Le client envoie un heartbeat REST toutes ~20s (lease ~60-90s); quitter la page (beforeunload + sendBeacon release) ou inactivité = expiration naturelle côté serveur. Le WS de présence (PresenceConsumer) est étendu d'un simple message lock.update qui DIFFUSE l'état (sans en être la source) pour que les autres voient instantanément 'arbitré par X'. Traçabilité: ArbitrationEvent (qui, quoi, quand, note optionnelle) écrit à chaque décision GOLD, indépendant du verrou.

**Forces** : Source de vérité durable et auditable: survit aux redémarrages WS, multi-worker, et au fait que prod n'a PAS encore Redis (CACHES=LocMemCache par défaut, channel layer InMemory). Le verrou ne peut PAS reposer sur le cache actuel. ; Réutilise à l'identique le pattern lock/unlock/locked_by/locked_at déjà validé prod (Annotation/Project) + ws_auth JWT + PresenceConsumer existants; faible risque. ; Auto-expiration robuste: expiration calculée serveur (expires_at), pas dépendante du WS onclose qui est non fiable (onglet tué, réseau coupé). ; steal/override explicite (lead/reviewer) trivial à implémenter et à auditer. ; Dégrade proprement: si WS off, le verrou reste fonctionnel en pur REST (polling), cohérent avec le repli REST déjà conçu (useLivePresence).

**Faiblesses** : Latence de diffusion du verrou ~heartbeat si on n'ajoute pas le message WS (mitigé en ajoutant lock.update au consumer). ; Heartbeat REST = un peu de trafic périodique (négligeable: 1 req/20s/arbitre). ; Nécessite une migration + nouveau modèle (GoldLock/ArbitrationEvent).

**Pertinence** : Idéal: répond directement à 'verrou EXCLUSIF auto-expirant' + 'traçabilité qui a arbitré quoi + note optionnelle' sans dépendre d'infra absente en prod. La durabilité DB est non négociable pour un verrou d'arbitrage qui gate l'écriture du GOLD.

## B — Verrou 100% temps réel porté par le WS/cache (presence-as-lock, ownership éphémère)
Le verrou devient un attribut du roster de présence: on étend PresenceConsumer pour qu'à l'entrée dans la salle d'arbitrage d'un doc, le premier arbitre 'claim' le lock stocké dans le même cache que le roster (consumers.py:55 _write, TTL déjà à 120s). disconnect() (consumers.py:39) libère immédiatement; le TTL cache assure l'auto-expiration en cas de crash. Diffusion instantanée via le group_send existant. Pas de heartbeat REST: la connexion WS vivante EST le heartbeat. Note d'arbitrage et historique restent en DB (ArbitrationEvent) écrits au moment de la décision.

**Forces** : Temps réel parfait et libération immédiate à la déconnexion: l'expérience 'le verrou se libère quand je pars' est native (disconnect()). ; Réutilise au maximum l'infra présence: minimal de code neuf côté transport. ; Aucun trafic de heartbeat REST; latence quasi nulle pour voir qui arbitre.

**Faiblesses** : FRAGILE en l'état prod: le roster vit dans CACHES par défaut = LocMemCache (par-process, NON partagé) et le channel layer est InMemory. Sans Redis (absent du deploy actuel), un verrou cache n'est ni partagé entre workers ni durable → faux sentiment d'exclusivité. ; Le verrou disparaît si le process WS redémarre ou si le TTL expire alors que l'arbitre est toujours actif (faux unlock pendant une longue arbitrage). ; Pas de source de vérité durable: difficile à auditer/forensique, et 'steal' par un lead nécessite quand même un canal serveur. ; Verrou non interrogeable par le module de gestion (liste docs résolus/en cours) sans WS connecté.

**Pertinence** : Séduisant sur le papier (temps réel pur) mais risqué: un verrou qui GATE l'écriture du GOLD ne doit pas reposer sur un cache non partagé/non durable. Acceptable seulement APRÈS bascule Redis prod, et même alors la durabilité reste faible.

## C — Verrou advisory DB (PostgreSQL advisory lock / row lock) sans nouvelle table, WS optionnel
On s'appuie sur les verrous applicatifs natifs: soit pg_advisory_lock(docId) côté session, soit on réutilise directement les champs locked/locked_by/locked_at du doc (réutilisation littérale du champ existant) en posant que 'arbitrage en cours' = doc locked par un arbitre. L'expiration repose sur un job/balayage (cron ou check lazy à l'acquisition: si locked_at trop ancien → reprise). WS sert uniquement à rafraîchir l'UI.

**Forces** : Zéro ou quasi-zéro nouveau modèle: réutilise locked/locked_by/locked_at déjà migrés et le pattern lock/unlock prod. ; Exclusivité garantie par la DB sans Redis. ; Très peu de surface de code.

**Faiblesses** : Réutiliser le champ 'locked' métier (verrou de campagne/figeage) pour 'arbitrage en cours' crée une COLLISION sémantique: locked sert déjà à figer un doc/projet (ProjectLockControl) — on mélange 'figé définitif' et 'occupé temporairement'. ; pg_advisory_lock est lié à la durée d'une connexion DB: incompatible avec un cycle requête/réponse REST stateless (le lock se relâche à la fin de la requête) → inutilisable tel quel pour un verrou inter-requêtes. ; Auto-expiration nécessite un balayage périodique (cron/Monitor) ou logique lazy fragile; pas de heartbeat → soit on expire trop tôt, soit trop tard. ; Pas de note/commentaire ni d'historique dédié sans table additionnelle → on retombe partiellement sur A.

**Pertinence** : La plus économe mais la moins propre: collision sémantique avec le verrou de campagne existant et inadéquation des advisory locks au REST stateless. À écarter sauf comme repli minimal.

## ✅ Recommandation : A — Verrou DB-source-de-vérité (modèle GoldLock + lease/heartbeat REST) avec diffusion temps réel via le PresenceConsumer existant

> C'est la seule option qui satisfait simultanément les trois exigences (exclusif, auto-expirant, traçable) SANS dépendre d'une infra absente en prod. Constat de code décisif: le verrou d'arbitrage va GATER l'écriture de la base GOLD — il doit donc être durable et partagé. Or la présence actuelle (consumers.py) stocke son roster dans le cache Django par défaut = LocMemCache (aucun override CACHES dans config/settings), et le channel layer n'est Redis que si CHANNELS_USE_REDIS=true (base.py:138), ce qui n'est PAS câblé dans deploy/. Faire porter le verrou par le cache/WS (option B) donnerait une exclusivité illusoire en multi-worker. L'option C casse sur l'inadéquation des advisory PG au REST stateless et sur la collision sémantique avec le 'locked' de campagne déjà en prod (ProjectLockControl/Annotation.locked). L'option A calque exactement le pattern lock/unlock déjà éprouvé en prod, garde le WS dans son rôle naturel (diffusion de présence/état), et rend l'auto-expiration robuste car calculée serveur (expires_at) plutôt que tributaire d'un onclose WS non fiable. Le temps réel reste excellent en ajoutant un simple message lock.update au groupe de présence pour la diffusion instantanée.

### Détails clés d'implémentation
- Modèle backend GoldLock(document FK, scope: 'document'|'batch', holder FK->user, acquired_at, expires_at, note TEXT null, version int) + ArbitrationEvent(document, sentence/clause ref, actor, verb: 'decide'|'override'|'comment', payload JSON, note, created_at) pour la traçabilité 'qui a arbitré quoi'.
- Endpoints REST calqués sur annotations/views.py:278 lock/unlock: POST /gold/{docId}/lock:acquire (select_for_update + check now>expires_at → réattribue), POST .../lock:heartbeat (prolonge expires_at), POST .../lock:release, POST .../lock:steal (réservé lead/reviewer, écrit ArbitrationEvent verb=override). Lease 90s, heartbeat 20s.
- Front: hook useArbitrationLock (React Query) avec setInterval heartbeat 20s + window.addEventListener('beforeunload', () => navigator.sendBeacon(releaseUrl)); détection d'inactivité (pas d'input/mousemove ~60s) → stoppe le heartbeat → expiration naturelle serveur.
- Diffusion temps réel: étendre PresenceConsumer (consumers.py) d'un handler receive 'lock' qui group_send {type:'lock.update', holder, expiresAt}; côté client createWebSocketCollab.onPresence reçoit déjà le roster — ajouter un onLock parallèle. Si WS off, repli polling REST identique au pattern useLivePresence.ts.
- Réutiliser ws_auth.JWTAuthMiddleware (token query string) et routing.py: nouvelle route ws/arbitration/{docId}/ ou réutiliser ws/presence/ avec un type de salle 'gold'.
- UI: badge 'Arbitré par {name}' (couleur user_color déjà dispo via common.identity), bandeau read-only quand verrou tenu par un autre, bouton 'Reprendre l'arbitrage' (steal) visible lead/reviewer; data-testids gold-lock-banner, gold-lock-acquire, gold-lock-steal, gold-arbitration-note.
- Module de gestion: la liste docs (non résolus/en cours/résolus/%) lit GoldLock.holder/expires_at en DB → statut 'en cours' fiable même sans WS, contrairement à un verrou cache.
- Prérequis prod à signaler: pour le temps réel multi-worker, activer CHANNELS_USE_REDIS=true + REDIS_URL et un CACHES Redis partagé (deploy/ ne les câble pas encore); le verrou A reste correct sans Redis car sa vérité est en DB.
