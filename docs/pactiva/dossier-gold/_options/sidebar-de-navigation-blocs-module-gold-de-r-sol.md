# Sidebar de navigation (blocs) — module GOLD de résolution inter-annotateurs

## Sidebar à deux pistes synchronisées (Plan + Divergences) en onglets segmentés
Une seule colonne gauche réutilisant le gabarit TocPanel (en-tête + nav scrollable flex-1 + barre de sélection), mais avec un switch segmenté en tête : « Plan » (blocs de clauses style sommaire de contrat, dérivés de deriveBlocks sur le GOLD courant) et « Divergences » (blocs de désaccord, dérivés d'un divergenceSegments généralisé N-annotateurs). Le même composant ClauseChip/bloc sert dans les deux pistes ; on n'affiche qu'une piste à la fois. Chaque entrée porte un état (résolu / en cours / non résolu) et un mini-indicateur de sévérité (accord absolu, divergence LLM-only, divergence humaine forte). Clic d'une entrée → selectClause + focusSentence (sync existante), retour scrollIntoView du chip déjà câblé.

**Forces** : Réutilise quasi tel quel TocPanel + divergence.ts + blocks.ts + la sync focusSentence/selectClause/scrollIntoView déjà en place — coût d'implémentation minimal, aucune duplication ; Le switch segmenté est un pattern déjà présent (LangSwitch/WorkspaceToolbar), a11y et tokens connus ; Une seule colonne = on garde ResizablePanels à 3 zones, rien à recomposer ; mémoire de layout par doc inchangée ; Plan « façon contrat » immédiat via deriveBlocks (regroupe les suites de même thème) → factorisation visuelle demandée

**Faiblesses** : Une piste cache l'autre : on ne voit pas simultanément la place d'une divergence dans le plan global du contrat ; Le switch ajoute un clic/un raccourci pour passer plan↔divergences (friction légère sur le geste « sauter de désaccord en désaccord » si on est sur la piste Plan) ; Risque de désynchronisation perçue : si on résout un désaccord, il faut rafraîchir le compteur des deux pistes

**Pertinence** : Très bonne adéquation court terme : capitalise au maximum sur le socle (DivergenceNav devient une piste, TocPanel devient l'autre) et livre les deux modes de navigation exigés (a) blocs similaires et (b) blocs de divergence avec un effort réduit. Limite : ne montre pas les deux dimensions d'un coup.

## Sidebar unifiée « partition de contrat » : un seul plan, divergences incrustées en sous-blocs
Une liste unique style sommaire de contrat où les blocs d'accord continus (deriveBlocks) sont regroupés et factorisés (catégorie en avant, comme des articles/sections), et où les phrases en désaccord apparaissent comme des sous-entrées surlignées (puce de sévérité, pastille de vote « 3 annot. / 2 LLM »). Un filtre/cycle « divergences seules » replie les blocs d'accord pour transformer la même liste en file de désaccords. La navigation désaccord→désaccord (n/p, façon useDivergenceShortcuts) saute d'un sous-bloc divergent au suivant sans changer de vue. Tout est piloté par une structure dérivée unique mêlant blocks.ts et divergenceSegments généralisés.

**Forces** : Vue mentale unique = mise en page la plus proche d'un contrat réel (articles regroupés, désaccords visibles dans leur contexte) — répond pile à « regrouper les blocs d'accord, catégorie en avant, factoriser » ; Aucune bascule d'onglet : sauter de désaccord en désaccord ET situer le désaccord dans le contrat se font dans la même liste → moins de charge cognitive, gestes enchaînés sous le curseur ; Le repli/dépli (accord ↔ divergences-seules) est un seul état booléen mémorisable par doc, pas deux pistes à maintenir cohérentes ; Sévérité + votes (humain>LLM) visibles inline → le signal fort « décision humaine ≠ LLM » saute aux yeux dans le plan

**Faiblesses** : Structure de données dérivée plus riche à concevoir/tester (fusionner runs same-theme ET segments de divergence multi-source, gérer multi-label primaire+secondaire) — plus de travail pur que l'option 1 ; Risque de surcharge visuelle sur documents longs très divergents (beaucoup de sous-entrées) → besoin d'une virtualisation/regroupement soigné ; Le repli des accords peut désorienter si mal animé (les indices de phrase « sautent »)

**Pertinence** : La plus alignée sur la contrainte UX maîtresse (mise en page proche d'un contrat + factorisation + catégorie en avant) et sur l'interconnexion navbar↔zone↔sélection. C'est l'option « top agence » mais elle demande une nouvelle brique pure de fusion blocs/divergences bien testée.

## Double rail : minimap verticale de sévérité (fine) + liste de blocs (large), couplées
Deux sous-colonnes dans l'aside gauche : (1) une minimap verticale ultra-fine sur toute la hauteur du doc (un trait par phrase, couleur = thème, intensité = sévérité de divergence, marqueur = état résolu), façon scrollbar sémantique ; (2) à sa droite, la liste de blocs de clauses (deriveBlocks). Survol de la minimap → tooltip riche (votes, sources) + preview ; clic → focusSentence. La liste de blocs offre la navigation « sommaire de contrat » ; la minimap offre le saut désaccord→désaccord visuel et la densité globale en un coup d'œil. Les deux sont liées au même curseur de focus et se surlignent mutuellement.

**Forces** : La minimap donne une lecture instantanée de la densité/sévérité des conflits sur tout le doc (impossible avec une liste seule) — excellent pour l'arbitre qui priorise ; Deux modes de navigation coexistent sans onglet : grain fin (minimap) + grain bloc (liste) ; Survols riches + clic-sans-bouger : la minimap est dense, le curseur reste dans la zone, les éléments défilent dessous ; Un composant minimap réutilisable au-delà du GOLD (atelier /annotate pourrait en profiter)

**Faiblesses** : Consomme de la largeur dans une UI déjà à 3 panneaux redimensionnables ; la minimap fine est un défi d'a11y (cibles minuscules) et de tokens (intensité sans hex en dur → échelle de tokens à créer) ; Composant minimap entièrement nouveau (rendu performant par phrase, hit-testing, tooltip ancré) = le plus gros coût des trois, peu de réutilisation directe du socle ; Sur petits écrans, deux sous-colonnes + 3 panneaux = densité difficile à tenir ; risque de doublonner la fonction de la liste

**Pertinence** : Forte valeur d'arbitrage (priorisation visuelle des zones chaudes) et très « premium », mais c'est l'option la plus coûteuse et la plus risquée a11y/tokens, avec le moins de réutilisation du socle existant. Pertinente comme évolution, pas comme socle de la v1.

## ✅ Recommandation : Option 2 — Sidebar unifiée « partition de contrat » avec divergences incrustées, doublée du repli/dépli « divergences seules » (et, en interne, factorisée pour pouvoir basculer vers les onglets de l'option 1 si besoin).

> La contrainte UX maîtresse du brief est « mise en page PROCHE d'un contrat juridique : regrouper les blocs d'accord continus, mettre la catégorie en avant, factoriser, lisibilité maximale » ET « navigation rapide entre désaccords ET entre blocs de clauses similaires » avec interconnexion totale navbar↔zone↔sélection. L'option 1 livre les deux modes mais les sépare en onglets, ce qui casse précisément le geste-clé (situer un désaccord dans le contrat tout en sautant de l'un à l'autre). L'option 3 est superbe mais coûteuse, risquée a11y/tokens et peu réutilisable pour une v1. L'option 2 unifie les deux navigations dans une seule liste « sommaire de contrat », réutilise le gabarit TocPanel (en-tête figé + nav flex-1 scrollable + barre de sélection), la sync focusSentence/selectClause/scrollIntoView déjà câblée, les chips/blocs existants, et les fonctions pures divergence.ts + blocks.ts. Le seul vrai nouveau livrable est une brique PURE de fusion (blocs d'accord same-theme ⊕ sous-blocs de divergence multi-source/multi-label), parfaitement testable comme l'est déjà runs.ts/blocks.ts/divergence.ts — donc dans la culture du repo. On garde l'architecture à 3 panneaux et la mémoire de layout par doc intactes. Recommandation d'implémentation factorisée : coder la structure dérivée et le composant de liste de façon à ce que le mode « onglets » de l'option 1 reste activable derrière un flag, ce qui dérisque la livraison.

### Détails clés d'implémentation
- Nouvelle lib pure frontend/src/lib/goldOutline.ts : buildOutline(blocks: Block[], divergence: {bySource: Record<string,(string|null)[]>}, resolved: Set<number>) → liste d'entrées {kind:'accordBlock'|'divergence', start, end, theme, severity, votes:{humans,llms}, status:'unresolved'|'inProgress'|'resolved'}. Réutilise deriveBlocks (runs perSentence) pour les accords et un divergenceSegments GÉNÉRALISÉ N-sources (pas seulement claude/codex) : étendre divergence.ts pour accepter un Record<source,(string|null)[]> et calculer divergence = ≥2 thèmes distincts présents.
- Sévérité dérivée du moteur de scoring (humain>LLM) : niveau 'accordAbsolu' (1 thème) / 'llmOnly' (LLM divergent, humains d'accord) / 'humainFort' (au moins un humain ≠ majorité LLM = signal fort du brief) ; mappée sur des tokens d'intensité (ex. --gold-sev-1..3), ZÉRO hex en dur, à ajouter dans lib/tokens.ts + la charte docs/pactiva/.
