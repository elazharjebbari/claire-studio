# Config de campagne de résolution (interface de paramétrage AVANT lancement de la résolution inter-annotateurs vers une base GOLD)

## Option A — Config minimale dans Project.settings (sous-clé resolution{}), édition inline sur la page admin/projects/[slug]
Réutiliser tel quel le JSONField Project.settings (déjà sérialisé/round-trip via ProjectSerializer) en y ajoutant une sous-clé resolution{}. Un panneau 'Résolution GOLD' s'ajoute à la page admin existante /admin/projects/[slug]/page.tsx, à côté des sections membres + verrou déjà présentes. Paramètres réduits au strict nécessaire: pondération binaire (LLM compte / ne compte pas), seuil unique d'auto-décision, partage auto on/off, secondaires obligatoires on/off. Pré-rempli 'confiance aux annotateurs' = LLM départage seulement les ex-aequo, partage on, seuils prudents. Lecture via mergeResolutionConfig(DEFAULTS, project.settings.resolution) calqué sur mergeUiPrefs.

**Forces** : Coût quasi nul: Project.settings existe et est déjà writable côté admin (serializers.py l.33), aucune migration ; Réutilise mergeUiPrefs (whitelist + défauts + soft-migration) → robuste aux ajouts de juges/champs sans migration ; Surface UI minuscule: un bloc de plus sur la page admin déjà connue des leads, zéro nouvel écran à apprendre ; Le pré-remplissage 'confiance annotateurs' est trivial à exprimer en quelques flags

**Faiblesses** : N'exprime PAS la richesse demandée: pas de pondération PAR annotateur, pas de distinction arbitre↔visualiseur fine, pas de seuils par niveau de risque (C1–C5) ; Pondération LLM binaire ignore 'quand/comment' le LLM intervient (départage, signal, jamais) ; settings{} libre = pas de validation serveur typée; un payload incohérent (seuil>1) peut passer si le merge front est contourné via l'API ; Pas de versionnage de la config par campagne ni d'historique des changements de paramètres (traçabilité faible)

**Pertinence** : Répond au 'modifiable' et au pré-remplissage, mais sous-dimensionné face au besoin explicite (pondérations fines, arbitres, seuils par risque, partage révocable). Bon pour un MVP, insuffisant comme cible 'aussi aboutie que /annotate'.

## Option B — Modèle dédié ResolutionCampaign + table de pondérations par participant, écran de config en assistant (wizard) sticky
Créer un modèle ResolutionCampaign(project, scope=docs/lot, status draft|running|closed, config JSON validé par serializer typé, version) + ResolutionWeight(campaign, subject_type=annotator|judge, subject_ref LIBRE, weight float, mode) + champ arbiter sur ProjectMembership (ou table ResolutionArbiter). Un écran /admin/projects/[slug]/resolution en assistant 3 étapes (Périmètre → Voix & pondérations → Règles & partage) avec récap sticky façon InspectorPanel. Pondération LLM avec MODE explicite par juge: ignore | tiebreak | signal | full, + poids; pondération par annotateur (curseurs); rôles arbitre/visualiseur dérivés de membership (lead/reviewer=arbitre par défaut); seuils d'auto-décision PAR niveau de risque (accord absolu→1 clic; C1–C2 faible risque→auto; C3–C5→manuel); secondaires obligatoires on/off; partage auto révocable. Config gelée/copiée à snapshot au lancement (immutable record) → traçabilité.

**Forces** : Couvre TOUS les paramètres demandés (pondération par annotateur ET par juge avec mode/quand/comment, arbitres, seuils par risque C1–C5, partage révocable, secondaires) ; Snapshot immutable de la config au lancement = traçabilité réelle (qui a configuré quoi, quand) alignée sur l'exigence 'historique' ; subject_ref LIBRE pour les juges (jamais d'enum figée) → cohérent avec la doctrine 'ids de modèle libres' du schéma prefs ; Serializer typé = validation serveur (poids∈[0,1], seuils monotones) impossible à contourner via l'API brute ; Scope par lot/campagne mappe directement sur ExportJob.scope et permet plusieurs résolutions concurrentes (intermédiaire vs final)

**Faiblesses** : Coût élevé: nouveaux modèles + migrations + serializers + endpoints + nouvel écran wizard, charge la plus lourde des trois ; Risque de sur-paramétrage: trop de leviers tue l'ergonomie si le pré-remplissage n'est pas excellent (la plupart des leads garderont les défauts) ; Le wizard multi-étapes va à l'encontre du 'clics successifs sans bouger la souris' si mal fait (étapes = navigation longue) ; Duplication potentielle avec ProjectMembership (rôles) si arbitre n'est pas dérivé proprement des rôles existants

**Pertinence** : C'est la cible fonctionnelle complète et la seule qui assure la traçabilité par snapshot et la pondération fine 'quand/comment'. Le risque est l'ergonomie du wizard et le sur-coût si tout est livré d'un bloc.

## Option C — Config typée dans Project.settings.resolution{} (schéma versionné, validé) + 'Studio de config' en panneau unique progressive-disclosure, presets + override par participant
Compromis: garder le stockage léger (Project.settings.resolution{}, zéro migration) MAIS le typer comme le schéma prefs (resolutionConfig.ts pur + version + mergeResolutionConfig + validateResolutionConfig côté serializer DRF). UN seul panneau 'Studio de résolution' greffé sur /admin/projects/[slug] (pas de wizard): un PRESET en tête ('Confiance annotateurs' par défaut / 'Équilibré' / 'Audit strict') qui pré-remplit tout, puis progressive-disclosure: réglages avancés repliés (pondérations par participant, seuils par risque). La pondération LLM est un mode global llmRole: ignore|tiebreak|signal|full + override par juge optionnel (map LIBRE judgeId→{role,weight}); pondération annotateur = map LIBRE userId→weight (défaut 1, 'décision humaine ≠ LLM = signal fort' encodé par signalBonus). Arbitres = liste d'userIds (défaut: leads+reviewers via my_role), visualiseurs = reste des membres. Partage auto révocable = autoShare:true. Secondaires: secondaryPolicy: optional|required|advisory. Traçabilité via un mini journal configChanges[] horodaté dans le même JSON (append-only) — pas de table, mais historique conservé. Tout modifiable tant que la campagne n'est pas verrouillée (réutilise Project.locked).

**Forces** : Zéro migration (Project.settings existe et round-trip) tout en obtenant un schéma TYPÉ + versionné + validé serveur, comme le socle prefs (schema.ts/mergeUiPrefs) — pattern déjà éprouvé et testé ; Couvre la quasi-totalité des paramètres demandés: llmRole avec quand/comment (ignore/tiebreak/signal/full), poids par annotateur ET par juge (maps LIBRES, robustes aux ajouts), arbitres/visualiseurs, seuils par risque C1–C5, secondaires, partage révocable ; Presets + progressive-disclosure = ergonomie 'de tonnerre': le lead garde le défaut 'confiance annotateurs' en 1 vue, l'expert déplie l'avancé sous le curseur sans changer d'écran (pas de wizard) ; Traçabilité légère mais réelle via configChanges[] append-only horodaté, sans nouvelle table ; Réutilise Project.locked comme gel de config (déjà câblé: toggle-project-lock, lockProject/unlockProject) → cohérence avec le gel de campagne existant

**Faiblesses** : JSON unique sans relations: requêter 'qui arbitre dans toutes les campagnes' est moins direct qu'avec un modèle dédié (acceptable au volume actuel) ; configChanges[] dans le même blob grossit le settings et n'offre pas la rigueur d'un audit-trail relationnel (suffisant pour la traçabilité de config, pas pour l'audit des décisions de fusion — qui vit ailleurs) ; Une seule campagne de résolution par projet dans le blob (sauf à indexer par lot) — multi-campagnes concurrentes moins naturel qu'en Option B ; La validation serveur doit être écrite à la main dans le serializer (pas 'gratuite' comme des champs de modèle)

**Pertinence** : Meilleur rapport richesse/coût/ergonomie: atteint ~90% du périmètre B sans migration ni wizard, en capitalisant exactement sur les patterns maison (schéma versionné + merge + Project.settings + Project.locked). Aligné mot pour mot avec 'modifiable', 'pré-rempli confiance annotateurs', tokens/a11y.

## ✅ Recommandation : Option C — Config typée versionnée dans Project.settings.resolution{} + Studio de config en panneau unique (presets + progressive-disclosure), modifiable tant que la campagne n'est pas verrouillée

> C'est l'option qui maximise richesse fonctionnelle, ergonomie et réutilisation du socle, au coût le plus faible. Le besoin exige une config FINE (pondération LLM 'quand/comment', pondération par annotateur, arbitres vs visualiseurs, seuils d'auto-décision par risque, partage révocable, secondaires obligatoires), pré-remplie 'confiance aux annotateurs' et MODIFIABLE — tout cela s'exprime parfaitement dans un schéma TYPÉ versionné, exactement le pattern déjà éprouvé et testé du socle (frontend/src/lib/prefs/schema.ts: version + mergeUiPrefs whitelist+défauts+soft-migration, ids de modèle LIBRES jamais d'enum). Le stockage est gratuit: Project.settings (JSONField) est déjà writable et round-trip via ProjectSerializer (backend/claire/projects/serializers.py l.33), donc ZÉRO migration contre l'Option B. Côté UX, le couple preset + progressive-disclosure tient la contrainte 'clics sans bouger la souris / panneaux interconnectés' bien mieux qu'un wizard multi-étapes (Option B): un lead voit le défaut en une vue, l'expert déplie l'avancé sur place. La pondération LLM par MODE (ignore|tiebreak|signal|full) capture le 'quand/comment' que l'Option A binaire rate, et le bonus 'décision humaine ≠ LLM = signal fort' est encodable directement. On réutilise Project.locked (toggle déjà câblé) pour geler la config = cohérence avec le gel de campagne existant. L'Option B reste la cible si l'on a besoin de multi-campagnes concurrentes et d'un audit relationnel des configs, mais elle peut être atteinte plus tard en migrant le blob validé vers des modèles — la forme de C est volontairement compatible.

### Détails clés d'implémentation
- Schéma: nouveau frontend/src/lib/resolution/config.ts — interface ResolutionConfigV1 { v:number; llm:{ role:'ignore'|'tiebreak'|'signal'|'full'; weight:number; perJudge:Record<string,{role?,weight?}> /* ids LIBRES */ }; annotatorWeights:Record<string,number> /* userId→poids, défaut 1 */; signalBonus:number /* décision humaine ≠ LLM */; autoResolve:{ absoluteAgreement:boolean /* accord absolu = 1 clic */; lowRiskLevels:('C1'|'C2'|'C3'|'C4'|'C5')[] /* auto */; manualLevels:(...)[] }; arbiters:number[] /* userIds, défaut leads+reviewers */; autoShare:boolean /* défaut true, révocable */; secondaryPolicy:'optional'|'required'|'advisory'; configChanges:{at,by,patch}[] }
- mergeResolutionConfig(DEFAULTS, raw) + migrateResolutionConfig(raw) calqués 1:1 sur mergeUiPrefs/migratePrefs (whitelist par section, énumérations bornées, maps LIBRES via cleanMap, version croissante) — réutiliser les helpers isObj/asBool/asStr/cleanBoolMap de schema.ts
- Pré-remplissage 'CONFIANCE AUX ANNOTATEURS' (RESOLUTION_CONFIG_DEFAULTS): llm.role='tiebreak' (LLM départage seulement les ex-aequo), llm.weight=0.5, annotatorWeights={} (tous=1), signalBonus actif, autoResolve.absoluteAgreement=true, lowRiskLevels=['C1','C2'], manualLevels=['C3','C4','C5'], arbiters dérivés des memberships role∈{lead,reviewer}, autoShare=true, secondaryPolicy='advisory'
- Backend: valider dans ProjectSerializer (ou un ResolutionConfigSerializer dédié monté sur PATCH /api/projects/{slug}/) — bornage weight∈[0,1], seuils cohérents, role∈enum, userIds ∈ memberships du projet ; append automatique à configChanges[] {at:now, by:request.user.id, patch:diff} à chaque écriture (traçabilité sans table)
- UI: section 'Studio de résolution' ajoutée à frontend/src/app/(app)/admin/projects/[slug]/page.tsx (à côté des sections membres l.355+ et verrou l.638) ; en-tête = <PresetPicker> (Confiance annotateurs / Équilibré / Audit strict) qui écrase la config ; <details>/disclosure 'Réglages avancés' replié par défaut ; data-testid: resolution-config-panel, resolution-preset, llm-role-select, annotator-weight-{userId}, autoshare-toggle, secondary-policy, arbiter-checkbox-{userId}, save-resolution-config
- Gel: réutiliser Project.locked + endpoints lockProject/unlockProject (data-testid toggle-project-lock déjà présent l.686) — config en lecture seule quand locked ; afficher un bandeau 'Campagne verrouillée — config figée' avec tokens existants (zéro hex)
- Tokens/a11y: curseurs de pondération = inputs range tokenisés, labels reliés (aria-describedby), focus visible ; animations de disclosure sobres (réutiliser la même classe de transition que les panneaux InspectorPanel)
- Le moteur de scoring consomme cette config: annotatorWeights × votes humains (exact per-sentence via iaa._theme_vector) ; llm.role/weight applique les votes juges (forward-fill via concordance._judge_vector) ; signalBonus déclenché quand best_match LLM diverge de la décision humaine — ne PAS dupliquer iaa.py/concordance.py, les paramétrer
