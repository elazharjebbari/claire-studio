# Ergonomie « clics successifs » & interconnexion pour le module GOLD de résolution de conflits inter-annotateurs

## Option A — File de décision « cursor-park » étendue depuis QuickActionRail/Triage
Reprendre TEL QUEL le pattern sticky-cursor déjà éprouvé dans QuickActionRail (`onValidateAdvance(index, clientY)` + scroll côté DocumentPanel qui ramène l'action suivante SOUS le curseur) et le généraliser à une « file de conflits ». Chaque conflit (phrase/bloc en désaccord) est une carte dont le bouton primaire « Adopter + suivant » se re-positionne au même clientY après résolution. Réutiliser `useDivergenceShortcuts` (n/p, 1/2 = adopter juge) en l'élargissant à des touches par option de vote (1..9 = la k-ième proposition: annotateur A, annotateur B, LLM claude…). Navigation des conflits = `divergenceSegments`/`nextDivergence`/`divergenceOrdinal` (déjà purs, déjà testés) recablés sur des vecteurs INTER-ANNOTATEURS au lieu de Claude/Codex. Le DivergenceNav existant devient une « ConflictNav » (◂ k/N ▸). Interconnexion via le store workspace existant (`selectClause`/`focusSentence`) déjà écouté par TocPanel/DocumentPanel/InspectorPanel.

**Forces** : Coût quasi nul: le sticky-cursor (clic enchaîné sans bouger la souris) EXISTE déjà et est validé en prod (QuickActionRail + scroll DocumentPanel), donc zéro risque sur la mécanique la plus délicate ; divergence.ts (segments/anchors/next/prev/ordinal) est PUR et déjà testé — on le ré-instancie sur des vecteurs inter-annotateurs sans réécrire la logique de navigation ni de regroupement en blocs contigus ; Raccourcis (n/p/1/2) et focus management déjà montés et anti-saisie (isEditable) — extension naturelle à 1..9 votes ; Interconnexion panneaux gratuite: selectClause/focusSentence sont déjà la colonne vertébrale écoutée par les 3 panneaux

**Faiblesses** : Le sticky-cursor actuel est par-phrase: un conflit GOLD porte souvent sur un BLOC (suite de phrases même catégorie) → il faut élargir l'unité de parcage du curseur au bloc, sinon clics redondants ; useDivergenceShortcuts est binaire (Claude/Codex via 1/2); passer à N votes (annotateurs+LLM) demande une table de mapping touche→option stable et lisible dans le hover ; La file de triage C1–C5 est conçue pour 1 annotateur vs LLM, pas pour l'agrégation multi-annotateurs — le scoring doit être injecté en amont (pas un blocage UX mais une dépendance)

**Pertinence** : Très élevée: c'est l'option qui réutilise le PLUS le socle exact exigé (sticky-cursor, divergence.ts, shortcuts, focus store) et porte le moins de risque sur l'ergonomie « clics successifs ». Idéale comme socle de la V1 du module GOLD.

## Option B — Cockpit interconnecté piloté par un store dédié `goldStore` (hover/selection bus partagé)
Introduire un store Zustand DÉDIÉ au GOLD (miroir de workspace.ts) portant un « bus d'interaction »: `hoveredConflictId`, `activeConflictId`, `hoveredOption` (annotateur/LLM/gold), `lockedBy` (verrou d'arbitrage temps réel). Tous les panneaux (ConflictNav navbar, DocumentPanel central type-contrat, InspectorPanel de vote) s'abonnent à CE bus → survol d'un vote dans l'inspecteur surligne la phrase + la carte de file + la ligne de concordance, simultanément, partout (hover synchronisé bidirectionnel). Hovers riches via le `useAnchoredPosition` existant (flip+clamp viewport déjà fait) pour des cartes denses (qui a voté quoi, support, rationale, écart au LLM). Focus management centralisé: une seule machine d'état décide quel élément a le focus DOM après chaque décision et le re-parque sous le curseur. Mémoire de config d'interface PAR DOCUMENT via une NOUVELLE couche de prefs (le schéma actuel n'a que shell-local + compte-serveur, pas de couche par-doc).

**Forces** : Hover/sélection synchronisés PARTOUT de façon bidirectionnelle = exactement la contrainte « panneaux interconnectés » poussée au maximum (niveau agence top) ; useAnchoredPosition (flip+clamp+ResizeObserver) déjà prêt pour des hovers riches qui s'agrandissent (rationale dépliable) sans saut ni débordement ; Un store dédié isole le GOLD du workspace d'annotation (pas de pollution croisée des invariants multi-label) et rend la machine de focus testable isolément, comme placeWithinViewport/divergence ; Pose proprement la couche de prefs PAR DOCUMENT qui MANQUE aujourd'hui (mergeUiPrefs ne gère que compte) — répond à « mémoire de config par document »

**Faiblesses** : Plus de code neuf qu'A: un store + un bus d'interaction + une machine de focus = surface de test plus large (risque de désynchronisation hover si mal câblé) ; Risque de divergence d'architecture avec workspace.ts (deux stores qui se ressemblent) → dette si non factorisé ; La couche prefs par-document ajoute un aller-retour serveur (User.ui_preferences est par-compte; il faut une clé composite compte×doc ou un nouveau champ) — décision de modèle à acter avant code

**Pertinence** : Élevée: c'est l'option qui atteint le mieux le niveau « ergonomie de tonnerre / interconnexion totale » exigé, et qui comble proprement le trou « mémoire par document ». Plus ambitieuse, à réserver à la V2 ou à une équipe qui veut le haut du panier d'emblée.

## Option C — Mode « revue séquentielle plein-conflit » (un conflit à la fois, focus tunnel)
Plutôt qu'un document complet annotable, présenter une vue TUNNEL: un seul conflit occupe le centre (la/les phrases en désaccord mises en avant comme dans un contrat, catégorie en titre), les options de vote empilées verticalement sous le curseur, et le reste du document réduit à un fil contextuel (mini-map/ToC). Avancer = la carte suivante glisse exactement sous le curseur (transform translateY animé, sobre). Raccourcis: Espace/Entrée = accepter le vote majoritaire pondéré, 1..9 = choisir une option, n/p = conflit ±, u = annuler. Auto-résolution intégrée au flux: les accords absolus sont pré-cochés et « passés » en rafale (1 clic = valider tout le lot C1), seuls les cas risqués demandent un arrêt. S'appuie sur divergence.ts pour l'ordre, sur le scoring backend (votes annotateurs > LLM) pour le pré-choix, et sur la file de triage comme modèle mental.

**Forces** : Minimise au maximum le déplacement de souris: il n'y a presque qu'UN point d'action à l'écran, toujours au même endroit → clics successifs parfaits, vitesse maximale en fin de campagne (centaines de conflits) ; Les niveaux d'auto-résolution (accord absolu 1 clic, peu risqué auto, risqué manuel) deviennent natifs au flux plutôt qu'un réglage à côté ; Charge cognitive faible: catégorie en titre, factorisation des accords, mise en page proche d'un contrat — répond directement aux contraintes de lisibilité

**Faiblesses** : Rompt avec la familiarité de l'atelier /annotate (ResizablePanels 3 colonnes): l'arbitre perd la vue d'ensemble du document, gênant pour les conflits dont la résolution dépend du contexte voisin ; Interconnexion « partout » plus pauvre par construction (le tunnel cache les autres panneaux) — tension avec la contrainte panneaux interconnectés ; Réutilise MOINS la structure visuelle existante (DocumentPanel/Inspector) → plus de composants neufs, et un 2e paradigme d'UI à maintenir à côté de l'atelier ; Navigation entre BLOCS de clauses similaires moins naturelle quand on ne voit qu'un conflit à la fois

**Pertinence** : Moyenne à ciblée: excellent pour le débit pur en toute fin de campagne (purge de masse des conflits faciles), mais en tension avec l'exigence d'interconnexion et de vue contrat globale. Bon candidat comme MODE secondaire (toggle « focus ») plutôt que comme interface principale.

## ✅ Recommandation : Option A comme socle V1, en adoptant d'emblée le bus d'interaction et la couche prefs-par-document de l'Option B, et en gardant l'Option C comme mode « focus » optionnel (toggle).

> L'exigence la plus risquée — « valider en série sans bouger la souris, l'élément suivant vient sous le curseur » — est DÉJÀ résolue et en prod via QuickActionRail (`onValidateAdvance(index, clientY)` + scroll DocumentPanel) et la navigation par segments est DÉJÀ pure et testée (divergence.ts: segments/anchors/next/prev/ordinal). Reconstruire (Option C) ou tout réarchitecturer (Option B seule) gaspillerait ce capital et réintroduirait du risque sur la mécanique la plus délicate. On part donc d'A (réutilisation maximale du sticky-cursor, des shortcuts, du focus store et de DivergenceNav recâblés sur des vecteurs inter-annotateurs), mais on emprunte tout de suite à B les deux briques qui MANQUENT réellement au socle: (1) un bus d'interaction hover/selection partagé pour l'interconnexion bidirectionnelle « partout », et (2) une couche de prefs PAR DOCUMENT (le schéma actuel n'a que shell-local + compte-serveur via mergeUiPrefs, rien par-doc). C'est l'arbitrage du niveau agence top: réutiliser l'éprouvé, n'inventer que le strictement absent, et offrir le mode tunnel d'C en option pour le débit de masse sans en faire le paradigme principal.

### Détails clés d'implémentation
- Recâbler `lib/divergence.ts` (divergenceSegments/divergenceAnchors/nextDivergence/prevDivergence/divergenceOrdinal — déjà PURS et testés) sur des vecteurs INTER-ANNOTATEURS au lieu de claudeByIndex/codexByIndex; garder le regroupement en segments contigus pour sauter de BLOC de conflit en bloc, pas phrase par phrase
- Réutiliser le sticky-cursor de `QuickActionRail.onValidateAdvance(index, clientY)` + le scroll de DocumentPanel qui re-parque le bouton suivant sous le curseur; élargir l'unité de parcage de la PHRASE au BLOC (deriveBlocks de lib/blocks.ts) pour les suites de même catégorie
- Étendre `useDivergenceShortcuts`: garder n/p (conflit ±), e (peek evidence), g (compare); remplacer le binaire 1/2 par 1..9 = adopter la k-ième option de vote (annotateur A/B/…, puis LLM claude/codex/mistral), Espace/Entrée = vote majoritaire pondéré, u = annuler; conserver le garde isEditable + metaKey/ctrlKey
- Hovers riches via `useAnchoredPosition`/`placeWithinViewport` (flip+clamp viewport+ResizeObserver déjà prêts) pour des cartes denses: qui a voté quoi, support, rationale, écart au LLM, signal « décision humaine ≠ LLM »
- Nouveau `goldStore` (Zustand, miroir léger de store/workspace.ts) portant le bus d'interaction: hoveredConflictId, activeConflictId, hoveredOption, lockedBy (verrou d'arbitrage exclusif auto-expirant via le WebSocket de présence existant lib/collab/collabClient.ts)
- Interconnexion: réutiliser selectClause/focusSentence du store (déjà écoutés par TocPanel/DocumentPanel/InspectorPanel) comme canal de sélection; ajouter le hover bidirectionnel via le bus → survol d'un vote dans l'inspecteur surligne phrase + carte de file + ligne de concordance simultanément
- Mémoire de config PAR DOCUMENT: ajouter une couche au-dessus de mergeUiPrefs (lib/prefs/schema.ts) clé compte×doc (overrides de la couche compte), persistée comme User.ui_preferences (camelCase via drf-camel-case) sous un sous-objet perDoc[docId]
- Composants à dériver (pas dupliquer): ConflictNav (depuis DivergenceNav, ◂ k/N ▸ + data-testid conflict-nav/conflict-counter/conflict-prev/conflict-next), VoteCard (depuis SuggestionCard), ConflictQueue (depuis triage/TriageQueue)
- Scoring injecté en amont: nouveau service backend dans claire/projects/ aux côtés de iaa.py (cohen_kappa, project_iaa, project_iaa_detail) et concordance.py (project_concordance) — pondération votes annotateurs > votes LLM, et flag « humain ≠ LLM = signal fort »; les KPI annotateur↔gold réutilisent project_concordance
- Tokens/zéro hex (charte docs/pactiva): remplacer les bg-amber-400/text-emerald-400 en dur des composants source par des tokens de sévérité de conflit; conserver l'a11y (role=navigation/dialog, aria-label, focus visible) déjà présente
- Mode « focus » optionnel (Option C) derrière un toggle persistant dans la couche prefs-par-document: vue tunnel un-conflit-à-la-fois pour la purge de masse des accords absolus (1 clic = valider le lot C1)
