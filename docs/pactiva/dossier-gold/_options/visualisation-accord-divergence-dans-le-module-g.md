# Visualisation accord/divergence dans le module GOLD de résolution inter-annotateurs (par document, primaire + secondaires, multi-label)

## Document juridique annoté + rail de consensus (vue "contrat")
Reprend la mise en page DocumentPanel/blocks.ts : le texte se lit comme un contrat, regroupé en BLOCS d'accord continus via deriveBlocks. Statut de consensus calculé par phrase avec agreementSegments généralisé aux humains (strict = tous identiques / majoritaire = un thème domine / divergence totale). Un rail gauche continu (type ModelBoundaryRail) code le statut par segment ; le fond du bloc reprend getThemeToken du thème consensuel, l'intensité/saturation portant le degré d'accord. Badge primaire plein + chips secondaires en contour sur chaque bloc, avec compteur de votes (3/4) au survol RationaleHover.

**Forces** : S'aligne pile sur la contrainte UX "mise en page proche d'un contrat" et "regrouper les blocs d'accord continus" ; Réutilise massivement le socle : deriveBlocks, agreementSegments, ModelBoundaryRail, getThemeToken, RationaleHover, blockAt — quasi zéro nouvelle primitive ; Lecture naturelle de gauche à droite : on voit le thème consensuel en avant (exigence "catégorie en avant") et on plonge dans une zone seulement si elle est rouge ; Le rail continu offre une mini-carte de densité de conflit sans quitter le document

**Faiblesses** : Le statut tri-état (strict/majoritaire/total) doit encoder DEUX dimensions (primaire ET secondaires) sur un même bloc : risque de surcharge visuelle si mal hiérarchisé ; Les blocs masquent la granularité phrase : un désaccord secondaire isolé dans un long bloc d'accord primaire peut être noyé ; Forward-fill humain interdit (modèle exact per-sentence) : deriveBlocks sur vecteurs exacts produira beaucoup de petits blocs si l'annotation est éparse

**Pertinence** : Très haute : c'est l'option la plus fidèle au cahier des charges UX et la moins coûteuse en dette. Le risque multi-label se gère en séparant clairement la couche primaire (fond) de la couche secondaire (chips), pas en empilant des couleurs.

## Matrice annotateurs × phrases (heatmap de consensus)
Une grille dense : lignes = annotateurs (+ lignes LLM grisées en bas, distinctes car votes LLM < votes humains), colonnes = phrases ou blocs. Chaque cellule = pastille du thème (getThemeToken + readableTextColor). Colonnes surlignées selon agreementSegments : vert strict, ambre majoritaire, rouge divergence. Une bande "consensus" en tête de colonne résume. Multi-label géré par split-cell : moitié haute = primaire, moitié basse = secondaires empilés. Clic colonne = saute à l'arbitrage de cette phrase ; navigation horizontale entre désaccords via nextDivergence/prevDivergence.

**Forces** : Vue d'ensemble la plus dense : on repère instantanément QUI diverge et SUR QUOI (utile pour les stats annotateur↔annotateur) ; Excellent pour le rôle arbitre/lead : voir d'un coup les patterns (un annotateur systématiquement à part) ; Réutilise getThemeToken, readableTextColor, agreementSegments, nextDivergence ; cohérent avec iaa.py par-paire

**Faiblesses** : S'éloigne franchement de la contrainte "mise en page proche d'un contrat" — c'est une vue analytique, pas une vue de lecture ; Scalabilité : un document de 200 phrases × 6 annotateurs = grille immense, navigation au scroll, perte du curseur (contre l'exigence "clics sans bouger la souris") ; Le split-cell primaire/secondaire devient illisible en dessous d'une certaine taille de cellule ; Ne factorise pas les blocs d'accord continus (chaque phrase = colonne)

**Pertinence** : Moyenne comme vue PRINCIPALE de résolution, haute comme vue SECONDAIRE/stats. Trop analytique pour être l'écran d'arbitrage principal, mais précieuse en complément (onglet "vue matrice").

## File de conflits priorisée + carte de désaccord (cartes empilées)
Inspiré de la file de triage C1–C5 : une liste verticale de cartes, une par ZONE de désaccord (conflictZones / divergenceSegments étendus aux humains), triée par sévérité (divergence totale > majoritaire serrée > secondaires seulement). Chaque carte montre l'extrait de phrase, les votes côte à côte (chips de thème par annotateur, LLM dégradés), un en-tête de statut, et primaire/secondaires sur deux lignes. Les accords stricts sont repliés en une barre "N blocs en accord" dépliable. Le focus suit le curseur : valider une carte fait remonter la suivante sous la souris.

**Forces** : Colle parfaitement à "clics successifs sans bouger la souris" et "navigation rapide entre désaccords" : la file fait défiler le travail vers l'arbitre ; Priorisation native par sévérité = aligne sur le moteur de scoring et les niveaux d'auto-résolution (accord absolu masqué/1 clic, risqué en haut) ; Réutilise les patterns triage (file, cartes, raccourcis useDivergenceShortcuts) et conflictZones/divergenceSegments ; Multi-label clair : deux lignes dédiées primaire vs secondaires, sans compromis de couleur

**Faiblesses** : Perd la vue d'ensemble "document" : on voit les conflits mais pas la structure contractuelle globale ni les longues plages d'accord (contre "mise en page proche d'un contrat") ; Le contexte autour d'une clause (phrases voisines) demande un aller-retour vers le document — risque de désorientation ; divergenceSegments est aujourd'hui pairwise (claude vs codex) : il faut le généraliser N-way humains (faisable, agreementSegments le fait déjà)

**Pertinence** : Haute pour la PRODUCTIVITÉ d'arbitrage, mais insuffisante seule car elle sacrifie la lisibilité "contrat" exigée. Idéale comme moteur de navigation accolé à une vue document.

## ✅ Recommandation : Option 1 (document "contrat" + rail de consensus) comme vue principale, augmentée du moteur de file de l'Option 3 comme overlay de navigation, l'Option 2 reléguée en onglet stats.

> Le cahier des charges insiste deux fois sur une mise en page "proche d'un contrat juridique", le regroupement des blocs d'accord continus, la catégorie en avant et la lisibilité maximale : seule l'Option 1 satisfait cela frontalement, et c'est aussi celle qui réutilise le plus le socle (deriveBlocks, agreementSegments, ModelBoundaryRail, getThemeToken, RationaleHover) sans créer de dette. Mais la contrainte "clics successifs sans bouger la souris" + "navigation rapide entre désaccords" est une force de l'Option 3 ; on la greffe comme rail/file de navigation (nextDivergence/prevDivergence sur des ancres N-way) plutôt que comme écran séparé. L'Option 2 (matrice) répond aux STATS annotateur↔annotateur mais s'oppose à la lisibilité contrat : on la garde en onglet annexe. La clé multi-label : NE PAS empiler les couleurs — le fond du bloc = thème PRIMAIRE consensuel (saturation = degré d'accord), les SECONDAIRES = chips en contour avec leur propre micro-statut d'accord, et l'accord se calcule séparément sur les deux couches (réutilise theme_tags / alpha_masi côté backend). On distingue strict / majoritaire / divergence par une combinaison couleur de rail + intensité de fond + badge, jamais par la seule teinte (a11y, pas de dépendance à la couleur).

### Détails clés d'implémentation
- Nouveau lib pur `goldConsensus.ts` (jumeau de divergence.ts/concordance.ts, testable isolément vitest) : `consensusByIndex(annotatorVecsExact, n)` renvoyant par phrase {primary: {theme, votes, status: 'strict'|'majority'|'split'}, secondaries: [{theme, votes, status}]} ; généralise agreementSegments du pairwise LLM au N-way HUMAIN en réutilisant le modèle EXACT per-sentence (PAS de forward-fill humain, cf. iaa.py `_theme_vector`)
- Composant `GoldDocumentPanel` dérivé de DocumentPanel : blocs via deriveBlocks appliqué au thème consensuel ; fond = `getThemeToken(theme).color` avec opacité pilotée par le statut (strict ~33, majoritaire ~22 + liseré, split = pas de fond + bordure d'alerte) ; texte lisible via readableTextColor — zéro hex en dur (corriger au passage STATUS_COLOR de ComparePanel.tsx qui hardcode #34D399/#FBBF24/#64748B → tokens)
- Rail gauche continu type `ModelBoundaryRail` mais "rail de consensus" : 3 états via token + motif (uni=strict, hachure=majoritaire, plein vif=divergence) pour ne pas dépendre de la couleur seule (a11y AA)
- Couche secondaires : chips en `outline` sous le badge primaire de chaque bloc, chacune avec son compteur de votes au survol (RationaleHover existant) ; statut secondaire calculé indépendamment (un bloc peut être strict en primaire, split en secondaire)
- Navigation : `useDivergenceShortcuts` réutilisé, ancres = `divergenceAnchors` recalculées N-way humains ; n/N affiché via `divergenceOrdinal` ; focus qui suit le curseur (clic = saute + recentre, l'élément suivant arrive sous la souris)
- Distinction votes humains vs LLM : les rangées/chips LLM en teinte désaturée + icône, jamais comptés dans le statut primaire de consensus (alignement futur moteur de scoring : humain > LLM, décision humaine ≠ LLM = signal fort)
- Repli des plages d'accord strict en une barre dépliable "N blocs en accord (tous identiques)" pour densifier et factoriser (exigence factorisation/densité), conflits jamais repliés
- Mémoire d'interface par document : persister densité/replis/onglet via le store prefs PAR COMPTE existant (src/store/prefs.ts, namespacé, sync /me), clé `gold:<documentId>`
- Multi-label backend déjà prêt : s'appuyer sur ClauseTheme role primary/secondary + theme_tags ; le statut secondaire réutilise la logique d'ensembles de `_theme_set_vector`/alpha_masi pour cohérence avec l'IAA
- data-testids : `gold-consensus-rail`, `gold-block-<start>`, `gold-block-status`, `gold-secondary-chip`, `gold-divergence-next/prev/counter`, `gold-agree-fold` (cohérent avec les conventions compare-*/divergence-* existantes pour les tests vitest/playwright)
