# Atelier de RÉSOLUTION (cœur) — interface d'arbitrage des conflits inter-annotateurs (+ LLM) pour produire la base GOLD, aussi aboutie que /annotate, centrée sur la décision phrase-par-phrase.

## Option A — Atelier-jumeau : /resolve/<doc> qui réutilise les 3 panneaux de /annotate, l'arbitre est un « super-annotateur » dont la session EST le GOLD
Nouvelle route /resolve/<documentId> montée sur AnnotationWorkspace existant via un drapeau `mode="resolve"`. On crée une Annotation GOLD spéciale (annotator=arbitre, source nouvelle `gold`) : l'arbitre annote comme d'habitude mais le DocumentPanel, au lieu des seuls fantômes LLM, superpose des FANTÔMES-ANNOTATEURS (un rail par humain, comme les rails LLM de ComparePanel) ; le gutter coloré devient un gutter de CONSENSUS (vert=accord total, ambre=conflit, slate=partiel) calculé sur N annotateurs + M LLM. L'InspectorPanel garde MultiLabelEditor/BoundaryEvidence/certitude, et on étend InspectorJudgeCompare en `SourceCompare` listant Annotateur-A / Annotateur-B / … / Claude / Codex / Mistral, chaque ligne avec son primaire+secondaires+evidence+rationale et un bouton « Adopter » qui pose la décision GOLD sur la phrase. Le SentenceMenu (long-press/clic-droit) gagne un bloc « Annotateurs » jumeau du bloc « LLM ». Le store workspace.ts est étendu (pas dupliqué) avec un slice `resolve` (votes par phrase, décision gold courante).

**Forces** : Réutilisation maximale du socle : ResizablePanels, gutter continu, overlays injustice/langue, raccourcis, redimensionnement persistant par compte — tout marche immédiatement, zéro re-build de l'ergonomie « clic sans bouger la souris » déjà câblée dans SentenceMenu/QuickActionRail. ; La décision GOLD est une vraie Annotation : exports (ExportJob scope JSON), versions immuables (AnnotationVersion), historique, commentaires, verrou — tout l'outillage existant s'applique sans nouveau modèle de persistance. ; Cohérence cognitive totale pour les arbitres déjà formés à /annotate : courbe d'apprentissage quasi nulle, mise en page « contrat juridique » (blocs d'accord regroupés) héritée du DocumentPanel et de runs.ts. ; InspectorJudgeCompare existe déjà pour comparer Vous↔juges : le passage à N annotateurs + M LLM est une généralisation, pas une invention. ; concordance.py / iaa.py se branchent : ann GOLD devient une 4e source dans les vecteurs per-sentence (exact humain) → stats annotateur↔gold immédiates.

**Faiblesses** : Une session d'arbitrage présente N annotateurs + M LLM sur les MÊMES rails que /annotate, vite saturés visuellement au-delà de 3 sources ; le DocumentPanel (68 ko) devra accueillir une densité d'information bien supérieure sans casser sa lisibilité. ; Le modèle « la session de l'arbitre EST le GOLD » mélange la sémantique annotateur/arbitre : il faut garder l'indépendance (l'arbitre VOIT les sessions des pairs, contrairement à la politique annotateur) → un chemin de données distinct, donc du conditionnel `mode` qui alourdit AnnotationWorkspace. ; L'arbitrage est orienté DÉCISION (trancher vite) plus que SAISIE (poser des ancres) ; réutiliser l'atelier tel quel laisse l'arbitre saisir librement au lieu de surtout choisir parmi des propositions — risque d'ergonomie sous-optimale pour le geste dominant « adopter le vote majoritaire ».

**Pertinence** : Très élevée sur la contrainte « aussi aboutie que /annotate » et « ne pas dupliquer » : c'est littéralement le même atelier enrichi. Le risque est la densité N-sources et la confusion saisie/décision, à corriger par des conventions d'affichage (regroupement des accords, sources repliables).

## Option B — Atelier de décision dédié : panneau central « conflit-first » (file de désaccords + carte de vote), réutilise overlays/inspecteur mais pas le DocumentPanel de saisie
Route /resolve/<documentId> avec sa propre composition : à gauche un TocPanel de CONFLITS (réutilise TocPanel + planCoverage mais colore par statut résolution non-résolu/en-cours/résolu et regroupe les blocs d'accord continus en une seule ligne factorisée « phrases 12–18 · INDEMNISATION · 5/5 d'accord »), au centre un nouveau ResolutionPanel qui NE permet pas de saisir des ancres mais affiche, pour la phrase/bloc focalisé, une CARTE DE VOTE : une ligne par source (annotateurs d'abord puis LLM, triées par poids), chaque ligne montrant primaire+secondaires+evidence (hover RationaleHover existant) + boundary, avec la répartition des votes en barre, et le geste central = cliquer la ligne gagnante (l'élément suivant — la prochaine phrase non résolue — vient sous le curseur via useAnchoredPosition, principe « clic sans bouger »). À droite l'InspectorPanel inchangé édite la décision GOLD retenue (multi-label, nature, certitude, commentaire d'arbitrage). Le DivergenceNav/divergence.ts pilote la navigation entre conflits ; ComparePanel reste disponible en drawer pour la vue d'ensemble des rails.

**Forces** : Geste dominant optimisé : l'arbitre passe 90 % de son temps à « trancher » → une carte de vote dédiée rend chaque décision plus rapide qu'un atelier de saisie détourné ; colle parfaitement à « trancher vite » et « accès global instantané aux infos d'une phrase ». ; Lisibilité « contrat juridique » poussée : factoriser les suites d'accord en une ligne (point central de la contrainte UX) est natif au panneau central, pas un compromis sur un DocumentPanel pensé pour la phrase. ; Réutilise les briques pures sans détourner le composant de saisie : divergence.ts, runs.ts, concordance.ts, RationaleHover, InspectorPanel, ComparePanel en drawer, DivergenceNav — donc faible risque de régression sur /annotate. ; Le moteur de scoring (votes annotateurs > LLM, décision humaine ≠ LLM = signal fort) a une place visuelle évidente : la barre de votes pondérés et un badge « divergence du consensus LLM » sur la carte. ; Navigation conflit↔conflit ET bloc-similaire↔bloc-similaire directement servie par une file/ToC orientée résolution (suites de même catégorie regroupées).

**Faiblesses** : Construit un nouveau panneau central (ResolutionPanel) et une nouvelle ToC : c'est le plus gros effort de dev des trois, et il faut soigner pour atteindre le « niveau /annotate » sans hériter directement du DocumentPanel. ; Risque de perdre le CONTEXTE du document : en se concentrant sur la carte de vote d'une phrase, l'arbitre voit moins le texte alentour qu'un atelier plein-texte ; il faut un mini-aperçu du contrat (phrases voisines) pour ne pas arbitrer hors-sol. ; Deux ergonomies à maintenir (saisie /annotate vs décision /resolve) : divergence de conventions possible dans le temps si les deux ne partagent pas assez de composants.

**Pertinence** : La plus alignée sur le BESOIN réel de l'arbitrage (décider, pas saisir) et sur les contraintes UX fines (factorisation, clic-sans-bouger, nav inter-conflits). Le surcoût de dev est réel mais ciblé, et l'essentiel des briques pures est déjà là.

## Option C — Mode overlay « résolution » DANS /annotate : pas de nouvelle route, un toggle de la WorkspaceToolbar active une couche d'arbitrage par-dessus l'atelier existant
Aucune route ni composant majeur nouveau : la WorkspaceToolbar gagne un bouton « Résolution » (visible aux reviewer/lead) qui, sur le document courant, bascule le LlmSourceSwitch en un mode `consensus` ; le DocumentPanel surligne les phrases en conflit (réutilise highlightEvidence/InjusticeLens patterns), et un clic ouvre un SentenceMenu enrichi listant tous les votes (annotateurs + LLM) avec adoption en place. La décision est écrite dans une Annotation GOLD créée à la volée. Le module de gestion (liste docs, %), le verrou d'arbitrage temps réel et les stats vivent dans des pages /gold séparées, mais l'acte d'arbitrage lui-même se fait sans quitter l'atelier connu.

**Forces** : Coût de dev le plus faible et time-to-first-value le plus court : un toggle + l'enrichissement du SentenceMenu (qui a déjà le bloc LLM) suffisent pour un MVP d'arbitrage. ; Zéro nouvelle surface à apprendre : l'arbitre reste dans l'atelier qu'il connaît, contrainte « interconnexion navbar↔zone↔sélection » déjà satisfaite. ; Réutilise intégralement overlays, gutter, raccourcis, prefs par compte — aucune duplication. ; Risque de régression minimal sur la persistance (réutilise Annotation/Clause/exports).

**Faiblesses** : Ne tient PAS la barre « aussi aboutie que /annotate, MAIS centrée sur la décision » : c'est /annotate avec une casquette, pas une vraie surface d'arbitrage ; la densité N-annotateurs + M-LLM dans un SentenceMenu popover devient ingérable. ; Pas de vue « contrat factorisé » ni de file de conflits de premier ordre : la navigation inter-désaccords et le regroupement des blocs d'accord restent secondaires, à l'opposé des contraintes UX exigées. ; Le mélange visuel saisie/décision dans le même DocumentPanel brouille le mode courant (suis-je en train d'annoter ou d'arbitrer ?), source d'erreurs sur le GOLD. ; Le moteur de scoring et la traçabilité d'arbitrage n'ont pas de place naturelle dans l'atelier — relégués hors-flux, donc peu utilisés.

**Pertinence** : Faible au regard de l'ambition (« module GOLD aussi abouti que l'atelier »). Pertinent seulement comme jalon intermédiaire/MVP ou comme repli si le budget est très contraint ; ne répond pas aux contraintes UX de fond ni au besoin de surface d'arbitrage dédiée.

## ✅ Recommandation : Option B — Atelier de décision dédié /resolve/<documentId> (panneau central conflit-first + carte de vote), avec réutilisation agressive des panneaux latéraux et briques pures, et un mini-aperçu plein-texte pour garder le contexte.

> Le besoin GOLD n'est pas « annoter de nouveau » mais « trancher des conflits déjà posés » : le geste dominant est la DÉCISION, pas la SAISIE. L'option A (atelier-jumeau) gagne le « pas de duplication » mais détourne un DocumentPanel de saisie (68 ko, pensé phrase-par-phrase) vers une densité N-annotateurs + M-LLM qu'il ne sait pas afficher proprement, et entretient la confusion saisie/décision. L'option C est un simple MVP qui ne tient aucune des contraintes UX de fond (contrat factorisé, file de conflits, scoring visible). L'option B place la décision au centre : une carte de vote par phrase/bloc où l'on clique la ligne gagnante, l'élément suivant non résolu venant sous le curseur (useAnchoredPosition) — c'est exactement « clics successifs sans bouger la souris » et « accès global instantané aux infos d'une phrase ». Surtout, B est la seule qui rend NATIF le regroupement des suites d'accord en lignes factorisées (mise en page proche d'un contrat) et qui donne une place visuelle évidente au moteur de scoring (barre de votes pondérés annotateurs>LLM + badge « décision humaine ≠ consensus LLM = signal fort »). Le surcoût — un ResolutionPanel central et une ToC de conflits — est ciblé : tout le reste (InspectorPanel, ComparePanel en drawer, DivergenceNav, RationaleHover, ResizablePanels, prefs par compte, divergence.ts/runs.ts/concordance.ts, exports via ExportJob, versions, verrou) se réutilise tel quel. On adopte donc B en empruntant à A son point fort : la décision GOLD EST une Annotation (source=gold) pour hériter gratuitement exports/versions/historique/concordance, et on garde un mini-DocumentPanel en lecture (phrases voisines) pour ne jamais arbitrer hors-sol.

### Détails clés d'implémentation
- Route Next.js App Router : frontend/src/app/(app)/resolve/[documentId]/page.tsx → composant ResolutionWorkspace (data-testid="resolution-workspace") monté sur ResizablePanels existant (left=ConflictTocPanel, center=ResolutionPanel, right=InspectorPanel inchangé).
- Persistance : la décision GOLD est une Annotation avec un nouveau AnnotationSource `gold` (annotations/models.py) + annotator=arbitre ; aucune nouvelle table de décision → exports (ExportJob scope JSON), AnnotationVersion (gold intermédiaire/final), HistoryPanel, CommentsPanel et le verrou Annotation.locked s'appliquent sans code neuf.
- Carte de vote (ResolutionPanel) : une ligne par source, annotateurs d'abord (poids fort) puis LLM (poids faible), chaque ligne = chip thème primaire + chips pointillés secondaires (réutilise le rendu de MultiLabelEditor) + evidence/rationale au survol (RationaleHover) + boundary ; data-testid="resolve-vote-<sourceId>", clic = adopter (pose primaire+secondaires sur la décision GOLD), data-testid="resolve-adopt-<sourceId>".
- Moteur de scoring : fonction PURE nouvelle frontend/src/lib/goldScore.ts (testable comme divergence.ts/concordance.ts) — votes pondérés (config campagne), niveaux d'auto-résolution (accord absolu → bouton 1 clic data-testid="resolve-accept-unanimous" ; cas peu risqués auto ; cas risqués manuels) ; badge data-testid="resolve-llm-divergence" quand la décision humaine diffère du consensus LLM (signal fort).
- Multi-label : s'accorder sur PRIMAIRE + SECONDAIRES — la carte sépare visuellement vote-primaire et votes-secondaires ; réutilise sanitizeThemeSet/withPrimaryTheme du store et validate_clause_theme_set côté backend (exactement un primaire, refuge jamais secondaire).
- Vue contrat factorisée : ConflictTocPanel étend TocPanel+planCoverage en regroupant les suites de phrases en accord total en une seule ligne (« phrases 12–18 · INDEMNISATION · 5/5 ») et colore par statut résolution (non-résolu/en-cours/résolu/%) ; les conflits sont des lignes ambre cliquables.
- Navigation : DivergenceNav + divergence.ts/runs.ts pour sauter conflit↔conflit ET bloc-similaire↔bloc-similaire (suites de même catégorie) ; raccourcis via useDivergenceShortcuts ; l'élément suivant non résolu se positionne sous le curseur via useAnchoredPosition (« clic sans bouger »).
- Vecteurs : étendre concordance.py et iaa.py pour ajouter le GOLD comme 4e source per-sentence EXACT (réutilise _theme_vector) → stats annotateur↔annotateur, ↔LLM, ↔GOLD (qui est le plus proche du gold) sans nouveau calcul de fond ; frontend concordance.ts/llmAgreement.ts déjà alignés.
- Contexte plein-texte : mini-aperçu en lecture seule (phrases voisines de la phrase focalisée) dérivé du DocumentPanel en lecture, pour ne jamais arbitrer hors-sol, sans rouvrir l'éditeur de saisie.
- État UI : nouveau slice `resolve` dans store/workspace.ts (votes par phrase, décision courante, curseur de conflit) + mémoire de config d'interface PAR DOCUMENT via store/prefs.ts (namespacé compte, déjà synchronisé /me) ; ComparePanel réutilisé en drawer pour la vue rails N-way.
- Temps réel : verrou d'arbitrage exclusif auto-expirant via le WebSocket de collaboration existant (présence) — réutiliser le canal de lib/collab, un lease par (document, arbitre) avec TTL ; bandeau « X arbitre ce document » jumeau du session-banner d'AnnotationWorkspace.
- Tokens/a11y : zéro hex en dur (les couleurs de statut agree/diverge/partial actuellement codées en dur dans ComparePanel.tsx STATUS_COLOR sont à migrer vers les tokens) ; radiogroup/aria-checked sur la carte de vote comme dans InspectorJudgeCompare ; tests vitest+MSW pour goldScore.ts et la carte, pytest pour la source gold et les vecteurs de concordance.
