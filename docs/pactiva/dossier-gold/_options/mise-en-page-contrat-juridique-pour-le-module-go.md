# Mise en page « contrat juridique » pour le module GOLD de résolution de conflits inter-annotateurs : factoriser les blocs d'accord continus (lecture fluide, catégorie en avant) et basculer en mode décision dense sur les conflits, sur le socle Pactiva (Clause per-sentence, deriveBlocks/coalesceRuns, concordanceReport/divergenceSegments, tokens font-reading/leading-reading/max-w-reading, ResizablePanels).

## Articles factorisés + cartouches de conflit en flux (un seul corps de contrat)
Un seul document type contrat, rendu en font-reading/max-w-reading. deriveBlocks() factorise les phrases consécutives d'accord absolu en un ARTICLE replié : en-tête de catégorie en chip coloré (token getThemeToken) + numérotation juridique (Art. 4.2), corps gris discret, hauteur compacte. Là où concordanceReport/divergenceSegments signalent un conflit, le flux s'ouvre sur un CARTOUCHE de décision dense inline (fond elevated, bordure accent) listant les votes annotateurs vs LLM et la cible GOLD. Lecture = on déroule le contrat de haut en bas ; les zones calmes se lisent en 1 ligne, les zones chaudes deviennent des panneaux de décision sans quitter le fil.

**Forces** : Réutilise tel quel deriveBlocks/coalesceRuns (factorisation déjà pure et neutre IAA) et divergenceSegments/conflictZones pour décider accord vs conflit — zéro nouveau moteur ; Métaphore contrat la plus fidèle : numérotation d'articles, catégorie en titre, blocs d'accord = paragraphes calmes ; densité concentrée exactement où il y a litige ; Un seul fil scrollable = clics successifs sans bouger la souris (le cartouche de décision s'ouvre sous le curseur, le suivant remonte sous le curseur après résolution), conforme à la contrainte UX ; Mémoire de pliage par document branchable sur le store prefs par compte (comme overlays/panneaux) ; Densité variable : 1 ligne par article d'accord libère un maximum de verticalité pour les conflits

**Faiblesses** : Hauteur de ligne hétérogène (1 ligne vs gros cartouche) → le scroll saute ; nécessite scroll-margin et anim sobre pour ne pas désorienter ; Sur un contrat très conflictuel, l'écran redevient dense partout (l'avantage de factorisation s'estompe) ; Le repli/dépli d'article ajoute un état UI à gérer (sync sélection navbar↔fil↔inspecteur)

**Pertinence** : Très haute : c'est l'expression la plus littérale de « regrouper les blocs d'accord, catégorie en avant, mode décision dense sur conflit » et elle s'appuie directement sur les briques pures existantes.

## Sommaire d'articles (gauche) + lecteur contrat / panneau de décision (droite), deux modes
On garde ResizablePanels : à gauche un SOMMAIRE d'articles factorisés par deriveBlocks (catégorie + numéro + pastille d'état non résolu/en cours/résolu, façon DocStatusBadge), au centre le contrat en lecture continue (font-reading), à droite l'inspecteur. Cliquer un article basculé en conflit fait passer le CENTRE en mode décision plein cadre (vue dense dédiée à un seul désaccord : matrice votes×phrases, secondaires, cible GOLD), tandis que les articles d'accord restent en lecture. Deux modes nets : LECTURE (parcourir le contrat) vs DÉCISION (trancher un article), pas d'inline.

**Forces** : Sépare proprement les deux régimes (lecture fluide vs décision dense) → chaque mode peut être optimisé à fond sans compromis de hauteur de ligne ; Réutilise l'ossature ResizablePanels + le pattern TocPanel (sommaire navigable, scrollIntoView du chip sélectionné) et DocStatusBadge/verrous existants ; Le mode décision plein cadre offre la place pour une matrice riche (annotateurs × LLM × secondaires) sans serrer ; Sommaire = navigation rapide entre désaccords ET entre blocs de même catégorie (filtrage par thème trivial)

**Faiblesses** : Casse partiellement la métaphore « un seul document » : trancher un conflit sort du fil de lecture (changement de contexte centre) ; Plus de clics/allers-retours sommaire↔centre ; risque de perdre le contexte des phrases adjacentes pendant la décision ; Deux layouts de centre à construire et tester (lecture + décision) = surface de code/tests plus large

**Pertinence** : Haute : excellent pour la productivité d'arbitrage et la gestion (sommaire d'état), mais s'éloigne de l'immersion « document juridique unique » et multiplie les changements de contexte.

## Contrat à reliure : marge gauche d'autorité (rail catégorie continu) + glose de conflit dans la marge droite
Mise en page de contrat relié : colonne centrale font-reading/max-w-reading avec un RAIL de catégorie continu en marge gauche (réutilise le rail coloré de runs/coalesceRuns du DocumentPanel) qui regroupe visuellement les blocs d'accord par un trait + label de catégorie pivoté, sans replier le texte (tout le contrat reste lisible). Les conflits ne s'insèrent pas dans le flux : ils s'affichent en GLOSE dans la marge droite (apparat critique), avec une loupe au survol (pattern RationaleHover/InjusticeLens) ; cliquer la glose ouvre la décision dans l'inspecteur droit. Le corps reste un contrat intégral et lisible de bout en bout.

**Forces** : Lisibilité maximale du contrat en continu (aucun pliage, aucun cartouche n'interrompt le texte) — le plus proche d'un vrai document relié annoté ; Réutilise le rail de runs + coalesceRuns (déjà rendu dans DocumentPanel) et le pattern hover riche (RationaleHover/InjusticeLens/useAnchoredPosition) pour la glose ; Catégorie « en avant » via rail continu + label, factorisation visuelle sans perte de texte ; a11y : ordre de lecture du corps préservé ; Marge de glose = espace naturel pour densité de conflit sans empiéter sur la lecture

**Faiblesses** : La décision elle-même est repoussée dans l'inspecteur/marge → mode décision moins « dense plein cadre » que demandé ; arbitrage lourd à l'étroit ; Marge droite chargée sur documents très conflictuels (gloses qui s'empilent, chevauchements à résoudre) ; Exige une largeur d'écran confortable (3 zones + 2 marges) ; dégradation mobile/étroit non triviale ; Moins de factorisation de hauteur : un long contrat reste long à scroller même là où tout est d'accord

**Pertinence** : Moyenne-haute : superbe pour la lecture et la fidélité documentaire, mais sous-sert l'exigence « mode décision dense » qui est le cœur fonctionnel du module GOLD.

## ✅ Recommandation : Articles factorisés + cartouches de conflit en flux (Option 1), avec le sommaire d'état de l'Option 2 monté dans le panneau gauche de ResizablePanels

> Le cœur du module GOLD est de trancher des conflits vite et bien tout en restant dans la lecture d'un contrat. L'Option 1 est la seule qui exprime littéralement la consigne « regrouper les blocs d'accord continus, catégorie en avant, mode décision dense sur conflit » dans un fil unique, et elle se branche directement sur les briques PURES déjà livrées (deriveBlocks/coalesceRuns pour factoriser, divergenceSegments/conflictZones/concordanceReport pour décider accord vs conflit) — donc peu de moteur neuf, surtout de la mise en page. Le fil unique satisfait la contrainte forte « clics successifs sans bouger la souris » : on résout un cartouche, le suivant remonte sous le curseur. On récupère le meilleur de l'Option 2 sans son coût (changement de contexte centre) en plaçant le SOMMAIRE d'articles avec pastilles d'état (non résolu/en cours/résolu/%) dans le panneau gauche existant — navigation rapide entre désaccords et entre blocs de même catégorie, sans sortir du contrat. L'Option 3 sacrifie la densité de décision (cœur fonctionnel) et l'Option 2 sacrifie l'immersion documentaire ; l'hybride 1+sommaire garde les deux.

### Détails clés d'implémentation
- Réutiliser deriveBlocks(computeRuns(drafts,n,{perSentence:true})) pour les ARTICLES d'accord et coalesceRuns pour le rail catégorie ; ne créer aucun objet persistant (article = vue dérivée, neutre IAA, comme aujourd'hui)
- Statut d'un article via un sélecteur pur articleState(votes) ∈ {accordAbsolu, peuRisque, conflit} dérivé de concordanceReport/divergenceSegments — accordAbsolu => article replié 1 ligne ; conflit => cartouche déplié
- Composant <ContractArticle> (en-tête: ClauseChip catégorie token getThemeToken + numéro juridique Art. N.M ; corps font-reading leading-reading max-w-reading bg-reading text-ink) et <ConflictCartouche> (fond bg-elevated, border-accent, matrice votes annotateurs vs fantômes LLM, primaire + secondaires)
- Cartouche = mode décision dense : lignes par votant (annotateur > LLM via pondération du moteur de scoring), pastille « décision humaine ≠ LLM = signal fort », boutons cible GOLD primaire/secondaires, champ commentaire d'arbitrage optionnel, verrou exclusif temps réel (réutiliser WebSocket présence + Annotation.locked, badge auto-expirant)
- Navigation : data-testid='gold-article-{n}' et 'gold-conflict-{seg}', raccourcis n/N entre conflits (réutiliser useDivergenceShortcuts/DivergenceNav) avec scroll-margin-top pour que le cartouche suivant arrive sous le curseur ; après résolution, focusSentence(nextConflict.start)
- Panneau gauche (ResizablePanels) = sommaire d'articles façon TocPanel : pastille d'état type DocStatusBadge (non résolu/en cours/résolu) + barre de % global, filtre par catégorie de thème, clic => scrollIntoView({block:'nearest'}) de l'article ; sélection synchronisée navbar↔fil↔inspecteur via le store workspace
- Mémoire de pliage et densité PAR DOCUMENT dans le store prefs namespacé par compte (même mécanisme que overlays/panneaux/auto-prefill, sync /me) : quels articles repliés, seuil d'auto-résolution affiché
- Zéro hex en composant : catégories via getThemeToken, états via tokens accent/emerald/amber/ink-muted déjà utilisés (validation-track, badges) ; a11y: chaque cartouche est un <section role=group aria-label='Conflit Art N.M'>, ordre de lecture = ordre document, focus géré au clavier
- Multi-label: le cartouche s'accorde sur PRIMAIRE et SECONDAIRES séparément (deux sous-blocs de vote, role primary/secondary du ClauseTheme), GOLD écrit les deux
