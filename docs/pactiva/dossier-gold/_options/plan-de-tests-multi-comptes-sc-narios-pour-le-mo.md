# Plan de tests (multi-comptes & scénarios) pour le module GOLD de résolution inter-annotateurs

## Pyramide stratifiée par couche (unitaire dense → intégration API → e2e fin)
Réutilise telle quelle la stratification existante : moteur de scoring/auto-résolution testé en pur (comme iaa.py/concordance.py via test_iaa.py/test_concordance.py), endpoints GOLD testés via APIClient + factories conftest (un nouveau fixture gold_campaign seedant 3 annotateurs claude/codex/mistral + PreAnnotation LLM), logique front pure (résolution, vote, multi-label) en vitest sur src/lib (comme concordance.test.ts/divergence.test.ts), composants en jsdom+MSW, et seulement quelques parcours e2e Playwright critiques (arbitrage bout-en-bout, verrou exclusif, export gold). Pas de nouveau harnais : on étend conftest.py, src/mocks/handlers.ts et e2e/.

**Forces** : Cartographie 1:1 sur l'organisation actuelle (40 fichiers pytest, 41 vitest, 26 e2e) — adoption immédiate par l'équipe ; Le moteur de scoring (votes annotateurs>LLM, divergence humain/LLM=signal fort) se teste en FONCTION PURE comme cohen_kappa : ultra-rapide, déterministe, exhaustif sur les barèmes/pondérations ; Coûts e2e maîtrisés : Playwright lent et MSW-only aujourd'hui, on n'y met que l'irréductible (verrou temps réel, parcours d'arbitrage, gating export) ; Couverture multi-label (primaire+secondaires) testable au niveau lib pur + API sans dépendre d'un navigateur

**Faiblesses** : Le scoring pur ne prouve pas le branchement réel modèle↔API↔store : risque de drift entre la fonction pure et son câblage ; Demande de la discipline pour ne pas dupliquer un même invariant aux 3 niveaux ; Les scénarios multi-comptes concurrents (2 arbitres sur le même désaccord) sont mal couverts par des tests unitaires

**Pertinence** : Très élevée : épouse exactement le socle (iaa/concordance déjà testés en pur, factories conftest, MSW mutable). C'est le prolongement naturel et le moins risqué.

## Scénarios end-to-end "campagne complète" pilotés par fixtures multi-comptes (golden-path narratif)
Centre la stratégie sur des scénarios-récits joués de bout en bout : bootstrap campagne → 3 annotateurs (claude/codex/mistral) soumettent des annotations divergentes seedées → ouverture du module GOLD → auto-résolution des accords absolus → arbitrage manuel des cas risqués → export gold intermédiaire puis final → stats de concordance ↔gold. Implémenté surtout en pytest d'intégration API (style test_campaign_simulation.py, qui réconcilie un modèle de référence à chaque pas) avec un méga-fixture paramétré par seed, doublé d'e2e Playwright sur le parcours visible. La vérité se construit en jouant le produit, pas en isolant des unités.

**Forces** : Reproduit la PHILOSOPHIE déjà gagnante de test_campaign_simulation.py (réconciliation continue d'un modèle de référence, multi-seeds → milliers d'ops vérifiées) — parfait pour le besoin "du bootstrap à l'export" ; Couvre nativement le multi-comptes et l'interconnexion des panneaux (navbar↔zone↔sélection) puisqu'on rejoue un vrai parcours ; Détecte les drifts de câblage que les tests purs ratent (statuts non résolus/en cours/résolus/%, gating export, traçabilité/historique) ; Excellent filet anti-régression pour les invariants transverses (étanchéité des rôles, verrou)

**Faiblesses** : Lent et plus fragile : un échec de scénario localise mal la cause (vs un test pur) ; Le moteur de scoring (barèmes, pondérations exactes, départage votes humains vs LLM) est sous-spécifié si tout passe par le scénario — on rate les cas-limites numériques ; Le temps réel (verrou exclusif auto-expirant) reste difficile à scénariser de façon déterministe sans contrôle d'horloge ; Coût de maintenance des fixtures narratives élevé quand la config de campagne évolue

**Pertinence** : Élevée pour le "du bootstrap à l'export" et le multi-comptes, mais insuffisante seule pour le moteur de scoring et le temps réel — à combiner.

## Risque-d'abord : property-based + concurrence/temps-réel + étanchéité comme priorité, golden-path en complément
Priorise les zones à plus fort risque du GOLD. (1) Moteur de scoring & auto-résolution : property-based hypothesis (comme test_kappa_bounded_and_symmetric) — monotonie (ajouter un vote concordant ne baisse pas le gold), bornes, invariance par permutation des annotateurs, dominance votes humains>LLM, "décision humaine ≠ LLM = signal fort" comme propriété. (2) Temps réel : tests Channels WebsocketCommunicator (comme test_presence_ws.py) pour le verrou d'arbitrage EXCLUSIF, + contrôle d'horloge (introduire freezegun/cache-TTL, aujourd'hui ABSENT) pour l'auto-expiration et la course "2 arbitres simultanés". (3) Étanchéité rôles/verrous : matrice de permissions exhaustive (style test_permissions.py/test_annotation_lock.py 423). Le golden-path e2e n'arrive qu'en finition.

**Forces** : Attaque frontalement les 3 vrais pièges du GOLD : exactitude numérique du scoring, concurrence d'arbitrage, étanchéité — là où un bug fait perdre/corrompre le gold de référence ; Property-based prouve des INVARIANTS du barème (pas juste des exemples), idéal pour des pondérations configurables par campagne ; Comble une lacune réelle du socle : pas de freezegun/mock d'horloge aujourd'hui → indispensable pour un verrou auto-expirant testable de façon déterministe ; Réutilise les patrons existants éprouvés (hypothesis, WebsocketCommunicator, matrices 423)

**Faiblesses** : Property-based exige une spec formelle des propriétés du scoring avant d'écrire les tests — investissement de conception en amont ; Introduit une dépendance/outillage horloge (freezegun) et plus de tests async Channels (transaction=True, plus lents/flaky) ; Couverture "parcours utilisateur visible" et UX (hovers, clics sans bouger la souris, panneaux interconnectés) reléguée au second plan si mal cadencé ; Plus exigeant pour des devs peu familiers du property-based

**Pertinence** : Très élevée sur les zones critiques (scoring, temps réel, étanchéité) qui sont précisément les exigences neuves du GOLD ; à condition d'y adosser un socle de golden-path pour la couverture parcours/UX.

## ✅ Recommandation : Hybride à dominante "risque-d'abord" (Option 3) charpenté par une pyramide stratifiée (Option 1), avec une poignée de golden-paths narratifs (Option 2) en filet e2e.

> Le socle Pactiva a déjà prouvé que trois leviers marchent et doivent être réutilisés tels quels : (a) la fonction pure testée exhaustivement (iaa.py/concordance.py) — donc le moteur de scoring GOLD doit naître comme module pur testable au niveau unité ET en property-based ; (b) la simulation randomisée à réconciliation continue (test_campaign_simulation.py, 12 seeds × ~140 pas) — le patron idéal pour prouver l'absence de perte/corruption du gold du bootstrap à l'export ; (c) la matrice de refus 423 + WebsocketCommunicator (test_annotation_lock.py, test_presence_ws.py) — le patron pour l'étanchéité des rôles et le verrou temps réel. Les exigences NEUVES du GOLD (exactitude du barème votes-humains>LLM, verrou d'arbitrage exclusif auto-expirant, auto-résolution par niveaux de risque) sont exactement les zones que des tests d'exemple ratent et que le property-based + le contrôle d'horloge couvrent. On démarre donc par le risque (scoring pur + concurrence + étanchéité), on structure en pyramide pour la rapidité, et on scelle par 3-4 golden-paths Playwright pour la couverture parcours/UX. Lacune à combler explicitement : aucun mock d'horloge n'existe aujourd'hui (seul un cache-TTL ROSTER_TTL=120 dans consumers.py) — c'est le prérequis bloquant du verrou auto-expirant.

- Backend — property-based (hypothesis, déjà en place) : tests/test_gold_scoring_property.py — monotonie (un vote concordant supplémentaire ne diminue jamais le score gold), bornes [0,1], invariance par permutation des annotateurs, idempotence du recompute, sur des pondérations de campagne tirées aléatoirement.
- Backend — fixtures multi-comptes : étendre conftest.py avec PreAnnotationFactory/PreClauseFactory (absents aujourd'hui) + un fixture gold_campaign seedant 3 annotateurs réels (claude/codex/mistral) avec annotations DIVERGENTES contrôlées + PreAnnotation par juge, primaire+secondaires, sur document_with_sentences.
