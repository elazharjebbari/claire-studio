# Export du gold

## Gold = annotation système exportée par le pipeline existant tel quel
La base GOLD est matérialisée comme une Annotation système (annotator=compte technique `__gold__`, source nouvelle valeur `arbitration_gold`, status `approved`) par document. L'arbitrage écrit des Clause + ClauseTheme normaux dessus. L'export gold = `createExport` avec `scope.annotators=['__gold__']` (ou `scope.goldOnly=true`) sur les formats jsonl/csv/conll/xml/md/iaa_matrix DÉJÀ implémentés dans services.py. Zéro nouveau format, zéro nouveau modèle d'export. La provenance fine vit à côté mais l'export ne sort que le verdict.

**Forces** : Reutilise integralement run_export, _selected_annotations (scope.annotators existe deja lignes 44-52), build_snapshot, manifest, self-heal, retry, download confine, polling, page admin/exports : effort backend quasi nul ; build_snapshot sort DEJA les secondaires (`themes` role/support l.144-147), boundary, triage_level, certainty, validated, source : multi-label gold gratuit dans tous les formats ; Le gold devient comparable aux annotateurs via iaa_matrix/concordance.py sans code dedie (qui est le plus proche du gold) ; Un seul modele mental : 'le gold est une annotation' ; intermediaire vs final = juste scope.statuses

**Faiblesses** : build_snapshot expose annotator='__gold__' mais PAS qui a reellement arbitre chaque clause ni le commentaire : provenance fine perdue a l'export ; Aucune trace dans l'artefact du desaccord resolu (votes annotateurs, signal LLM, niveau d'auto-resolution) : export gold 'plat' ; Mele le gold aux sessions humaines dans Annotation : le scope par defaut (status submitted/in_review/approved l.37) risque d'ASPIRER le gold dans les exports annotateurs → pollution silencieuse ; L'unicite (project, document, annotator) force un seul gold/doc : versions de gold concurrentes mal modelisees

**Pertinence** : Tres bonne reutilisation du socle mais sacrifie la provenance d'arbitrage exigee et cree un risque de pollution des exports annotateurs : convient pour un MVP rapide, insuffisant pour la tracabilite demandee.

## Nouvel ExportFormat `gold` + writer dédié branché sur le modèle GOLD natif
Le module GOLD a ses propres modeles (GoldAnnotation/GoldClause/ArbitrationDecision avec provenance, votes, score, niveau d'auto-resolution). On ajoute UN format `gold` (et `gold_provenance`) a ExportFormat, un `_write_gold(path, project, scope)` dans services.py, une cle dans `_IMPLEMENTED_FORMATS` et `ext_by_format`. run_export dispatche dessus. L'artefact gold est riche : verdict + qui a arbitre + commentaire + votants + concordance. Les formats existants restent pour les sessions annotateurs.

**Forces** : Provenance complete dans l'artefact : qui a arbitre, commentaire, votes annotateurs vs LLM, niveau d'auto-resolution, signal humain!=LLM — le materiau exact du module GOLD ; Separation nette : zero risque de polluer les exports annotateurs (scope defaut l.37 inchange), le gold a son format identifie ; Modele GOLD natif = versions intermediaire/final propres, pas de hack sur l'unicite Annotation ; manifest peut tracer la config de campagne ; Garde des formats neutres pour livrer le verdict seul (scope.provenance=false) a un consommateur ML

**Faiblesses** : Plus de code a ecrire et tester : writer(s), branchements run_export, serializer, radio admin, types contract ; Risque de DUPLIQUER build_snapshot/_write_* si pas de socle commun extrait — anti-DRY explicitement interdit par la consigne ; Concordance 'plus proche du gold' a recabler : concordance.py compare humain<->LLM, pas <->GoldClause ; Deux familles de formats a documenter : confusion possible 'je veux le gold mais csv sort les annotateurs'

**Pertinence** : Repond pleinement a la provenance et a la separation, mais paie en duplication de code et en recablage concordance, ce qui heurte la contrainte de non-duplication du socle.

## Couche d'adaptation 'gold→pivot' : modèle GOLD natif, mais réutilise les writers existants
Compromis. Modeles GOLD natifs (provenance/votes/score). Au lieu d'un nouveau writer, un adaptateur `gold_snapshot(doc)` produit le MEME dict pivot que build_snapshot (doc/annotator='gold'/clauses/themes/boundary…) ENRICHI d'un bloc additif `arbitration` (qui, commentaire, votes, niveau, score). _selected_annotations gagne une branche `scope.gold=true` qui itere GoldAnnotation et appelle gold_snapshot. Tous les writers existants consomment ce dict — jsonl/xml/md sortent le bloc arbitration, csv/conll l'ignorent (extrasaction='ignore' l.70 deja tolerant). Un flag scope.provenance pilote l'inclusion.

**Forces** : Reutilise les 6 writers ET run_export/manifest/self-heal/retry/download SANS dupliquer : un seul point d'entree (le snapshot) varie — conforme a l'esprit DRY de la consigne ; Provenance riche disponible (jsonl/xml/md la portent) tout en gardant csv/conll/hf plats pour le ML : richesse opt-in via scope.provenance ; Modele GOLD natif → versions intermediaire/final, votes, score, niveau d'auto-resolution proprement stockes et exportables ; pas de hack d'unicite ; Concordance 'plus proche du gold' triviale : gold_snapshot expose le meme vecteur per-sentence que les annotations → iaa.py/_theme_vector et concordance.py reutilisables ; exportable via iaa_matrix existant ; scope.documents existe deja (l.38-40) → export gold par lot (intermediaire) ou corpus (final) sans nouveau code ; UI minimale (un toggle 'Base gold' + 'inclure provenance')

**Faiblesses** : Le contrat du dict pivot doit etre documente/teste : le bloc `arbitration` doit rester purement ADDITIF (a verrouiller par test pour ne pas casser build_snapshot) ; Effort moyen : ecriture de gold_snapshot + branche _selected_annotations + adaptateur de vecteur concordance (superieur a l'option 1) ; csv/conll restent volontairement pauvres en provenance : provenance en tableur → jsonl/xml (acceptable mais a expliquer) ; Couplage de calendrier : necessite que le modele GOLD natif existe deja

**Pertinence** : Meilleur equilibre : satisfait simultanement non-duplication du socle, provenance riche opt-in, versions intermediaire/final et stat 'plus proche du gold' — le seul a cocher les trois exigences en tension.

## ✅ Recommandation : Couche d'adaptation 'gold→pivot' : modèle GOLD natif, mais réutilise les writers existants (option 3)

> Seule des trois à satisfaire simultanément les trois exigences en tension : (1) NE PAS DUPLIQUER le socle — un seul gold_snapshot rebranche les 6 writers + run_export + manifest + self-heal + retry + download deja livres prod ; (2) une provenance RICHE (qui a arbitre, commentaire, votes annotateurs>LLM, signal humain!=LLM, niveau d'auto-resolution) que l'option 1 perd a l'export et que l'option 2 obtient au prix d'un writer duplique ; (3) la stat 'qui est le plus proche du gold' gratuite, car gold_snapshot expose le MEME vecteur per-sentence que build_snapshot et iaa.py/_theme_vector + concordance.py se rebranchent sans reecriture. L'option 1 est la moins chere mais sacrifie la provenance et risque d'aspirer le gold dans les exports annotateurs (defaut status l.37). L'option 2 est propre sur la separation mais paie en duplication de code, interdite par la consigne. L'option 3 prend le modele GOLD natif de l'option 2 ET la reutilisation maximale de l'option 1 en concentrant toute la variabilite sur UN point : le snapshot. Le bloc `arbitration` etant purement additif, les writers actuels l'ignorent deja (csv via extrasaction='ignore' l.70), donc la regression sur build_snapshot est verrouillable par un seul test de contrat.

### Détails clés d'implémentation
- Backend services.py : ajouter `gold_snapshot(gold_annotation) -> dict` retournant le pivot build_snapshot (doc/annotator='gold'/schema/status/clauses avec themes[role/support]/boundary/triage_level/certainty/validated) ENRICHI d'un bloc additif `arbitration: {arbiter, decided_at, comment, level (absolute_1clic|auto_low_risk|manual), votes:{annotators:[...],llm:[...]}, humanDiffersFromLlm:bool, score}`
- _selected_annotations (services.py l.26) : nouvelle branche `if scope.get('gold'): iterer GoldAnnotation.objects.filter(project=...) [+ scope.documents l.38-40 pour lot vs corpus] et yield gold_snapshot(...)` ; sinon comportement actuel intact (zero regression export annotateurs)
- scope JSON : `{gold:true, documents?:[...], provenance?:true (defaut), statuses?:['gold_draft'|'gold_final']}` — intermediaire = gold non finalise par lot, final = corpus gold finalise
- Writers : AUCUN nouveau. jsonl/xml/md emportent le bloc `arbitration` ; csv/conll/hf l'ignorent (plats pour le ML). Test verrouillant que `arbitration` est purement additif et que build_snapshot (sessions humaines) ne le contient jamais
- manifest enrichi (services.py l.235-252) : ajouter `gold_version`, `arbiters` (provenance agregee), `campaign_config:{weights,who_arbitrates,sharing}`, `n_auto_resolved` vs `n_manual` — artefact auto-portant et auditable, dans le meme dict manifest deja serialise
- Concordance gold : adapter concordance.py / iaa.py pour accepter le vecteur de gold_snapshot (meme forme per-sentence que _theme_vector EXACT humain) → KPI 'annotateur le plus proche du gold' = kappa(annotation_i, gold) sans nouveau moteur ; exposable via le format iaa_matrix existant (_write_iaa_matrix l.107)
- Frontend admin/exports/page.tsx : ajouter hors-radio un toggle `Base gold` (set scope.gold, data-testid `gold-scope`) + checkbox `Inclure la provenance d'arbitrage` (scope.provenance, data-testid `gold-provenance`) ; reutiliser createExport(slug,{format,scope}) et toute la machinerie ExportRow/polling/Telecharger/Relancer
- Lien depuis la gestion GOLD : bouton 'Exporter ce lot / le corpus gold' depuis la liste de docs du module GOLD → createExport avec scope.documents du lot (intermediaire) ou sans (final), reutilise l'historique d'exports existant (pas de nouvelle vue de download)
- Geler le contrat du dict pivot dans un test partage pour que gold_snapshot et build_snapshot ne divergent pas ; pas besoin de AnnotationSource.ARBITRATION_GOLD dans cette option (le gold a son propre modele)
