# Module de gestion (liste docs) du module GOLD — tableau de bord de résolution des conflits inter-annotateurs

## Option A — Page projet dédiée /projects/[slug]/gold, étendant l'endpoint documents existant
Nouvelle route App Router /projects/[slug]/gold avec une liste à plat (1 ligne par document), réutilisant et étendant l'action DRF ProjectViewSet.documents (backend/claire/projects/views.py:264) qui produit déjà la matrice doc×annotateur (status/nClauses/locked). On enrichit chaque ligne d'un bloc gold (statut résolution non_résolu/en_cours/résolu, % phrases arbitrées, arbitre(s), verrou d'arbitrage). Filtres/tri/recherche côté client sur ce payload ; entrée vers la résolution via lien /gold/[documentId]. Lock d'arbitrage réutilise le pattern Project.locked/Annotation.locked (locked/locked_at/locked_by) sur un nouveau modèle léger GoldResolution. Traçabilité via record_event (claire/audit/services.py).

**Forces** : Réutilise au maximum le socle : action documents déjà document-centrée anti-duplication (ADR-001), DocStatusBadge, ProjectLockControl, useProjectDocuments, prefs namespacés par compte ; Cohérent avec l'IA existante : project_iaa fournit déjà le kappa pairwise par document → colonne 'difficulté/chaleur de désaccord' triable sans nouveau calcul lourd ; Coût d'intégration faible, livrable vite, surface de test réduite (étend des endpoints/composants déjà testés pytest/vitest) ; Navigation directe liste→résolution alignée sur le flux docs→/annotate déjà connu des utilisateurs

**Faiblesses** : Une liste à plat scale mal au-delà de ~50-100 docs : pas de regroupement par lot, KPIs de campagne noyés ; L'action documents devient multi-responsabilité (annotation + gold) — risque de payload lourd si on charge le % résolution par doc en N+1 ; Pas de vue 'cockpit' (stats agrégées de concordance ↔GOLD) sans page complémentaire ; Le temps réel (verrou exclusif auto-expirant) n'est pas natif au pattern Project.locked qui est un verrou manuel sans expiration

**Pertinence** : Forte adéquation au besoin minimal (liste + statut + % + verrou + arbitres + entrée résolution) et au socle ; mais ne couvre pas seule les lots et le cockpit de stats demandés. Bon socle d'itération 1.

## Option B — Cockpit de campagne en deux étages : bandeau KPIs + table dense de documents virtualisée, sur endpoint gold dédié
Page /projects/[slug]/gold structurée en un bandeau supérieur (KPIs campagne : %docs résolus, file restante par niveau de risque C1–C5, concordance moyenne annotateur↔GOLD) + une DataTable dense, virtualisée, colonnes triables/filtrables (statut, %arbitré, difficulté=kappa, arbitre assigné, verrou live, dernier arbitrage). Sélection multiple → barre d'actions de lot (assigner arbitre, verrouiller/déverrouiller, marquer auto-résolvable, exporter gold partiel). Backend : nouvel endpoint /projects/{slug}/gold/documents agrégeant GoldResolution + niveaux d'auto-résolution (accord absolu/peu risqué/risqué) calculés depuis project_iaa + theme_set_vector. Verrou d'arbitrage exclusif auto-expirant via un nouveau canal WebSocket (réutilise l'infra channels/PresenceConsumer, group gold_{project}) avec TTL serveur.

**Forces** : Répond à TOUTES les exigences du module de gestion d'un coup : lots, filtres/tri, statut, %, arbitres, verrou temps réel, entrée résolution, et amorce les stats de concordance ↔GOLD ; Cockpit hiérarchisé (KPIs→table) = mise en page 'top agence', priorise visuellement la file à risque (C1–C5 déjà modélisé en triage_level) ; Niveaux d'auto-résolution exposés dès la liste (badge 'accord absolu, 1 clic') → accélère massivement le throughput d'arbitrage ; Virtualisation + sélection de lot = scale à plusieurs centaines de docs ; barre d'actions sans bouger la souris (contrainte UX clics successifs)

**Faiblesses** : Plus gros chantier : nouveau modèle GoldResolution + endpoint agrégé + canal WS lock = surface backend et tests significative ; Verrou exclusif auto-expirant via WS demande une logique TTL/heartbeat/reclaim non triviale (gestion des déconnexions, idempotence) ; Risque de sur-ingénierie si la campagne reste petite ; KPIs ↔GOLD nécessitent que le gold existe déjà (œuf/poule au démarrage) ; DataTable virtualisée dense doit rester a11y (navigation clavier, ARIA grid) — coût d'accessibilité réel

**Pertinence** : La plus alignée sur la vision 'module aussi abouti que /annotate' et sur l'intégralité des exigences (lots, temps réel, niveaux, stats). C'est la cible produit ; le risque est le périmètre.

## Option C — Vue Kanban par statut de résolution (colonnes non résolu / en cours / résolu) avec cartes-documents drag-to-assign
Tableau de gestion façon Kanban : trois (ou quatre avec 'auto-résolvable') colonnes par statut de résolution, chaque document est une carte riche (titre, %arbitré en jauge, mini-heatmap de désaccord par bloc, avatars annotateurs, arbitre assigné, badge verrou live). Glisser une carte vers 'en cours' déclenche l'assignation d'arbitre + pose du verrou ; clic sur la carte ouvre la résolution. Filtres globaux (par arbitre, par niveau de risque, par lot/tag). Backend identique en données à B (GoldResolution + statut), mais l'UI est orientée flux de travail plutôt que tableur.

**Forces** : Lecture immédiate de l'avancement de campagne (où est le travail, qui bloque quoi) — excellent pour un lead qui pilote des arbitres ; Le drag pour assigner/verrouiller est ludique et lisible ; les avatars d'arbitres rendent le partage des arbitrages tangible ; Mini-heatmap par carte met la 'difficulté' en avant sans ouvrir le doc, cohérent avec l'esprit contrat juridique (catégories en avant) ; Réutilise user_color/display_name (identity) et le pattern de présence pour les avatars live

**Faiblesses** : Le Kanban scale mal pour le tri/filtre fin et la sélection de LOT (action de masse moins naturelle qu'une table) ; Comparaison chiffrée entre docs (kappa, %) moins lisible qu'en colonnes triables → les stats de concordance passent au second plan ; Drag-and-drop a11y est notoirement difficile (doit avoir un équivalent clavier complet) ; Le statut 'en cours' en Kanban duplique l'information du verrou temps réel → risque d'états incohérents si le verrou expire mais la carte reste en colonne

**Pertinence** : Séduisant pour le pilotage visuel et le partage d'arbitrages, mais en tension avec deux exigences fortes (lots/tri fin et stats chiffrées). Convient mieux comme VUE alternative que comme tableau de gestion principal.

## ✅ Recommandation : Option B — Cockpit de campagne (bandeau KPIs + table dense virtualisée) avec endpoint gold dédié, en réutilisant la matrice de documents existante et l'infra channels pour le verrou exclusif

> C'est la seule option qui couvre l'intégralité du périmètre exigé (liste+statut+%+verrou+arbitres+lots+historique+entrée résolution, et amorce les stats ↔GOLD) tout en restant 'aussi abouti que /annotate'. Le socle existant rend le coût raisonnable : ProjectViewSet.documents fournit déjà la matrice doc×annotateur anti-duplication (ADR-001) qu'on n'étend que d'un bloc gold ; project_iaa donne le kappa pairwise par document gratuitement pour la colonne difficulté et le tri 'là où l'accord chute' ; le pattern Project.locked/Annotation.locked (locked/locked_at/locked_by) et record_event donnent verrou+traçabilité sans réinventer ; l'infra channels (PresenceConsumer) sert de base au canal de verrou exclusif. On évite ainsi le piège d'Option A (liste à plat qui ne scale pas, pas de cockpit) et la tension d'Option C (Kanban hostile au tri/lots/stats). Le Kanban d'Option C peut revenir plus tard comme VUE optionnelle sur le même endpoint. Risque principal à maîtriser : périmètre — donc livrer en deux passes (table+filtres+verrou d'abord, KPIs↔GOLD ensuite une fois le premier gold produit) et garder le verrou auto-expirant simple (TTL serveur + heartbeat).

### Détails clés d'implémentation
- Backend : nouveau modèle GoldResolution(project, document, status[unresolved/in_progress/resolved], pct_resolved, arbiters M2M, lock fields locked/locked_at/locked_by/lock_expires_at) dans une app claire/gold/ ; ne PAS surcharger Annotation.
- Endpoint : action DRF @action(detail=True, url_path='gold/documents') sur ProjectViewSet, renvoyant results_envelope([{document, goldStatus, pctResolved, difficultyKappa, autoLevel, arbiters[], lock}]) — réutilise l'index ann_idx/assign_idx de la méthode documents() (views.py:300-339) et project_iaa pour difficultyKappa.
- Niveaux d'auto-résolution dérivés serveur : 'accord_absolu' (tous annotateurs = même theme_set par phrase, 1 clic), 'peu_risque' (désaccord mineur secondaire / triage C4–C5), 'risque' (primaire divergent / C1–C2) — calculés via _theme_set_vector (iaa.py:28) + triage_level.
- Verrou exclusif auto-expirant : nouveau consumer GoldLockConsumer (group gold_{projectSlug}), réutilise l'infra channels de claire/collaboration/consumers.py ; TTL serveur (ex. 120s) rafraîchi par heartbeat client, reclaim au disconnect ; lock pose via record_event(verb='gold.locked').
- Frontend : route frontend/src/app/(app)/projects/[slug]/gold/page.tsx ; hook useGoldDocuments(slug) (React Query) ; composant GoldDashboard avec <GoldKpiBar/> (data-testid='gold-kpi-bar') + table virtualisée <GoldDocTable/> en role='grid' (a11y clavier), réutilise DocStatusBadge + ajoute GoldStatusBadge + DifficultyMeter (tokens, zéro hex).
- Filtres/tri/lots : barre de filtres (statut, arbitre, niveau de risque C1–C5, recherche titre) ; sélection multi-ligne (checkbox + shift-click) → <GoldBatchBar/> ancrée (data-testid='gold-batch-bar') actions: assigner arbitre, verrouiller/déverrouiller, exporter gold partiel ; placement sous le curseur pour clics successifs sans déplacer la souris.
- Prefs interface : persister tri/filtres/colonnes via le store prefs namespacé par compte (frontend/src/store/prefs.ts, sync /me), avec mémoire PAR DOCUMENT pour la résolution (clé project+document).
- Export gold partiel/final : brancher sur ExportJob existant (scope JSON) avec un nouveau format/scope 'gold' ; bouton dans GoldBatchBar pointant vers le flux export async déjà livré (dossier-export-async).
- Lien d'entrée résolution : chaque ligne → /projects/[slug]/gold/[documentId], data-testid='open-gold-{externalId}', miroir du pattern open-doc-{externalId} de docs/page.tsx:99.
- Tests : pytest sur GoldResolution + endpoint gold/documents + auto-levels (réutiliser fixtures iaa/concordance) ; vitest/MSW sur GoldDashboard (filtres/tri/lots) ; playwright sur verrou exclusif (deux sessions, expiration).
