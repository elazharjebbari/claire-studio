# Plan d'exécution

## Stratégie de branche & déploiement

"Modèle : déploiement continu sur prod (pactiva.legal) avec un lot = une branche = une PR = un déploiement, chaque livraison VERTE au gate (pytest + tsc + vitest ; les e2e Playwright ne sont PAS dans le gate). Branche d'intégration de la refonte 'refonte/atelier-v2' partant de main ; chaque lot sur une branche courte enfantée d'elle (ex. 'refonte/atelier-v2/lot-0-socle-couleur', puis lot-2-button, lot-3-theme-icons, lot-5-sentence-menu, etc.), nommées par numéro de lot pour refléter l'ordre du séquencement. Règle anti-mur-rouge : le Lot 0 cadre le périmètre dur du linter (workspace + ui + lib triage/validationDisplay) AVANT toute autre tokenisation ; les lots suivants n'élargissent le périmètre check-no-hex qu'à mesure qu'ils nettoient leurs fichiers. Commits atomiques par sous-tâche isolable (backend / schéma prefs / helper pur / primitive / câblage UI / adaptation tests) pour faciliter la revue et le rollback granulaire ; messages en français suivant la convention du repo (feat/fix(scope)). Ordre d'intégration imposé par les dépendances : 0 -> 2 -> 3 -> 5 -> 4 -> 6 -> 7 -> 1 -> 8 -> 9. Chaque PR : (1) merge sur main seulement gate vert ; (2) déploiement incrémental immédiat via les scripts deploy/ (gate de déploiement via backend/.venv, lancer avec DJANGO_SECRET_KEY=x) ; (3) pour les lots à backend (Lot 1 layout, Lot 4 planFilter/displayOpen, Lot 6 inspectorOpen) la migration/whitelist ui_prefs.py est livrée et déployée AVANT ou avec le front, jamais après. Garde-fou e2e : les Playwright n'étant pas dans le gate, exécuter un passage Playwright manuel ciblé après les lots à fort risque de data-testid (5, 4, 6, 7, 1, 8) avant de déclencher le déploiement. Fallbacks token-only minimaux (Disclosure/Kbd/Button-warning locaux) tolérés si un consommateur doit avancer avant son fournisseur, avec une issue de dette pour converger sur la primitive partagée. Demander confirmation à l'utilisateur avant tout commit/push/merge/déploiement (aucun n'est déclenché sans accord explicite)."

## Risques globaux

- Primitives fondatrices ABSENTES du repo (vérifié) : check-no-hex.mjs, eslint anti-hex, Disclosure.tsx, Button.tsx étendu (seulement 4 variantes non-sémantiques aujourd'hui), themeIcons.ts, shortcuts.ts, Kbd.tsx. Tout le plan repose sur leur livraison ordonnée en tête (Lot 0/2/3/5/9). Un glissement de Lot 0/2/5 décale en cascade 6/7/8. Mitigation : séquencement strict + fallbacks token-only minimaux documentés (dette à rembourser) si un lot consommateur doit avancer.
- Mur rouge du linter anti-hex : 147 occurrences de couleurs Tailwind brutes dans le repo, majoritairement HORS atelier (admin/auth/public). Si check-no-hex scanne tout src/**, la CI explose et bloque le gate de TOUS les lots. Mitigation impérative : périmètre dur = components/workspace/** + components/ui/** + lib/triage|validationDisplay ; reste en allow-list/TODO warning. À cadrer dès le Lot 0.
- Préservation des data-testid alimentant les e2e Playwright (hors gate mais garde-fous de régression) : la fusion des bandeaux (Lot 1), le déplacement de toggles sous Disclosure (Lot 4/8), le retrait du bloc LLM (Lot 5), l'extraction TriageLevelBadge/TriageWhy (Lot 6) risquent de supprimer/déplacer des ids. Règle transverse : ne jamais retirer un data-testid ; monter le contenu plié caché (pas démonté) pour rester atteignable ; n'adapter une spec que si strictement nécessaire et dans le même lot (notamment document-ux/llm-compare/theme-multipicker pour Lot 5).
- Frontière token MÉTIER (thème/triage/juge/compare) != token d'ÉTAT (--sem-success/warning/danger/info) : tentation récurrente de mapper agree->success, diverge->warning (Lot 0/7), couleur triage ou vert de thème -> success (Lot 2/3/6). PIÈGE interdit par la convention. Mitigation : rampe compare et triage MÉTIER dédiées, icônes thème en currentColor, revue systématique + test 'jamais token d'état réutilisé comme signal métier'. C3 multi-label -> info (ni succès ni alerte).
- WCAG AA en thème CLAIR non garanti pour certaines teintes métier : lime C2 (#84CC16) et ambre C4 (#F59E0B) en texte plein sur fond pâle, et les paires triage utilisées en couleur de TEXTE. Mitigation : assombrir les variantes light de la rampe triage dans design-tokens.json (comme les sémantiques) jusqu'à passer le harnais AA du Lot 0 ; tester axe en clair ET sombre (couverture aujourd'hui implicite).
- Persistance PAR COMPTE — whitelist backend oubliée : ui_prefs.py / merge_ui_preferences doit accepter les nouvelles clés (layout au Lot 1 ; planFilter/displayOpen au Lot 4 ; inspectorOpen au Lot 6). Si le serializer whiteliste sans ces clés, le PATCH /me les supprime silencieusement -> faux 'ça ne persiste pas' + risque de boucle de re-PATCH. Le changement backend est OBLIGATOIRE et testé (pytest) à chaque lot concerné. Respecter la garde rev (bump au mouseup/keyup, pas à chaque mousemove) pour éviter le flood de PATCH.
- Virtualisation vs jsdom (Lot 4) : @tanstack/react-virtual ne monte que les lignes visibles et dépend de mesures de hauteur indisponibles en jsdom -> tocCoverage.test.tsx peut échouer et casser le gate vitest. Cadrer AVANT introduction de la lib : forcer hauteur/largeur conteneur, mode non-virtualisé en test, ou stub. Risque aussi sur la synchro chip->vue (scrollToIndex au lieu de querySelector+scrollIntoView).
- Composants hypertrophiés à fort risque de régression silencieuse : DocumentPanel ~1530 lignes (Lot 7), WorkspaceToolbar ~615 lignes (Lot 8), ResizablePanels central contrôlé (Lot 1). Règle : ne toucher QUE rendu couleur + visibilité conditionnelle + structure, ZÉRO changement de handler/store métier. Les e2e Playwright n'étant PAS dans le gate, prévoir un passage Playwright manuel ciblé après ces 3 lots avant déploiement.
- Régression visuelle subtile par changement d'alpha lors du remplacement hex+alpha -> rgb(var(--token)/a) : caler exactement 0x22->0.133, 0x1a->0.10, 0x26->0.15. Tests asservis à un hex précis (boxShadow inset, colorClass amber) à adapter (validationDisplay.test.ts) sans toucher clauseChip.test.tsx (garder le mot 'inset').
- Collision de raccourcis (Lot 9) : useShortcuts et useDivergenceShortcuts montés simultanément écoutent window ; double preventDefault sur n/1/2. Le registre doit porter le contexte (en Compare, useShortcuts ne capture pas n). Capture sauvage en saisie si isEditable non appliqué partout (V/w/?). Curseur collant : V doit emprunter EXACTEMENT onQuickValidateAdvance (ne pas réimplémenter le scroll).
