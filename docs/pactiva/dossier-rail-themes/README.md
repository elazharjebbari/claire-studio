# Dossier — Décorateur gauche des phrases (rail de thème) · continuité + provenance

> Issu d'un workflow (5 agents : audit → 3 solutions concurrentes → synthèse). Objectif : rail
> CONTINU sur thèmes successifs identiques, RUPTURE au changement, distinction humain-validé vs
> LLM-suggéré, sans surcharge. Date : 2026-06-26.

## 1. Audit
**Système actuel** — Le rail gauche d'une phrase est rendu dans la SentenceRow (DocumentPanel.tsx ~l.1496-1507) via deux propriétés de style inline :
- box-shadow `inset 3px 0 0 ${runColor}` : un liseré vertical coloré, où runColor = `rgb(${hexToRgbChannels(getThemeToken(run.theme).color)} / 0.5)` (couleur métier du thème, alpha pré-baké 0.5). À défaut de thème, un liseré plus fin (inset 2px) porte le niveau de triage (triageColor) en overlay opt-in.
- border-top `1px dashed rgb(var(--surface-text-muted) / 0.3)` quand showDashedTop est vrai : la frontière pointillée marquant le DÉBUT d'un run.

Le `run` courant vient de `runAt(runs, s.index)`. La SOURCE `runs` dépend de llmSource (DocumentPanel ~l.299-302) : en mode `human`/`compare` ce sont les `humanRuns`, sinon les `runsByJudge[llmSource]`.

Différence clé de calcul :
- humanRuns = `computeRuns(drafts, n, { perSentence: true })` (l.242-244) : CHAQUE clause humaine devient un run d'EXACTEMENT une phrase `[ancre, ancre]`, séparé par des runs neutres. Aucune fusion. Donc `isRunStart = run.start === s.index` (l.817) est VRAI pour toute phrase annotée, et `showDashedTop = showBoundaries && isRunStart && run.theme != null` (l.818) trace un pointillé en tête de chaque phrase annotée.
- runsByJudge[j] = `coalesceRuns(computeRuns(judgeAnchors(...), n))` (l.257) : les segments adjacents de même thème sont FUSIONNÉS en un seul run (lib/runs.ts coalesceRuns), donc isRunStart n'est vrai qu'au vrai changement de thème.

En mode comparaison (isCompare), runColor traduit l'ACCORD (sem-success/sem-warning) et showDashedTop est forcé à false (l.821-829). La provenance (validated/seededFrom/resolvedFrom) n'est utilisée NULLE PART dans le rail/frontière ; elle ne sert qu'au badge texte d'attribution de la clause (« ✓ Juge » / « ◷ Juge », l.999-1015) et au statut de validation (vStatus).

### Problèmes
- POINTILLÉS PARTOUT (mode humain) : parce que humanRuns est calculé en perSentence, chaque phrase annotée est un run distinct → isRunStart est vrai sur TOUTES les phrases annotées → showDashedTop trace un border-top pointillé entre toutes les phrases annotées successives, MÊME quand elles partagent le même thème. La frontière perd tout sens (elle ne signale plus un changement) et crée un effet de hachures visuelles. Asymétrie injustifiée avec les juges, qui passent par coalesceRuns et n'affichent une frontière qu'au vrai changement de thème.
- RAIL DISCONTINU sur un même thème : le box-shadow inset du rail est dessiné phrase par phrase, mais comme chaque ligne a son propre padding/marges (`-mx-2 px-2 py-1`) et que chaque run perSentence est isolé, le liseré vertical apparaît segmenté/interrompu entre deux phrases successives de même thème au lieu d'être un trait continu. L'œil ne perçoit pas un BLOC thématique unique mais une succession de petits traits, ce qui contredit l'objectif (rail continu sur même thème, rupture nette au changement).
- AUCUNE DISTINCTION VISUELLE humain vs suggéré : le rail n'exploite jamais validated / seededFrom / resolvedFrom. Une phrase réellement validée par un humain (validated=true), une pré-annotation d'un juge non encore confirmée (seededFrom='preannotation:*', validated=false) et un arbitrage adopté (resolvedFrom) produisent EXACTEMENT le même rail (même couleur, même opacité 0.5, même style). L'annotateur ne peut pas distinguer d'un coup d'œil ce qui est ferme de ce qui est seulement suggéré ; la seule trace de provenance est le badge texte d'en-tête, absent du rail lui-même.
- FRONTIÈRE = SIGNAL UNIQUEMENT VISUEL (a11y) + ABSENCE EN MODE SUGGÉRÉ : le seul vecteur de la frontière et de la provenance est la couleur/le pointillé (border-top, alpha). Rien n'est porté par data-* exploitable, par un motif, ni par un libellé ; en mode compare le pointillé disparaît totalement (showDashedTop=false) sans substitut. Un daltonien ou un contraste faible (alpha 0.3 du pointillé, alpha 0.5 du rail) ne distingue ni les frontières ni le statut. La couleur est utilisée seule comme unique canal d'information.
- COUPLAGE perSentence ↔ rendu du rail : le même tableau humanRuns sert à la fois à l'INTERACTION (sélection multi-blocs, clauseRangeBetween, deriveBlocks, mapping phrase→clause qui EXIGE perSentence) ET au RENDU décoratif du rail/frontière. Toute correction du rendu (coalescence pour le rail) ne doit pas casser l'interaction : il faut un second jeu de runs coalescés DÉDIÉ à l'affichage, dérivé de humanRuns, sans toucher humanRuns lui-même.

### Contraintes
- humanRuns DOIT rester en perSentence : la sélection multi-blocs (clauseRangeBetween), deriveBlocks, le mapping phrase→clause et le voyant par phrase en dépendent. Ne pas remplacer humanRuns par des runs coalescés ; introduire un jeu de runs d'AFFICHAGE séparé (ex. coalesceRuns(humanRuns)) uniquement pour piloter runColor/isRunStart/showDashedTop du rail.
- ZÉRO hex en dur : toute couleur passe par getThemeToken(code).color + hexToRgbChannels pour produire rgb(r g b / alpha), ou par les tokens sémantiques (var(--sem-success), var(--sem-warning), var(--surface-text-muted)). Aucune valeur #RRGGBB littérale dans le composant.
- Accessibilité — la couleur jamais seule : la frontière (changement de thème) et la distinction humain vs suggéré doivent être portées par au moins un second canal NON coloré (style de trait plein vs pointillé, opacité/épaisseur du rail, motif, attribut data-* + libellé/title, ou icône) en plus de la teinte, et rester perceptibles à faible contraste / en daltonisme. Conserver des data-attributes (data-boundary, data-dashed, et idéalement data-provenance) pour le test et l'AT.
- Subtilité / non-surcharge : l'atelier affiche déjà badges, overlays injustice, triage, réglette N-way. La distinction humain/suggéré doit rester discrète (variation d'opacité/épaisseur/trait du rail, pas une nouvelle couleur criarde ni un second élément lourd) pour ne pas concurrencer les autres canaux.
- Cohérence inter-modes : le comportement du rail/frontière humain doit s'aligner sur celui déjà obtenu pour les juges via coalesceRuns (frontière au seul changement de thème). Le mode compare (rail = accord, pas de thème) ne doit pas être régressé.

### Données disponibles
- run.theme (string|null) — thème du run couvrant la phrase ; null = run neutre (lib/runs.ts Run.theme), base de la couleur et du regroupement par coalescence.
- run.start / run.end / run.localId — bornes du run et ancre ; après coalesceRuns, run.start === s.index identifie le VRAI début de bloc thématique (frontière légitime).
- validated (boolean, DraftClause l.105) — true = clause confirmée par un humain (saisie, adoption modèle, confirmation de pré-remplissage) → rail FERME (plein, opacité/épaisseur pleine).
- seededFrom (string|null, l.93, ex. 'preannotation:claude') — pré-annotation d'un juge NON encore validée → rail SUGGÉRÉ (atténué/pointillé/opacité réduite) ; le préfixe 'preannotation:' est à stripper pour le label du juge.
- resolvedFrom (string|null, l.99) — juge dont la proposition a été ADOPTÉE par arbitrage (implique validated=true) → traiter comme ferme, éventuellement avec une marque de provenance d'arbitrage.
- llmSource (store, 'human'|'compare'|'claude'|'codex'|…) — mode de rendu : en mode juge tout vient des runsByJudge (déjà coalescés) = SUGGESTION par nature ; en 'human' s'appuyer sur validated/seededFrom ; en 'compare' le rail code l'accord (pas le thème).
- anchorByIndex / drafts — accès O(1) à la clause (donc à validated/seededFrom/resolvedFrom) par index de phrase, pour décorer le rail de la phrase courante.
- Tokens & helpers : getThemeToken(code).color, hexToRgbChannels, readableTextColor, et tokens sémantiques var(--sem-success), var(--sem-warning), var(--surface-text-muted) pour pointillés/accord sans hex en dur.

## 2. Solutions concurrentes
### Capsules de thème — rail segmenté à coins arrondis (run = capsule continue, provenance par remplissage) — 9/10
**Principe** : Au lieu de redessiner un liseré indépendant par phrase, on traite chaque RUN de thème (suite contiguë de phrases de même thème) comme UNE capsule verticale unique : une barre colorée à coins arrondis dont le haut est arrondi à la 1re phrase du run et le bas à la dernière, sans interruption au milieu. Le rail cesse d'être une décoration par-ligne et devient la matérialisation d'un bloc thématique. La rupture (changement de thème) n'est plus un pointillé surajouté mais l'espace + l'arrondi naturel ENTRE deux capsules. La provenance (humain validé vs LLM suggéré) est portée par le TRAITEMENT de la capsule — plein vs contour/hachuré — et non par une teinte nouvelle. Tout repose sur un jeu de runs d'affichage dédié, displayRuns = coalesceRuns(humanRuns), qui n'altère JAMAIS humanRuns (perSentence) requis par la sélection/deriveBlocks/mapping phrase→clause.
- **Continuité** : On introduit, à côté de humanRuns, un displayRuns mémoïsé = coalesceRuns(humanRuns) (déjà importé, lib/runs.ts), utilisé UNIQUEMENT pour piloter runColor/isRunStart/showCap. Le run d'affichage de la phrase = runAt(displayRuns, s.index). Conséquence immédiate : pour N phrases successives de même thème, isRunStart n'est vrai qu'à la 1re — fini les pointillés partout, symétrie avec les juges (qui passent déjà par coalesceRuns).\n\nPour la CONTINUITÉ visuelle, on calcule par phrase trois booléens purs depuis le run d'affichage : isRunStart = run.start === s.index, isRunEnd = run.end === s.index, isRunMiddle = !isRunStart && !isRunEnd. La capsule reste un box-shadow inset (zéro nouvel élément DOM, on respecte « non-surcharge ») mais le RAYON suit la position dans le run, ce que box-shadow inset ne sait pas faire seul → on déplace le rail vers un ::before en position absolue, géré par data-attributes (déjà data-boundary/data-dashed présents l.1456-1457) :\n  - rail = pseudo-élément absolu left:0; top:0; bottom:0; width:3px; background:var(--rail-color) (variable CSS posée inline, couleur du thème via getThemeToken+hexToRgbChannels, alpha 0.5 conservé).\n  - top:-1px quand isRunMiddle || isRunEnd, bottom:-1px quand isRunMiddle || isRunStart → le rail d'une phrase CHEVAUCHE de 1px celui de la voisine de même run, ce qui SOUDE optiquement les segments par-dessus le py-1 + le gap de la liste (cause racine du rail « segmenté » identifiée dans l'audit).\n  - border-radius : 3px en haut seulement si isRunStart, 3px en bas seulement si isRunEnd, 0 ailleurs → coins arrondis au DÉBUT et à la FIN du run, droits au milieu = une seule capsule lisse.\nLa couleur étant identique sur tout le run (même run.theme) et le chevauchement supprimant les césures, l'œil lit UN bloc thématique continu. Le -mx-2 ... rounded-md px-2 py-1 de la ligne (l.1491) reste inchangé ; seul le rail passe du box-shadow au ::before, ce qui le découple du clipping de la ligne.
- **Rupture** : La rupture n'est plus un trait pointillé ajouté (border-top, l.1506) mais l'ABSENCE de capsule : entre deux runs de thèmes différents, il y a (a) deux arrondis qui se font face (bas arrondi du run sortant, haut arrondi du run entrant) et (b) un micro-interstice de 2–3px (on retire le chevauchement -1px précisément à la frontière de thème). Le changement de couleur + le double arrondi + le gap = trois signaux concordants au même endroit. C'est pour cela que « la frontière reprend du sens » : aujourd'hui le pointillé apparaît entre TOUTES les phrases annotées (perSentence) et ne signale donc plus rien ; avec coalesceRuns la frontière ne survient qu'au VRAI changement de thème, exactement comme pour les juges — elle redevient un événement rare et informatif, pas un motif de fond.\n\nOn CONSERVE néanmoins un liseré de frontière optionnel (showBoundaries) mais sous forme d'un trait PLEIN court de 2px de haut dans la couleur surface-text-muted, posé à la jointure, plutôt qu'un pointillé sur toute la largeur — moins bruyant, et porté par data-boundary pour les tests/AT. data-boundary reste = isRunStart (déjà en place l.1456), data-dashed est retiré (la frontière n'étant plus pointillée) ou conservé en alias pour ne pas casser les sélecteurs existants. En mode compare (isCompare), aucune régression : la capsule code l'accord (sem-success/sem-warning, l.822-827), tous les coins arrondis (chaque phrase = sa propre micro-capsule d'accord, car il n'y a pas de notion de thème à coalescer), pas de frontière — strictement le comportement actuel, juste rendu via le même ::before.
- **Provenance** : Provenance portée par le REMPLISSAGE de la capsule, pas par une couleur nouvelle (on garde la teinte métier du thème). On lit la provenance du run d'affichage via son ancre : pour le run coalescé, on récupère la clause de run.localId (anchorByIndex/drafts, O(1)) et on dérive un statut ternaire pur : 'ferme' si validated===true ou resolvedFrom!=null (arbitrage adopté ⇒ validated) ; 'suggere' si seededFrom!=null && !validated (pré-annotation non confirmée) ; 'ferme' par défaut pour une saisie humaine directe. Comme une capsule coalescée peut mélanger phrases fermes et suggérées, la règle de bloc = « suggéré tant qu'au moins une phrase du run n'est pas validée » (statut conservateur : on ne sur-affirme jamais « validé »). Rendu :\n  - FERME (humain) : capsule PLEINE, alpha 0.5, bord net. C'est l'état de référence, le plus « solide » visuellement.\n  - SUGGÉRÉ (LLM/pré-annotation) : capsule CREUSE — fond à alpha très réduit (~0.14) + un filet interne, obtenu par un dégradé répété (repeating-linear-gradient) en hachure FINE 45° de la même couleur de thème. La hachure baisse le « poids » perçu sans changer de teinte : on distingue ferme/suggéré au remplissage (plein vs strié), pas à la couleur.\nAccessibilité — couleur jamais seule : la distinction ferme/suggéré tient à la TEXTURE (plein vs hachuré) ET à l'opacité ET à un data-provenance='firm'|'suggested' (nouveau, testable + exposable en aria/title « suite suggérée, non validée »). À faible contraste ou en daltonisme, plein-vs-rayé et 0.5-vs-0.14 restent perceptibles indépendamment de la teinte. La hachure étant intra-capsule, elle reste discrète (ne concurrence ni les badges d'en-tête ✓/◷ l.1000-1015, ni l'overlay injustice, ni le triage) : c'est une variation de matière, pas un 4e canal coloré. En mode juge (llmSource=claude/codex…), TOUT le rail est par nature une suggestion → toutes les capsules sont rendues en hachuré, ce qui aligne sémantiquement « source LLM = proposition » sans code spécial.
- **Forces** : Corrige les DEUX bugs d'un coup avec une primitive unique : coalesceRuns(humanRuns) tue les pointillés-partout ET le chevauchement -1px + radius conditionnel soude le rail segmenté en bloc continu., Réutilise l'existant : coalesceRuns, getThemeToken, hexToRgbChannels, data-boundary/data-dashed déjà là ; aucun nouvel élément DOM lourd (rail = ::before), aucune nouvelle couleur, zéro hex en dur., Symétrie humain↔juges enfin obtenue : même règle de frontière (coalesce) des deux côtés ; la cohérence inter-modes demandée par les contraintes est structurelle, pas ad hoc., Provenance lisible d'un coup d'œil SANS surcharge : plein vs hachuré est une métaphore intuitive (ferme vs provisoire) et reste subtile ; mappe naturellement le mode juge sur 'tout est suggestion'., a11y solide : 3 canaux non-coloriels (texture, opacité, data-provenance/title) ; frontière re-signifiée + portée par data-attributes pour tests et AT., humanRuns intact → sélection multi-blocs, deriveBlocks, mapping phrase→clause et voyant par phrase non touchés (displayRuns est un dérivé d'affichage strict).
- **Faiblesses** : Migration box-shadow→::before : si un autre style (surlignage l.1515, focus ring) suppose le box-shadow inset comme canal du rail, il faut auditer les collisions de pseudo-éléments et de z-index., Capsule coalescée à provenance MIXTE (phrases fermes + suggérées dans le même run de thème) → la règle conservatrice 'suggéré si une seule non validée' peut sous-représenter une majorité validée ; acceptable mais à expliciter (title), sinon perçu comme 'pas encore validé' alors que presque tout l'est., La hachure 45° très fine peut moirer sur écrans non-rétina ou à certains zooms ; nécessite un pas de gradient testé (≥4–5px) et éventuellement un fallback plein+opacité si prefers-reduced-* / faible DPI., Le chevauchement -1px peut créer un léger sur-épaississement aux jointures si arrondi mal réglé ; demande un calage pixel., Ajoute un data-provenance et une lecture de clause par run.localId : surface de test à couvrir (golden) pour éviter les régressions.
- **Risques d'impl.** : box-shadow inset NE PEUT PAS faire des coins arrondis conditionnels haut/bas : il FAUT migrer le rail vers un ::before absolu (left:0;width:3px;top/bottom étendus) ; tenter de garder le box-shadow par-phrase laissera le rail segmenté., Le chevauchement de continuité doit se faire en top:-1px/bottom:-1px du ::before (et NON via margins, qui décaleraient le texte) ; sinon le py-1 + le gap de liste recréent des césures. Couper le chevauchement précisément aux frontières de thème, pas au sein du run., Mémoïser displayRuns = coalesceRuns(humanRuns) en useMemo sur [humanRuns] ; ne JAMAIS substituer displayRuns à humanRuns dans clauseRangeBetween/deriveBlocks/mapping (régression sélection garantie sinon)., Provenance du run coalescé : coalesceRuns garde le localId du PREMIER run (lib/runs.ts l.106) ; il faut scanner les clauses des phrases [run.start, run.end] pour le statut de bloc, pas seulement l'ancre — sinon une phrase suggérée au milieu d'un run 'ferme' sera ratée., Mode compare : ne pas coalescer (pas de thème) — chaque phrase = micro-capsule d'accord, tous coins arrondis, showCap basé sur comparePresent ; vérifier que isCompare force toujours showBoundaries/frontière à false (l.828) et que data-provenance n'est pas émis., Perf : la liste de phrases peut être longue ; garder le calcul des booléens (isRunStart/End/Middle, statut provenance) O(1) par phrase via runAt sur displayRuns + anchorByIndex, sans recalcul de runs dans le render., repeating-linear-gradient pour la hachure : fixer un pas testé (≥4px) et un angle (45°) stables, fournir un fallback plein+opacité réduite sous prefers-reduced-motion/contrast et basse densité ; valider le rendu à 100/125/150% de zoom., Conserver data-boundary=isRunStart et soit retirer data-dashed soit le garder en alias pour ne pas casser les sélecteurs de test existants ; ajouter data-provenance='firm'|'suggested' + title pour l'AT.

### Rail-fil : trait continu coalescé + nœud de rupture, provenance par texture — 9/10
**Principe** : Un rail vertical fin, de la couleur du THÈME, dessiné comme un FIL continu sur toute une suite de phrases de même thème — et non plus segment par segment. La continuité vient d'un jeu de runs d'AFFICHAGE coalescé (`displayRuns = coalesceRuns(humanRuns)`) dédié au rendu, distinct de `humanRuns` (qui reste perSentence pour la sélection/blocs). On dérive par phrase : `isRunStart` (haut du fil), `isRunEnd` (bas du fil), corps. Le rail devient le canal porteur de trois choses orthogonales : (1) le thème = teinte du fil ; (2) la frontière = un NŒUD discret seulement au vrai changement de thème (au `start` du run coalescé) ; (3) la provenance = la TEXTURE du fil (plein/opaque pour humain-validé, atténué+pointillé pour suggéré), aussi portée par data-attributs et title pour l'a11y. Pivot conceptuel : la frontière passe d'une LIGNE HORIZONTALE (border-top, parasite en perSentence car vraie partout) à un NŒUD sur le rail VERTICAL ; on supprime totalement ce border-top inter-phrases. Ainsi le rail porte à lui seul thème + rupture + provenance, sans ajouter d'élément lourd ni de couleur criarde.
- **Continuité** : Source d'affichage dédiée : `const displayRuns = useMemo(() => coalesceRuns(humanRuns), [humanRuns])`, sans toucher `humanRuns` (qui alimente toujours `blocks`/`deriveBlocks`/`clauseRangeBetween`/le mapping phrase→clause). Le rail lit `runAt(displayRuns, s.index)` : pour N phrases successives de même thème, c'est UN SEUL run, donc `isRunStart` n'est vrai qu'à la première et `runColor` est strictement identique sur toutes (même teinte, même alpha) → l'œil perçoit un bloc unique. Pour rendre le fil VISUELLEMENT continu malgré le `py-1` de chaque ligne, on garde `box-shadow: inset 3px 0 0 ${runColor}` (le `inset` couvre déjà top→bottom de la box, padding compris) et on RETIRE `border-top` qui était le seul élément créant une coupure horizontale. Le fil redevient un trait plein du haut de la 1re phrase au bas de la dernière. Aux extrémités, arrondi optionnel via `data-run-start`/`data-run-end` (CSS `border-top-left-radius`) pour signer début/fin du bloc sans casser le continu. Aucune régression d'interaction : `humanRuns` intact.
- **Rupture** : Au changement de thème, `runAt(displayRuns, s.index).start === s.index` n'est vrai qu'UNE fois (vrai début de bloc) : on y dessine un NŒUD discret. Implémentation : sur la phrase de début de run, une courte encoche horizontale en tête de rail (pseudo-élément `::before` positionné à gauche, ~6px de haut, teinte un cran plus contrastée) — soit une micro-rupture du fil (2px de vide puis reprise de la nouvelle teinte). On NE remet PAS le `border-top` horizontal (cause des hachures). La rupture « reprend du sens » car elle n'apparaît plus qu'aux vraies transitions thématiques (alignée sur le comportement déjà correct des juges via `coalesceRuns`) : voir un nœud = « ici le thème change », sans ambiguïté. La teinte du fil change aussi à ce point (canal redondant). `data-boundary={isRunStart || undefined}` conservé (test/AT) ; on ajoute `data-run-end={isRunEnd || undefined}`. Le nœud étant porté par la GÉOMÉTRIE (encoche) en plus de la teinte, il reste perceptible en daltonisme et faible contraste.
- **Provenance** : On lit la provenance via `anchorByIndex.get(s.index)` (accès O(1) à `validated`/`seededFrom`/`resolvedFrom`) et on calcule un état de fermeté : FERME si la phrase de tête est `validated===true` ou a un `resolvedFrom` (arbitrage adopté = ferme) ; SUGGÉRÉ si `seededFrom` non vide et `!validated`. Rendu SANS nouvelle couleur : on module la TEXTURE et l'opacité du MÊME fil de thème — (a) FERME = trait PLEIN, alpha plein (~0.7), 3px ; (b) SUGGÉRÉ = trait POINTILLÉ VERTICAL atténué, alpha réduit (~0.35). Le pointillé vertical se fait en CSS sur un fin pseudo-élément gauche (`background: repeating-linear-gradient(to bottom, color 0 4px, transparent 4px 8px)`), pas en box-shadow (qui est toujours plein) : pour le suggéré on bascule du `box-shadow inset` plein vers ce gradient répété. Couleur via `rgb(${hexToRgbChannels(getThemeToken(run.theme).color)} / alpha)`, zéro hex en dur. A11y « couleur jamais seule » : DEUX canaux non colorés — texture (plein vs pointillé) ET opacité/épaisseur — plus `data-provenance="firm|suggested"` et un `title`/`aria` (« Thème X — validé » vs « Thème X — suggéré, non validé »). En mode juge (`llmSource` ≠ human/compare) tout est SUGGÉRÉ par nature → fil pointillé atténué partout, cohérent. En mode compare, aucune provenance (le rail code l'accord) → aucun changement.
- **Forces** : Résout les TROIS problèmes d'un coup avec un seul canal repensé (le rail) : continuité, rupture signifiante, provenance — sans élément lourd qui concurrencerait badges/injustice/triage/réglette., Aligne enfin le mode HUMAIN sur le mode JUGE (tous deux via coalesceRuns) : cohérence inter-modes, frontière au seul changement de thème., Réutilise l'existant : coalesceRuns (lib/runs.ts) déjà présent et testé, anchorByIndex O(1), data-boundary/data-dashed déjà câblés. Faible surface de changement., A11y solide : rupture portée par géométrie (encoche) + teinte ; provenance portée par texture + opacité + data-attr + title → robuste au daltonisme et au faible contraste, jamais la couleur seule., humanRuns reste strictement perSentence → zéro risque pour la sélection multi-blocs, deriveBlocks, clauseRangeBetween et le voyant par phrase., Subtil et 'premium' : un fil continu lit comme un bloc thématique unique, esthétique d'éditeur de code (gutter), cohérent avec la charte sombre de l'atelier.
- **Faiblesses** : Le pointillé VERTICAL ne peut pas se faire en box-shadow inset (toujours plein) : il faut un pseudo-élément/gradient → un peu plus de CSS et un second chemin de rendu (plein vs pointillé) à maintenir., La continuité visuelle parfaite dépend de l'absence de gap entre lignes ; un margin/rounded/ring résiduel (-mx-2, rounded-md, ring sélectionné) peut laisser un micro-trou à corriger finement., Deux états de fermeté + cas resolvedFrom doivent rester LISIBLES sans devenir un code Morse : risque de sur-signalement si l'encoche de nœud et le pointillé de provenance se ressemblent — il faut des géométries franchement distinctes (encoche = horizontale courte ; provenance = rythme vertical)., L'encoche de nœud ajoute un détail à un rail de 3px : à très faible densité elle peut être manquée (mais la teinte change en redondance).
- **Risques d'impl.** : box-shadow inset NE pointille PAS et s'arrête au padding : garder inset plein pour le fil continu ; pour le suggéré et l'encoche passer par un ::before/gradient (left:0; top:0; bottom:0) — ne pas tenter de faire les deux avec le seul box-shadow., Continuité : retirer border-top (cause des hachures) ET vérifier qu'aucun gap vertical ne subsiste entre lignes (py-1, -mx-2, rounded-md, ring focus/sélection). Le fil doit être border-to-border ; tester sur 3+ phrases successives de même thème., NE PAS remplacer humanRuns : introduire displayRuns = coalesceRuns(humanRuns) uniquement pour runColor/isRunStart/isRunEnd/nœud. blocks/deriveBlocks/clauseRangeBetween/le voyant par phrase doivent continuer à consommer humanRuns (perSentence) — sinon la sélection multi-blocs casse., isRunEnd se calcule sur displayRuns (run.end === s.index), pas sur humanRuns ; attention au dernier run neutre et aux runs d'une seule phrase (start===end → nœud + fermeture sur la même ligne)., Mode compare : ne PAS appliquer provenance ni nœud thématique (rail = accord sem-success/sem-warning, showDashedTop déjà false) — garder le court-circuit isCompare AVANT le calcul de texture pour ne pas régresser., Provenance : resolvedFrom implique validated=true (ferme) — ne pas le classer en suggéré ; stripper 'preannotation:' seulement pour le label, pas pour le test de présence de seededFrom., Perf : coalesceRuns est O(n) et déjà mémoïsé pour les juges ; mémoïser displayRuns sur [humanRuns]. Lire la provenance via anchorByIndex dans le rowProps déjà construit, pas dans une boucle séparée., A11y/tests : conserver data-boundary ; le pointillé ne signifie plus 'début de run' mais 'suggéré' → mettre à jour les tests assis sur data-dashed=frontière et ajouter data-provenance + title.

### Double canal « Thème continu + Provenance liminaire » — 9/10
**Principe** : Séparer physiquement DEUX informations qui aujourd'hui se chevauchent sur la même arête gauche : (1) le SENS DU THÈME, porté par un rail vertical CONTINU de couleur métier (le canal « quoi »), et (2) le SENS DE L'ÉTAT/PROVENANCE, porté par un marqueur fin et discret en TÊTE de bloc (le canal « d'où »). Le rail ne dit plus jamais « début de phrase annotée » ni « validé/suggéré » : il dit uniquement « ce bloc parle du thème X, et il est continu tant que X ne change pas ». Toute l'information d'état migre vers un canal géométriquement distinct (le tout début du run coalescé), jamais sur l'arête elle-même. Concrètement, on introduit un jeu de runs d'AFFICHAGE dédié, `displayRuns = coalesceRuns(humanRuns)`, qui pilote `runColor` / `isRunStart` / `showDashedTop` du rail, SANS toucher `humanRuns` (qui reste perSentence pour la sélection/deriveBlocks/mapping). La provenance se lit en O(1) via `anchorByIndex.get(run.start)` sur l'ancre du PREMIER run du bloc.
- **Continuité** : Le rail devient continu en deux temps. (1) SOURCE : on remplace la source du rail par `displayRuns = useMemo(() => coalesceRuns(humanRuns), [humanRuns])` ; `runAt(displayRuns, s.index)` renvoie alors un seul run couvrant tout un bloc de même thème, donc `runColor` (= `rgb(${hexToRgbChannels(getThemeToken(run.theme).color)} / 0.5)`) est IDENTIQUE sur toutes les phrases successives du bloc, et `isRunStart = run.start === s.index` n'est vrai qu'à la première. (2) CONTINUITÉ VISUELLE du trait : le `box-shadow: inset 3px 0 0` reste dessiné par phrase, mais la coupure perçue vient du `py-1` + `-mx-2 px-2` et de l'arrondi `rounded-md` de chaque ligne. Pour souder le rail, on conditionne ces deux propriétés à la position dans le bloc via des data-attributes : on calcule `isRunStart` (déjà là), `isRunEnd = run.end === s.index`, et `inBlock = run.theme != null`. Au niveau CSS on neutralise l'arrondi du rail sur les jonctions internes — `data-rail-mid` (ni start ni end) et `data-rail-start`/`data-rail-end` pilotent un `rounded-tl-none`/`rounded-bl-none` sur le pseudo-bord gauche, et on supprime le `py-1` visuel du rail en le faisant déborder : plutôt que `inset 3px 0 0` posé sur une box à padding vertical, on dessine le rail via un `::before` absolu `left-0 top-0 bottom-0 w-[3px]` dont le `top/bottom` valent `-1px` (ou `0`) sur les lignes `data-rail-mid` et `data-rail-end` pour recouvrir le gap inter-lignes. Résultat : un trait vertical ininterrompu sur tout le bloc thématique. La couleur, l'alpha (0.5) et l'épaisseur (3px) restent strictement ceux d'aujourd'hui — zéro régression chromatique.
- **Rupture** : La rupture « reprend du sens » parce qu'avec `coalesceRuns`, `showDashedTop = showBoundaries && isRunStart && run.theme != null` n'est plus vrai qu'au VRAI changement de thème (première phrase d'un run dont le thème diffère du précédent), exactement comme pour les juges (alignement inter-modes recherché par la contrainte). On garde le `border-top: 1px dashed rgb(var(--surface-text-muted) / 0.3)` existant, mais on lui ajoute un second canal non coloré pour l'a11y : (a) un MICRO-ESPACE — `margin-top` de 2px sur `data-rail-start[data-theme-change]` — qui crée une césure géométrique perceptible même sans couleur ni pointillé ; (b) le rail lui-même se RÉAMORCE visuellement (coin supérieur gauche ré-arrondi `rounded-tl-md` via `data-rail-start`) alors qu'à l'intérieur du bloc il reste droit : l'œil lit « nouveau bloc » à la forme, pas seulement au pointillé. On expose `data-boundary` (déjà présent) qui désormais ne se déclenche QU'aux vrais changements — sa sémantique de test redevient juste. Le pointillé n'est donc plus du bruit (fini l'effet hachures entre phrases de même thème) : sa présence = sémantiquement « ici le thème change », ce qui restaure sa valeur de signal.
- **Provenance** : Provenance = canal SÉPARÉ, posé UNIQUEMENT en tête de bloc (sur `data-rail-start`), jamais sur l'arête du rail, pour ne pas mélanger « sens du thème » et « sens de l'état ». On lit l'ancre du début de run : `const head = anchorByIndex.get(run.start)`. Trois états, trois rendus minimalistes, chacun à DOUBLE codage (couleur + forme/texture, jamais la couleur seule) : (1) HUMAIN-FERME (`head.validated && !head.seededFrom`, ou `head.resolvedFrom`) → une petite PASTILLE PLEINE de 5px (`::after` sur la tête, `top-0 left-[-1px]`, `rounded-full`, fond `currentTheme/0.9`) = forme « point plein » + icône `✓` réutilisée dans le title ; le rail reste à alpha 0.5 PLEIN (ferme). (2) SUGGÉRÉ (`head.seededFrom && !head.validated`, préfixe `preannotation:` strippé) → PAS de pastille pleine mais un petit ANNEAU CREUX 5px (`rounded-full border bg-transparent`, `border-color: rgb(var(--surface-text-muted))`) + le segment de rail du bloc passe en POINTILLÉ vertical : on n'utilise plus `box-shadow inset` mais un `::before` avec `background-image: repeating-linear-gradient(to bottom, currentColor 0 3px, transparent 3px 6px)` teinté du thème → texture « tireté » = « pas encore ferme », perceptible en N&B et en daltonisme. (3) ARBITRAGE ADOPTÉ (`resolvedFrom`) → traité comme ferme (rail plein) + pastille pleine mais en forme de LOSANGE (rotate-45 d'un carré 5px) pour signer « provenance arbitrage » sans nouvelle couleur. Tous portent un `data-provenance="human|seeded|resolved"` + un `title` (« Validé », « Pré-rempli — à valider », « Arbitrage adopté · {Juge} ») pour l'AT et les tests. Le badge texte d'en-tête existant (l.999-1016) reste, mais le rail devient LISIBLE seul, d'un coup d'œil, sans lire le texte. En mode juge (`llmSource` = claude/codex/…), tout le rail est par nature SUGGESTION : on applique d'office la texture pointillée + anneau creux, ce qui unifie la sémantique « suggéré » entre pré-annotation humaine non validée et sélection LLM.
- **Forces** : Sépare proprement deux dimensions orthogonales (thème = couleur continue / état = marqueur liminaire) : aucune arête ne porte deux sens à la fois — c'est exactement l'objectif anti-ambiguïté., Réutilise `coalesceRuns` DÉJÀ existant et déjà éprouvé sur les juges → cohérence inter-modes immédiate et code partagé, faible surface de bug., `humanRuns` (perSentence) reste intact : sélection multi-blocs, `clauseRangeBetween`, `deriveBlocks`, mapping phrase→clause non touchés ; on ajoute seulement `displayRuns` en dérivé., Triple codage a11y (teinte + forme de pastille + texture plein/pointillé du rail + data-* + title) : robuste en daltonisme et à faible contraste, couleur jamais seule, pour la frontière ET la provenance., Subtil : pas de nouvelle couleur criarde ni de second élément lourd ; on ne fait que moduler opacité/texture/forme d'éléments déjà présents (rail, pointillé, micro-pastille de 5px), donc pas de concurrence avec badges/injustice/triage/réglette N-way., Restaure la valeur de signal du pointillé : `data-boundary` redevient sémantiquement « changement de thème », ce qui réaligne aussi les tests/AT., Le rail devient lisible SANS lire le badge texte : gain ergonomique direct pour l'annotateur qui balaie verticalement le document.
- **Faiblesses** : La continuité parfaite du trait exige de passer le rail de `box-shadow inset` à un pseudo-élément `::before` positionné (débordement vertical contrôlé) : refonte CSS locale non triviale, à tester pixel-près sur les jonctions (gap `py-1`, `rounded-md`)., La texture pointillée verticale (repeating-linear-gradient) sur un trait de 3px reste discrète : à très faible zoom elle peut se lire comme un trait plein un peu clair — le double codage par l'anneau creux/plein compense mais ce n'est pas redondant à 100% à toutes les tailles., Trois formes de pastille (point plein / anneau creux / losange) ajoutent un petit vocabulaire à apprendre ; nécessite une légende quelque part (tooltip ou aide) pour être pleinement explicite., La provenance n'est posée qu'en TÊTE de bloc : si un bloc coalescé mélange des phrases de provenances différentes (ex. première validée, suivantes pré-remplies de même thème), la tête ne reflète que la 1re phrase → perte d'information intra-bloc (voir risques)., Léger surcoût de lecture par phrase : on lit `anchorByIndex.get(run.start)` au lieu de rien, et on calcule `isRunEnd`/jonctions — négligeable mais non nul sur de longs documents.
- **Risques d'impl.** : BOX-SHADOW INSET PAR PHRASE : `inset 3px 0 0` est clippé par la box (et par `rounded-md`/`overflow`), donc il ne « déborde » jamais pour combler le gap `py-1` inter-lignes — la continuité parfaite EXIGE de migrer le rail vers un `::before` absolu (`top:-1px;bottom:-1px` sur les jonctions internes) ; tant qu'on reste en box-shadow, le trait restera subtilement segmenté. Garder un fallback box-shadow pour le cas neutre/triage (l.1500-1504) où il n'y a pas de bloc., COALESCE & ATTRIBUTION : `coalesceRuns` conserve le `localId`/ancre du PREMIER run ; donc `anchorByIndex.get(run.start)` cible bien la tête, MAIS la provenance des phrases internes du bloc est ignorée. Si un bloc coalescé agrège des provenances hétérogènes (validée + pré-remplies de même thème), il faut décider : soit ne PAS coalescer à travers une frontière de provenance (coalescer uniquement si même thème ET même classe de provenance — variante `coalesceRuns` enrichie), soit assumer la provenance de tête. La 1re option évite de masquer du « suggéré » sous un point « ferme »., MODE COMPARE : ne pas régresser l.821-829 — en `isCompare` le rail code l'accord (sem-success/sem-warning) et `showDashedTop=false`. Le canal provenance NE DOIT PAS s'activer en compare (la notion n'a pas de sens) : garder le marqueur provenance derrière `!isCompare`. Vérifier aussi que `displayRuns` n'est utilisé QUE pour le rail humain/juge, pas pour la logique d'accord., MODE JUGE : en `llmSource` juge, `runs = runsByJudge[llmSource]` (déjà coalescé) — appliquer la texture « suggéré » d'office sans relire `anchorByIndex` (qui pointe les drafts HUMAINS, pas le juge) sous peine de fausse provenance. Bien distinguer source humaine vs source juge avant de lire l'ancre., PERF : `displayRuns = coalesceRuns(humanRuns)` doit être `useMemo([humanRuns])` ; `runAt(displayRuns, i)` est un find linéaire par phrase → sur de longs docs préférer un index pré-calculé (ex. `runByIndex: (Run|undefined)[]`) comme c'est déjà fait pour byIndex ailleurs, sinon O(n·k)., A11Y/TOKENS : la texture pointillée et les pastilles doivent rester en `rgb(var(--surface-text-muted))` / `currentColor` dérivé du thème via hexToRgbChannels — zéro hex en dur ; le `repeating-linear-gradient` doit utiliser une couleur tokenisée. Conserver/étendre `data-boundary`, `data-dashed`, ajouter `data-provenance` et `data-rail-start/mid/end` pour les tests et l'AT., CSS JONCTIONS : neutraliser `rounded` du rail à l'intérieur du bloc sans casser le `rounded-md` de la LIGNE (focus ring, hover bg) — cibler le pseudo-élément du rail, pas la box ; attention au `ring-1`/`outline-dashed` (l.1492-1494) qui se superposent au rail gauche.

## 3. Analyse comparative
Les trois solutions partagent le MÊME socle correct et non négociable : un jeu de runs d'affichage dédié displayRuns = coalesceRuns(humanRuns), mémoïsé sur [humanRuns], qui ne remplace JAMAIS humanRuns (lequel reste perSentence pour clauseRangeBetween/deriveBlocks/blocks/mapping phrase->clause). Ce socle tue à lui seul les pointillés-partout et aligne le mode humain sur le mode juge (qui passe déjà par coalesceRuns l.257). La différence se joue sur trois axes : (1) continuité visuelle du trait, (2) codage de la rupture, (3) codage de la provenance.

CONTINUITÉ. Le rail actuel est un box-shadow inset 3px (l.1500). L'audit et les trois solutions convergent : box-shadow inset est clippé par la box (rounded-md, py-1) et ne peut NI déborder pour combler le gap inter-lignes NI faire des coins arrondis conditionnels haut/bas. capsules et double-canal tranchent franc : migrer le rail vers un ::before absolu (top/bottom débordants) — c'est la seule façon d'obtenir un trait réellement continu et des extrémités arrondies. trait-continu parie qu'il suffit de retirer border-top en gardant box-shadow inset ; c'est partiellement faux (le inset couvre le padding vertical d'UNE ligne mais le gap résiduel -mx-2/rounded-md/ring laisse des micro-trous, comme le reconnaît sa propre section Risques). Verdict : le ::before est obligatoire pour tenir l'objectif « rail continu ».

RUPTURE. trait-continu remplace le pointillé par un « nœud/encoche horizontale » sur le rail — élégant mais c'est un NOUVEAU vocabulaire géométrique de 6px à 3px de large, peu lisible à faible densité et qui risque de se confondre avec la texture de provenance (il l'admet). double-canal et capsules gardent l'idée plus sobre : la rupture = changement de teinte + ré-arrondi du coin supérieur (le rail « se réamorce ») + micro-espace de 2px. C'est trois signaux concordants au même endroit sans inventer de glyphe. double-canal conserve en plus le border-top dashed existant MAIS uniquement aux vrais changements (donc re-signifié, plus du bruit), ce qui préserve data-dashed et les tests existants à moindre coût.

PROVENANCE. capsules code ferme/suggéré par la TEXTURE du remplissage (plein vs hachure 45° repeating-linear-gradient) — risque de moiré sous-rétina/zoom (sa propre faiblesse), et la hachure sur 3px de large est presque invisible. trait-continu code par pointillé VERTICAL du fil + opacité — bon, mais collision possible avec le nœud de rupture. double-canal sépare PHYSIQUEMENT les deux sens : le rail ne porte QUE le thème (continu), la provenance migre sur un marqueur liminaire en TÊTE de bloc (pastille pleine = ferme / anneau creux = suggéré / losange = arbitrage). C'est conceptuellement le plus propre (anti-ambiguïté : une arête = un sens), mais introduit trois formes à apprendre (sa faiblesse) et surtout NE LIT QUE l'ancre de tête : un bloc coalescé mixte (1re phrase validée, suivantes pré-remplies) afficherait « ferme » à tort. capsules résout justement ce point avec une règle conservatrice de bloc (« suggéré si au moins une phrase non validée »).

GAGNANT : HYBRIDE à dominante double-canal, complété par les meilleures idées des deux autres. On retient de double-canal la séparation des sens (thème sur le rail / provenance en marqueur liminaire) et la conservation du border-top dashed re-signifié pour l'a11y et la compat tests. On retient de capsules la migration vers ::before + chevauchement -1px (continuité réelle) ET surtout la règle de provenance de BLOC (scan des phrases du run, statut conservateur), qui corrige le défaut majeur de double-canal (provenance de tête trompeuse sur bloc mixte). On écarte le « nœud/encoche » de trait-continu (vocabulaire en trop) et la hachure 45° de capsules (moiré + illisible sur 3px), au profit d'un codage provenance double : opacité/épaisseur du rail (ferme=plein 0.5/3px, suggéré=atténué ~0.3/2px) + un marqueur de tête sobre à DEUX formes seulement (point plein = ferme, anneau creux = suggéré ; l'arbitrage resolvedFrom est traité comme ferme, distingué par le title, pas par une 3e forme). C'est le meilleur compromis subtilité / robustesse a11y / non-régression.

## 4. Proposition finale
Rail thématique CONTINU (canal « quoi ») + provenance LIMINAIRE (canal « d'où »), pilotés par un jeu de runs d'affichage coalescé dédié.

SOURCE. displayRuns = useMemo(() => coalesceRuns(humanRuns), [humanRuns]). humanRuns reste perSentence et reste l'unique source de blocks/deriveBlocks/clauseRangeBetween/selectClause/voyant par phrase. Le rail consomme run = runAt(displayRuns, s.index) ; on calcule isRunStart = run.start === s.index, isRunEnd = run.end === s.index, isMid = !isRunStart && !isRunEnd. En mode juge (llmSource = claude/codex/…), runs = runsByJudge[llmSource] déjà coalescé (inchangé).

CONTINUITÉ. Le rail migre de box-shadow inset vers un pseudo-élément ::before absolu (left:0; width:3px; background: var(--rail-color)), posé sur la ligne .relative existante. Pour souder par-dessus py-1/-mx-2/rounded-md, le ::before déborde de -1px en haut quand isMid||isRunEnd et de -1px en bas quand isMid||isRunStart ; aux frontières de thème (et aux bornes du document) le débordement est coupé. border-top-left/bottom-left-radius = 3px uniquement aux extrémités du run (isRunStart en haut, isRunEnd en bas), 0 au milieu. Couleur identique sur tout le run (même run.theme) -> l'œil lit UN bloc.

RUPTURE. Au seul vrai changement de thème (isRunStart sur displayRuns), trois signaux concordants : (a) la teinte du rail change ; (b) le coin supérieur du rail se ré-arrondit ; (c) on conserve border-top: 1px dashed rgb(var(--surface-text-muted) / 0.3) — mais désormais il n'apparaît qu'aux vrais changements (showDashedTop = showBoundaries && isRunStart && run.theme != null, inchangé en formule mais devenu rare grâce à la coalescence). data-boundary = isRunStart et data-dashed = showDashedTop restent émis (compat tests/AT). On ajoute un micro-margin-top de 2px sur la jonction de thème pour une césure géométrique perceptible sans couleur.

PROVENANCE (canal séparé, jamais sur l'arête). Statut de BLOC calculé via un helper pur runProvenance(run, drafts/anchorByIndex) qui scanne les phrases [run.start, run.end] : 'firm' si TOUTES les phrases couvertes sont validated===true ou resolvedFrom!=null ; 'suggested' dès qu'UNE phrase a seededFrom && !validated (règle conservatrice — on ne sur-affirme jamais « validé »). Double codage :
- Rail : FERME = alpha 0.5, 3px, trait net. SUGGÉRÉ = alpha ~0.3, 2px (rail plus fin et atténué) — variation d'opacité ET d'épaisseur, deux canaux non chromatiques.
- Marqueur liminaire (sur isRunStart seulement, !isCompare) : un ::after de 5px en tête de rail. FERME = point PLEIN (rounded-full, fond teinte du thème /0.9). SUGGÉRÉ = ANNEAU CREUX (border 1px var(--surface-text-muted), fond transparent). resolvedFrom -> traité comme ferme (point plein) ; sa nature d'arbitrage est portée par data-provenance="resolved" + title « Arbitrage adopté · {Juge} », PAS par une 3e forme (on ne surcharge pas).
Chaque phrase porte data-provenance="firm|suggested" + un title/aria (« Thème X — validé » / « Thème X — suggéré, non validé »). En mode JUGE, tout le rail est par nature suggestion -> rail atténué + anneau creux d'office, sans relire anchorByIndex (qui pointe les drafts HUMAINS).

COULEURS / TOKENS. var(--rail-color) posée inline = rgb(${hexToRgbChannels(getThemeToken(run.theme).color)} / a) avec a ∈ {0.5 ferme, 0.3 suggéré}. Pointillé/anneau/césure = rgb(var(--surface-text-muted) / 0.3). Accord compare = var(--sem-success)/var(--sem-warning). ZÉRO hex en dur.

A11Y. Rupture portée par 3 canaux (teinte + arrondi + dashed/césure géométrique). Provenance portée par 3 canaux non-chromatiques (opacité, épaisseur, forme du marqueur plein/creux) + data-provenance + title. Couleur jamais seule, lisible en daltonisme et faible contraste.

MODE COMPARE (isCompare). Aucune régression : displayRuns N'EST PAS utilisé pour l'accord ; le rail code l'accord (sem-success/sem-warning, l.821-827), showDashedTop = false, AUCUN marqueur de provenance émis (garde derrière !isCompare), chaque phrase = sa micro-capsule d'accord (tous coins arrondis). Le court-circuit isCompare reste AVANT le calcul de provenance.

### Décisions de design
- **Rail continu (trait soudé)** : Migrer le rail de box-shadow:inset 3px vers un ::before absolu (left:0;width:3px;top:0;bottom:0). Débordement -1px haut/bas sur les jonctions INTERNES du run (isMid||isRunEnd en haut, isMid||isRunStart en bas) pour recouvrir le gap py-1/-mx-2/rounded-md ; débordement coupé aux frontières de thème et aux bornes du document. Couleur identique sur tout le run. Conserver le box-shadow inset 2px UNIQUEMENT comme fallback du liseré de triage (cas sans thème, l.1500-1504).
- **Rupture (changement de thème)** : isRunStart calculé sur displayRuns coalescé -> vrai uniquement au vrai changement. 3 signaux concordants : changement de teinte + ré-arrondi du coin supérieur du rail (border-top-left-radius 3px seulement si isRunStart) + border-top dashed rgb(var(--surface-text-muted)/0.3) CONSERVÉ mais rare + margin-top 2px de césure. data-boundary=isRunStart et data-dashed=showDashedTop maintenus pour tests/AT.
- **Provenance humain vs LLM/suggéré** : Statut de BLOC conservateur via helper pur scannant [run.start,run.end] : 'firm' si toutes validated||resolvedFrom, 'suggested' si une seule seededFrom&&!validated. Codage rail : ferme=alpha 0.5/3px, suggéré=alpha 0.3/2px.
