# Annexe — détail intégral des 15 options analysées

> Matière brute de l'étude (workflow multi-agents). Voir la synthèse dans `01_etude_design.md`.


## Stockage des préférences UI/atelier par COMPTE (persistance multi-appareils, versionnage, latence, hors-ligne, cohérence) pour Pactiva

### A — localStorage par utilisateur (clé namespacée par user id), 100% client

Étendre la persistance client existante : préfixer les clés zustand par l'id du compte (claire.ui::<uid>, claire.workspace.prefs::<uid>, claire.workspace.layout::<uid>). On ajoute un store persist dédié aux prefs d'atelier (showUnfairness, ghostJudges, displayLang, llmSource, prefilledJudge, autoPrefillModel) et init()/reset() lisent ces prefs au lieu de réinitialiser en dur. Aucun changement backend.

**Forces** : Coût quasi nul : prolonge le pattern useUiStore déjà en place (zustand persist, claire.ui) et claire.workspace.layout — zéro migration Django, zéro endpoint, zéro round-trip réseau ; Latence nulle au chargement : hydratation synchrone localStorage, donc init() applique les overlays AVANT le premier rendu du document (pas de flash de reconfiguration) ; Hors-ligne natif et simple ; respecte les contraintes front (pas de payload réseau donc pas de souci camelCase, tokens/zéro hex non concernés)

**Faiblesses** : NE répond PAS au besoin verbatim « suivre le COMPTE / multi-appareils » : les prefs restent collées au navigateur, perdues sur un autre poste ou après vidage du cache (or l'équipe prod a 3 comptes potentiellement multi-postes) ; Fuite inter-comptes si on néglige le namespacing : sans purge au logout, le compte B hérite des overlays du compte A sur un poste partagé (risque réel sur postes mutualisés) ; Versionnage de schéma à gérer à la main par store et aucune source de vérité serveur pour auditer/réinitialiser

**Pertinence** : Satisfait le « ne pas reconfigurer à chaque ouverture » et l'auto-prefill sans flash, mais échoue sur l'exigence explicite « par COMPTE / multi-appareils ». Convient comme socle minimal ou fallback hors-ligne, pas comme réponse complète au besoin.

### B — Champ JSON serveur + endpoint /me/preferences (source de vérité serveur)

Ajouter User.preferences = models.JSONField(default=dict) + endpoint GET/PATCH /api/v1/me/preferences (ou exposer preferences dans UserSerializer + ProfileUpdateSerializer). Le front charge les prefs après /me, hydrate useUiStore et un nouveau store de prefs d'atelier ; chaque toggle PATCH (débounce). Schéma versionné par clé schemaVersion dans le JSON, migration côté serveur.

**Forces** : Répond EXACTEMENT au besoin : prefs attachées au COMPTE, multi-appareils, survivent au cache et au changement de poste — aligné sur l'équipe prod 3 comptes ; Source de vérité unique, auditable et réinitialisable côté admin ; versionnage/migration centralisés (un seul schemaVersion, pas N localStorage divergents) ; camelCase déjà géré globalement par djangorestframework-camel-case (autoPrefillModel, displayLang…) ; réutilise l'auth JWT et le pattern MeView/ProfileUpdateSerializer existant

**Faiblesses** : Latence + flash : /me est asynchrone (sondé après auth dans providers.tsx) ; sans cache local, le document peut rendre avec les défauts en dur puis se reconfigurer (flash d'overlays) — gênant pour l'auto-prefill à l'ouverture ; Hors-ligne dégradé et risque d'écrasement : PATCH par toggle = chatter réseau, conflits last-write-wins entre onglets/appareils, perte des derniers réglages si offline ; Travail backend non trivial : migration JSONField, validation/whitelist du payload (éviter d'accepter un JSON arbitraire), tests contractuels

**Pertinence** : Répond pleinement au volet « par compte / multi-appareils » mais dégrade l'expérience « pas de reconfiguration à l'ouverture » (flash, latence). Correct fonctionnellement, sous-optimal en UX sans cache client.

### C — Hybride : cache localStorage par compte + sync serveur /me/preferences (offline-first, write-through)

Garder le store zustand persist (clé namespacée par uid) comme cache d'hydratation instantanée, ET le champ JSON serveur (option B) comme source de vérité. Au login : hydrater depuis localStorage (rendu immédiat) puis réconcilier avec GET /me/preferences (le serveur gagne, via schemaVersion+updatedAt). Les toggles écrivent localStorage immédiatement et PATCH le serveur en débounce (write-through). Migration de schéma centralisée serveur, repli client si offline.

**Forces** : Cumule le meilleur : suit le COMPTE/multi-appareils (serveur) SANS latence ni flash (hydratation localStorage synchrone) — l'auto-prefill s'applique dès le premier rendu du nouveau document ; Robuste hors-ligne (cache local autoritaire tant que le réseau manque) et résilient (PATCH débounce + réconciliation updatedAt évite la perte et borne l'écrasement, dans l'esprit de l'autosave/flush() existant) ; Réutilise tout l'existant : zustand persist + claire.ui + claire.workspace.layout côté client, MeView/JWT + camelCase côté serveur ; le namespacing par uid règle aussi la fuite inter-comptes des postes partagés

**Faiblesses** : Le plus de code : deux chemins (cache + serveur), logique de réconciliation/conflit (updatedAt, schemaVersion) et purge au logout à tester sérieusement ; Versionnage à tenir des DEUX côtés (migration localStorage zustand ET migration JSON serveur) — surface de bugs si les schémas dérivent ; Sur-dimensionné pour un MVP si le multi-appareils n'est pas exigé immédiatement

**Pertinence** : Seule option qui satisfait l'INTÉGRALITÉ du verbatim (par compte + multi-appareils + pas de reconfiguration/flash + auto-prefill à l'ouverture) tout en restant homogène à l'architecture Pactiva existante. Complexité maîtrisée par un phasage.


**➜ Recommandation : C — Hybride : cache localStorage par compte + sync serveur /me/preferences (offline-first, write-through)**


> Le besoin verbatim impose deux exigences en tension qu'aucune approche unique ne couvre : « suivre le COMPTE (idéalement multi-appareils) » (qui exige le serveur, option B) ET « ne pas reconfigurer / auto-prefill dès l'ouverture du document » (qui exige une hydratation synchrone sans flash, donc le client, option A). L'option B seule introduit un flash d'overlays car /me est asynchrone (sondé après auth dans providers.tsx) et init() applique aujourd'hui des défauts en dur (showUnfairness:true, displayLang:'orig', prefilledJudge:null) — l'auto-prefill « à l'ouverture » se déclencherait après un premier rendu non configuré. L'option A seule trahit le « par compte / multi-appareils ». L'hybride résout les deux et s'appuie sur des briques DÉJÀ présentes et éprouvées : zustand persist (claire.ui), claire.workspace.layout, MeView+JWT, et la conversion camelCase globale (djangorestframework-camel-case) pour des clés comme autoPrefillModel/displayLang. Mise en œuvre concrète et bornée : (1) backend — User.preferences = JSONField(default=dict) + GET/PATCH /api/v1/me/preferences validant un schéma whitelisté et versionné (schemaVersion), pas un JSON arbitraire ; (2) front — un store de prefs d'atelier (zustand persist, clé namespacée ::<uid>) qui alimente init()/reset() au lieu des défauts en dur, write-through localStorage immédiat + PATCH débounce, réconciliation au login par updatedAt (le serveur gagne). Phasage pragmatique pour ne pas payer la complexité d'un coup : livrer d'abord le cache local namespacé par uid (valeur immédiate, zéro flash, corrige aussi la fuite inter-comptes sur postes mutualisés), puis brancher la sync serveur — le contrat de prefs et schemaVersion étant figés dès le départ pour éviter toute divergence de schéma. C'est la seule option qui satisfait l'intégralité du verbatim tout en restant homogène à l'architecture Pactiva (fichiers ancrés : frontend/src/store/ui.ts, frontend/src/store/workspace.ts, frontend/src/components/workspace/ResizablePanels.tsx, frontend/src/lib/api/endpoints.ts, backend/claire/accounts/views.py + serializers.py + models.py).


## Périmètre & schéma des préférences (quoi persister par compte, sous quelle forme, granularité, défauts, robustesse à l'évolution des juges)

### A. Bloc UI unique versionné, fusionné aux défauts (un seul objet uiPrefs côté serveur + miroir localStorage)

Un seul objet camelCase `uiPrefs` v1 stocké sur le compte (champ JSON `ui_preferences` sur User, exposé via MeView GET/PATCH). Sections internes : `layout` (sidebarCollapsed, inspectorOpen, density, readingZoom, readingWide, largeurs colonnes ex-`claire.workspace.layout`), `overlays` (showUnfairness, showBoundaries, showTriageLevels, showQuickActions, displayLang, llmSource), `panels` (history/comments/triage ouverts par défaut), `prefill` ({enabled, model, asked}), `ghostJudges` en map id→bool. Lecture = `mergeDeep(DEFAULTS, prefs)` ; écriture = PATCH partiel débounced. Granularité GLOBALE (par compte, pas par projet).

**Forces** : Réutilise l'infra existante (MeView PATCH partiel, ProfileUpdateSerializer, camelCase auto) — un seul champ JSON, une migration triviale ; Fusion `mergeDeep(DEFAULTS, prefs)` rend tout champ absent/inconnu inoffensif : robuste à l'évolution du schéma de juges (ghostJudges/prefill.model sont juste des chaînes d'id, jamais des enums figées) ; Un seul aller-retour réseau, un seul point de vérité ; le localStorage `claire.ui` devient un simple cache de démarrage (anti-flash) hydraté par le serveur ; Couvre le besoin verbatim en entier : overlays atelier (aujourd'hui réinitialisés par init()) ET layout ET panneaux ET auto-prefill, le tout par compte donc cross-navigateur

**Faiblesses** : init() du store workspace DOIT cesser de hard-réinitialiser overlays/displayLang/llmSource : il faut le faire lire depuis uiPrefs (refactor ciblé mais réel des lignes 463-485 de workspace.ts) ; Un seul gros blob = pas de granularité par-projet (si un jour on veut llmSource différent par campagne, il faudra ré-encadrer) ; Versionner le schéma (`v:1`) impose une discipline de migration douce côté front pour les renommages de clés

**Pertinence** : Très forte. C'est l'option la plus alignée sur l'existant : MeView fait déjà GET/PATCH partiel, djangorestframework-camel-case gère la conversion, et un champ JSON unique évite N colonnes. La fusion aux défauts neutralise le risque "modèle per-phrase / juges qui évoluent" car prefill.model et ghostJudges restent des id libres. Le seul vrai coût est de débrancher la réinitialisation dans init().

### B. Deux étages : useUiStore (localStorage, déjà là) étendu pour le layout + bloc serveur réservé à l'atelier & auto-prefill

On garde `useUiStore` (persist localStorage `claire.ui`) comme source des préférences PUREMENT visuelles/poste (theme, density, sidebar, inspectorOpen, zoom, largeurs) et on l'étend pour absorber les overlays atelier visuels. On crée un PETIT bloc serveur `workspacePrefs` limité à ce qui doit suivre le compte cross-poste : `prefill {enabled, model, asked}`, `displayLang`, `llmSource`, `defaultPanels`. Le store workspace lit ce bloc à l'init au lieu de hard-coder.

**Forces** : Effort minimal : la partie layout/visuelle reste 100% sur l'infra zustand-persist déjà en prod, zéro backend pour elle ; Le payload serveur est minuscule (juste prefill + 3 prefs atelier) → patch rapide, peu de surface de bug ; Sépare clairement "préférence de poste" (theme, largeurs d'écran) de "préférence de compte" (auto-prefill, langue) — défendable UX

**Faiblesses** : Contredit le besoin verbatim : l'utilisateur veut TOUT par compte ("dispositions de navbar et leurs états") ; laisser sidebar/inspector/largeurs en localStorage = ils ne suivent PAS l'utilisateur d'un poste à l'autre ; Deux sources de vérité (localStorage + serveur) → règles de préséance à arbitrer, risque de divergence et de logique de merge éparpillée ; Frontière "poste vs compte" est arbitraire et fragile : un overlay comme showUnfairness est-il visuel (local) ou métier (compte) ? Débat sans fin

**Pertinence** : Moyenne. Pragmatique et peu risquée techniquement, mais en tension directe avec le besoin ("sauvegarder PAR COMPTE"). Convient si l'on accepte explicitement que le layout d'écran reste lié au navigateur ; sinon elle ne résout qu'à moitié la douleur de reconfiguration et introduit une double source de vérité.

### C. Tables relationnelles normalisées (UserPreference clé/valeur + UserJudgePref par juge) avec granularité optionnelle par-projet

Modèle backend normalisé : table `UserPreference(user, scope, key, value)` où `scope` ∈ {global, project:<id>} pour clés scalaires (inspectorOpen, displayLang, llmSource, prefillEnabled, prefillModel, prefillAsked…), et `UserJudgePref(user, judge_id, ghost_visible)` pour la map de juges. Endpoints dédiés (GET/PUT /api/v1/me/preferences?scope=...). Le front compose un objet effectif (project override > global > défaut).

**Forces** : Granularité par-projet native (scope) : un annotateur peut vouloir llmSource=mistral sur une campagne et human sur une autre — répond à un besoin futur plausible sur une plateforme de campagnes ; Requêtable/auditables : on peut faire des stats serveur (combien d'annotateurs activent l'auto-prefill, sur quel modèle) sans parser un blob JSON ; Les juges en table dédiée s'alignent proprement sur le caractère N-modèles (un row par juge, FK douce sur l'id de juge)

**Faiblesses** : Sur-ingénierie nette vs le besoin actuel (global suffit) : 2 nouveaux modèles, migrations, serializers, endpoints, invalidation de cache, tests — pour un gain de granularité non demandé ; N'utilise PAS le MeView existant (GET/PATCH /me) → nouvelle surface d'API, plus de couplage front/back, plus de risques de régression sur un produit déjà en prod ; La composition project>global>défaut côté front est une logique non triviale à tester ; et le clé/valeur typé faiblement (value en texte) rend le contrat moins sûr que le JSON camelCasé bout-en-bout

**Pertinence** : Faible à court terme. Techniquement la plus "propre" pour un besoin de granularité par-projet et d'analytics, mais le verbatim ne demande que du par-compte global et l'existant (MeView + un champ JSON) couvre déjà ça à coût quasi nul. À garder en réserve si la granularité par-campagne devient un vrai besoin produit.


**➜ Recommandation : A. Bloc UI unique versionné, fusionné aux défauts**


> C'est l'option qui colle le mieux au besoin verbatim (TOUT par compte, plus de reconfiguration à chaque doc) tout en s'appuyant sur l'infra déjà en prod : MeView fait déjà GET/PATCH partiel et djangorestframework-camel-case convertit automatiquement, donc un seul champ JSON `ui_preferences` sur User suffit (migration triviale, zéro nouvel endpoint). Le pattern `mergeDeep(DEFAULTS, prefs)` à la lecture est la clé de la robustesse demandée : tout champ absent retombe sur le défaut, et comme `prefill.model` et `ghostJudges` sont des id de juge LIBRES (jamais des enums figées côté schéma), l'ajout/retrait d'un modèle (Mistral 22→47, futurs juges) n'invalide jamais les préférences stockées — parfaitement compatible avec le modèle per-phrase et N-modèles. Le `localStorage "claire.ui"` existant est conservé comme cache anti-flash hydraté par le serveur, et le seul refactor réel est ciblé : faire lire à `init()` (workspace.ts L463-485) les overlays/displayLang/llmSource depuis uiPrefs au lieu de les hard-réinitialiser. L'option B laisse le layout prisonnier du navigateur (contredit "par compte") et crée une double source de vérité ; l'option C est une sur-ingénierie (granularité par-projet non demandée) qui abandonne MeView et multiplie la surface d'API sur un produit déjà en prod. Pour l'auto-prefill, le sous-objet `prefill {enabled, model, asked}` porte exactement les trois états du besoin (proposer à la 1ʳᵉ exécution via `asked=false`, mémoriser le choix, et garder un switch ergonomique ensuite), sans toucher au schéma de juges.


## UX auto-prefill : première demande de consentement + bascule (switch/icône) pour (ré)activer l'auto-exécution du pré-remplissage à l'ouverture d'un document vierge, sur un modèle choisi

### Option A — Modale de consentement post-action + switch inline dans le radiogroup Pré-remplir

À la 1ère exécution manuelle réussie de requestPrefill(judge) (WorkspaceToolbar.tsx:115), une petite modale (réutiliser le pattern du dialog d'écrasement, lignes 455-497) demande « Auto-exécuter <Modèle> à chaque nouveau document ? » Oui → on persiste autoPrefill={enabled:true, judge}. Non → rien, mais un switch/icône discret (Zap lucide) apparaît dans le radiogroup à droite du sélecteur (lignes 247-279), aria-pressed, classes tokens (bg-accent/15 actif, text-ink-muted inactif). L'auto-exécution se branche dans l'effet init (AnnotationWorkspace.tsx:114) : si autoPrefill.enabled ET draftClauses.length===0 (vierge) ET pré-annotation du modèle dispo ET !readOnly, on appelle setPrefill(judge) une fois. Changer de modèle via le radiogroup met à jour autoPrefill.judge ; cliquer le switch off désactive.

**Forces** : Réutilise un pattern déjà présent et testé (le dialog d'écrasement) — coût d'implémentation et de revue faible, homogène visuellement ; La demande arrive APRÈS une action volontaire et réussie : intention claire, pas d'interruption à froid ; Le switch est placé exactement là où l'utilisateur configure déjà le prefill (radiogroup ligne 247) — découvrabilité maximale, modèle courant explicite ; Garde anti-écrasement naturelle : auto-exécution gated sur draftClauses.length===0, donc seuls les docs vierges sont touchés ; jamais d'écrasement d'une annotation existante ; Model-aware sans dette : la persistance stocke judge, et le rendu doit passer par llmJudgeLabel() (corrige au passage le label en dur claude/codex ligne 464 qui ignore Mistral)

**Faiblesses** : Une modale de plus dans un atelier déjà dense en dialogs (écrasement, soumission, succès) — risque de fatigue si mal cadencée ; à ne déclencher qu'UNE fois (drapeau autoPrefillAsked persistant) ; Si la préférence est persistée seulement dans useUiStore (localStorage claire.ui), elle reste PAR NAVIGATEUR — contredit le besoin « par compte » ; il faut étendre MeView/User preferences pour être réellement per-account ; Le switch ajoute un 6e contrôle au radiogroup déjà large (Aucun + 3 modèles) — surcharge visuelle à surveiller sur petits écrans (flex-wrap)

**Pertinence** : Très forte : épouse l'existant (requestPrefill, dialog réutilisable, effet init comme hook d'ouverture, radiogroup comme ancre du switch), respecte tokens/zéro hex et le modèle per-phrase (setPrefill déplie déjà par phrase). Le point dur reste la cible de persistance (localStorage vs backend) à trancher pour honorer le « par compte ».

### Option B — Bandeau/inline-prompt non bloquant sous la toolbar + icône-switch dédiée près du sélecteur

Pas de modale : à la 1ère exécution manuelle, un bandeau discret non bloquant s'insère (region aria-live polie) juste sous le radiogroup avec « Toujours pré-remplir avec <Modèle> à l'ouverture ? [Activer] [Non merci] ». Réponse mémorisée (autoPrefillAsked + autoPrefill). En cas de refus, l'icône-switch (Zap/ToggleLeft) reste visible en permanence dans la toolbar, à côté du sélecteur, avec tooltip « Auto-pré-remplissage : off ». Auto-exécution branchée dans l'effet init comme en A (gated vierge + modèle dispo + !readOnly). Changement de modèle = re-sélection dans le radiogroup ; l'icône reflète enabled/judge.

**Forces** : Zéro interruption : un bandeau inline ne vole pas le focus ni ne bloque l'écran — meilleur pour un flux d'annotation rapide au clavier (j/k, shortcuts) ; Icône-switch toujours présente : la (ré)activation ultérieure est triviale et découvrable, conforme au besoin « petit icône/switch ergonomique bien placé » ; aria-live polie : annonce accessible sans dialog modal à piéger au clavier ; Mêmes garanties anti-écrasement que A (gate vierge dans l'effet init)

**Faiblesses** : Un prompt non bloquant est plus facile à ignorer/rater — le consentement peut ne jamais être donné, laissant la fonctionnalité sous-utilisée ; Insérer un bandeau sous la toolbar déplace le layout (3 panneaux redimensionnables juste dessous) — risque de saut visuel ; à gérer en overlay absolu plutôt qu'en flux ; Deux états visuels permanents nouveaux (bandeau transitoire + icône) à designer pour rester homogènes ; plus de surface UI à maintenir/tester ; Même problème de persistance per-account que A si on s'arrête à localStorage

**Pertinence** : Forte : très respectueux du flux d'annotation et du besoin d'un switch permanent ergonomique. Légèrement plus risqué côté layout (les panneaux sont juste sous la toolbar) et côté taux de consentement (prompt esquivable). Compatible tokens, camelCase, per-phrase.

### Option C — Tout-réglage dans un panneau Préférences (compte) + simple toggle contextuel, sans modale de 1ère fois

On abandonne la « 1ère demande » au profit d'un réglage explicite : une section « Pré-annotation automatique » dans un panneau Préférences (page compte / MeView étendu) avec switch on/off + sélecteur de modèle (Aucun/Claude/Codex/Mistral via LLM_JUDGES). Dans la toolbar, un seul petit toggle-icône miroir près du radiogroup (lié à la même préférence) pour activer/désactiver vite. L'auto-exécution se branche dans l'effet init (gate vierge + modèle dispo + !readOnly). Persistance directement côté serveur (champ preferences JSON sur User, exposé par MeView GET/PATCH).

**Forces** : Persistance NATIVEMENT per-account : on étend MeView/User.preferences, donc la préférence suit le compte sur tout navigateur — répond littéralement au besoin « par compte » ; Source de vérité unique et auditable des préférences (cohérent avec une éventuelle persistance serveur des autres réglages d'atelier non persistés aujourd'hui) ; Pas de modale intrusive ; le toggle toolbar reste pour l'accès rapide — UX calme ; Évite la complexité du « moment exact » de la 1ère demande et le drapeau autoPrefillAsked

**Faiblesses** : Contredit une exigence explicite du besoin : « À la PREMIÈRE exécution manuelle, DEMANDER si on veut l'auto-exécution » — C supprime ce moment de découverte contextuel ; Découvrabilité faible : un réglage enfoui dans un panneau compte sera rarement trouvé ; l'utilisateur risque de ne jamais activer l'auto-prefill ; Plus de travail backend immédiat (migration User.preferences + sérialiseur camelCase + UI panneau) avant tout bénéfice visible ; Le sélecteur de modèle est dédoublé (panneau + radiogroup toolbar) : risque d'incohérence d'état à synchroniser

**Pertinence** : Moyenne : excellente sur la persistance per-account (le vrai point dur), mais en contradiction frontale avec l'exigence de demande contextuelle à la 1ère exécution et faible en découvrabilité. Bon comme SOCLE de persistance à combiner avec A/B, pas comme UX d'amorçage à lui seul.


**➜ Recommandation : Option A — Modale de consentement post-action + switch inline dans le radiogroup Pré-remplir**


> A est la seule option qui satisfait littéralement l'exigence (« à la 1ère exécution manuelle, DEMANDER ») tout en minimisant le risque et le coût, parce qu'elle se greffe sur des points d'ancrage qui EXISTENT déjà et sont testés : requestPrefill(judge) (WorkspaceToolbar.tsx:115) est le moment naturel pour déclencher la demande, le dialog d'écrasement (lignes 455-497) fournit un pattern de modale réutilisable et homogène (tokens, zéro hex), le radiogroup « Pré-remplir » (lignes 247-279) est l'emplacement évident pour le switch/icône de (ré)activation, et l'effet init (AnnotationWorkspace.tsx:114, keyé sur annId/docId) est le hook canonique d'« ouverture de document » pour brancher l'auto-exécution. Les garde-fous demandés tombent naturellement : on gate l'auto-exécution sur draftClauses.length===0 (ne toucher QUE les docs vierges, jamais d'écrasement), sur la disponibilité de la pré-annotation du modèle (availableJudges, déjà calculé ligne 229) et sur !readOnly ; le changement de modèle passe par le radiogroup existant et met à jour la préférence ; la désactivation est un clic sur le switch. Deux conditions de réalisation à acter : (1) la préférence et le drapeau « déjà demandé » doivent être persistés PAR COMPTE — donc via une extension de MeView/User.preferences (le besoin dit explicitement « par compte »), useUiStore/localStorage ne servant que de cache optimiste, sinon on retombe sur du per-navigateur ; (2) tout libellé de modèle doit passer par llmJudgeLabel() pour rester N-modèles, ce qui corrige au passage le label en dur claude/codex de la modale d'écrasement (ligne 464) qui ignore Mistral. On peut donc emprunter le SOCLE de persistance de l'option C (champ preferences serveur) sans renoncer à l'amorçage contextuel de A — c'est le meilleur compromis besoin/existant/contraintes.


## Application & feedback de sync des préférences UI par compte (chargement sans flash, moment de sauvegarde, indicateur « enregistré », bouton réinitialiser, source de vérité localStorage vs serveur, cohabitation avec workspace.init() qui réinitialise l'atelier à chaque document)

### A — localStorage-first, serveur en miroir paresseux (push/pull réconciliés)

localStorage reste la source de vérité immédiate (zustand persist actuel, hydratation synchrone = zéro flash). On AJOUTE un champ JSON `prefs` (camelCase) sur User via `/api/v1/me` ; au login on fait un pull one-shot (réconciliation `updatedAt` le plus récent gagne) qui réhydrate les stores, et chaque mutation de pref déclenche un PATCH /me debouncé (~800 ms). init() de l'atelier n'écrit plus de valeurs en dur pour displayLang/llmSource/showUnfairness/ghostJudges/prefilledJudge : il LIT ces défauts depuis le store de prefs (nouveau slice persisté).

**Forces** : Zéro flash garanti : on garde l'hydratation synchrone localStorage de useUiStore (claire.ui) déjà en place — rien à réécrire pour le shell ; Fonctionne hors-ligne et sans latence : l'UI ne bloque jamais sur le réseau, le serveur n'est qu'un miroir de portabilité inter-navigateurs ; Coût backend minimal : un seul champ `prefs` JSON + extension de ProfileUpdateSerializer/UserSerializer, réutilise l'endpoint /me et la pipeline camelCase existante ; Indicateur « enregistré » trivial à brancher sur le même modèle que SaveIndicator (saving/saved/idle) déjà éprouvé dans la toolbar

**Faiblesses** : Réconciliation multi-appareils par horodatage = dernier écrivain gagne, donc perte silencieuse possible si deux navigateurs modifient en parallèle ; Deux sources persistées (localStorage + serveur) à garder cohérentes : risque de divergence si le pull au login est raté/erreur réseau ; Il faut introduire un nouveau slice de prefs et débrancher les valeurs en dur de init() — touche le cœur de l'atelier (zone sensible aux pertes de données)

**Pertinence** : Très bonne adéquation : capitalise sur l'existant (zustand persist claire.ui, /me camelCase, SaveIndicator) et résout directement le besoin « par compte » via le pull au login, tout en éliminant le reset par document en sourçant les défauts atelier depuis les prefs. Respecte tokens/zéro hex (purement état). Le champ JSON `prefs` reste compatible per-phrase (le prefilledJudge auto y est rangé par modèle).

### B — Serveur source de vérité unique, hydratation via React Query + garde anti-flash

On supprime la persistance localStorage des prefs ; la source de vérité devient `/api/v1/me` (champ `prefs` JSON). useMe() (React Query) hydrate un store de prefs au chargement ; un écran/atelier n'affiche son contenu sensible aux prefs qu'après résolution de useMe (skeleton ou défauts neutres SSR). Sauvegarde = PATCH /me debouncé sur chaque changement, avec mise à jour optimiste du cache React Query. init() lit les défauts depuis le cache useMe. Réinitialiser = PATCH prefs={} + invalidation.

**Forces** : Source de vérité UNIQUE : pas de réconciliation, pas de divergence localStorage/serveur, comportement identique sur tous les navigateurs/appareils ; Cohérence forte avec l'archi data existante : useMe() est déjà un hook React Query, l'optimistic update + invalidation est un pattern maison ; Réinitialisation et audit triviaux côté serveur (un seul endroit fait foi) ; « Par compte » est natif, pas un effet de bord de la réconciliation

**Faiblesses** : RISQUE DE FLASH réel : les prefs (thème clair/sombre surtout) arrivent après le premier paint réseau ; il faut un garde (skeleton/classe neutre) sinon flash de thème — régression vs l'hydratation synchrone actuelle de useUiStore ; Hors-ligne / réseau lent : l'UI dépend d'un round-trip pour appliquer les prefs au boot ; Migration plus intrusive : il faut RETIRER la persistance localStorage existante de claire.ui (déjà en prod par navigateur) et gérer la transition des prefs déjà stockées ; Charge serveur au moindre toggle (debounce indispensable) et dépendance réseau pour des réglages purement cosmétiques

**Pertinence** : Adéquation correcte sur le « par compte » mais en tension avec une contrainte explicite de l'aspect (éviter le flash au chargement) : le thème est précisément le pire cas de FOUC. Casser l'hydratation synchrone de useUiStore déjà livrée est un recul ergonomique. Convient si la portabilité stricte inter-appareils prime sur la latence/flash, ce qui n'est pas le besoin verbatim (ne pas reconfigurer à chaque doc).

### C — Hybride par couches : localStorage pour le shell, serveur pour l'atelier+auto-prefill, init() refactoré

Découplage par NATURE de pref. Couche shell (theme, sidebar, density, inspectorOpen, gutter*, reading*, largeurs de colonnes) = reste 100% localStorage (claire.ui / claire.workspace.layout) — purement par navigateur, zéro flash, aucune touche backend. Couche atelier+comportement (displayLang, llmSource, showUnfairness, showBoundaries, showTriageLevels, panneaux ouverts, ET surtout l'auto-prefill par modèle) = persistée SERVEUR dans `/me.prefs` car c'est elle que l'utilisateur ne veut pas reconfigurer par document. init() est refactoré pour lire ses défauts depuis ce slice serveur (fin du hardcode), et exécute l'auto-prefill choisi à l'ouverture. Sauvegarde debouncée par couche, indicateur « enregistré » discret seulement pour la couche serveur.

**Forces** : Met chaque pref au bon endroit : cosmétique/poste = local (rapide, zéro flash) ; comportement/contenu = compte (portable), ce qui colle au besoin verbatim et au choix per-modèle de l'auto-prefill ; Élimine proprement le reset par document : init() ne réécrit plus de défauts en dur, il consomme le slice atelier persisté serveur ; Pas de réconciliation localStorage↔serveur pour les mêmes clés (couches disjointes) → pas de dernier-écrivain-gagne sur une même donnée ; Le flash est circonscrit : seules les prefs serveur peuvent arriver tard, et ce sont des overlays atelier (moins visibles qu'un flip de thème), gardables par défaut neutre le temps de useMe

**Faiblesses** : Modèle mental à deux vitesses : l'utilisateur peut s'étonner que le thème ne suive pas d'un appareil à l'autre alors que les overlays atelier, si — il faut l'expliciter dans l'UI (libellés « ce navigateur » vs « mon compte ») ; Deux mécanismes de persistance à maintenir (zustand persist + slice serveur React Query) avec deux indicateurs/résets logiques ; Refactor d'init() obligatoire et délicat (zone à risque de perte de clauses) : il faut garantir que lire les défauts serveur ne ré-déclenche pas init() ni n'écrase des éditions locales non encore autosauvées

**Pertinence** : Meilleure adéquation au besoin réel : le verbatim distingue implicitement « disposition/affichage » (souvent liés au poste/écran) de « comportement à l'ouverture » (auto-prefill par modèle, overlays) qui doit suivre le compte. Réutilise au maximum l'existant (claire.ui inchangé, /me étendu d'un seul champ), respecte tokens/zéro hex et camelCase, et adresse frontalement la contrainte init()-réinitialise en ne migrant côté serveur QUE les clés concernées par le besoin.


**➜ Recommandation : C — Hybride par couches : localStorage pour le shell, serveur pour l'atelier+auto-prefill, init() refactoré**


> C est le meilleur compromis entre les contraintes vérifiées et le besoin verbatim. (1) Anti-flash : on NE TOUCHE PAS l'hydratation synchrone déjà en prod de useUiStore (claire.ui) ni claire.workspace.layout — donc le pire cas de FOUC (le thème) reste résolu gratuitement, contrairement à l'option B qui le réintroduit. (2) Source de vérité sans réconciliation : en séparant les COUCHES (shell local vs atelier serveur) on évite le dernier-écrivain-gagne de l'option A sur des clés partagées, car aucune clé n'est persistée aux deux endroits. (3) Cible exacte du besoin : ce que l'utilisateur ne veut pas reconfigurer à chaque document, ce sont les overlays/affichages atelier (displayLang, llmSource, showUnfairness…) et surtout l'auto-prefill par modèle — précisément la couche qu'on met « par compte » dans /me.prefs ; le reste (zoom, largeurs, densité) est légitimement lié au poste et reste local. (4) Cohabitation avec init() : l'aspect impose d'éviter le conflit avec init() qui réinitialise l'atelier par document — C l'attaque de front en refactorant init() (workspace.ts:463) pour LIRE ses défauts depuis le slice serveur au lieu des constantes en dur (orig/human/null), ce qui supprime la cause racine du « reconfigurer à chaque doc » et fait de l'auto-prefill un simple effet post-init paramétré par la pref. (5) Coût backend minimal et conforme : un seul champ JSON `prefs` sur User + extension de ProfileUpdateSerializer/UserSerializer, déjà servis en camelCase via drf-camel-case, sans nouvelle route. (6) Feedback de sync : indicateur « enregistré » discret réutilisant le vocabulaire d'état du SaveIndicator existant (saving/saved/idle, aria-live polite) appliqué uniquement à la couche serveur debouncée (~800 ms), et un bouton « Réinitialiser mes préférences » = PATCH prefs={} + invalidation useMe + re-hydratation des défauts. Le seul vrai coût — un modèle à deux vitesses (par navigateur vs par compte) — se neutralise par des libellés explicites dans l'écran de préférences, et reste cohérent avec l'attente naturelle des utilisateurs (le zoom/écran est local, le comportement d'annotation suit le compte). Garde-fou impératif lié à la zone sensible : la lecture des défauts serveur doit alimenter init() SANS l'inclure dans son tableau de dépendances [annId, docId, nSent, isMine, locked] et sans écraser des éditions de clauses non encore autosauvées — sinon on réintroduit le risque de perte de données déjà commenté dans AnnotationWorkspace.


## Design/animation du switch auto-prefill et des contrôles de préférences d'affichage (style visuel, micro-animations, états, accessibilité, homogénéité avec la WorkspaceToolbar existante)

### Option A — Switch iOS-like dédié (track + thumb glissant), aligné tokens

Un composant <PrefSwitch> réutilisable rendant un vrai role="switch" : track arrondi (rounded-full) + thumb circulaire qui translate avec transition-transform. OFF = track bg-panel-muted/60, thumb bg-ink-muted ; ON = track bg-accent/80, thumb bg-accent-fg, ring-1 ring-accent/40. État indéterminé (auto-prefill suggéré mais non décidé) = thumb centré + pulse léger (animate-pulse borné, halo accent/30). Micro-animation : translate du thumb (transition-transform duration-150 ease-out) + flash de confirmation (ring accent qui s'estompe sur 400ms à l'activation). Icône lucide Wand2/Sparkles à gauche du label pour le sens « auto-pré-annotation ». Posé dans la toolbar à côté du segmented Pré-remplir, et réutilisé tel quel dans le panneau Préférences.

**Forces** : Affordance universelle on/off : zéro ambiguïté pour activer/désactiver l'auto-prefill plus tard, exactement le besoin verbatim (« petit icône/switch ergonomique ») ; role="switch" + aria-checked natif : a11y canonique, plus simple qu'un radiogroup pour un booléen ; Le thumb glissant + flash accent donne le « pulse de confirmation » demandé sans librairie d'animation, juste transition-transform/opacity Tailwind ; Composant réutilisable : un seul <PrefSwitch> sert le switch toolbar ET toutes les lignes du panneau Préférences (cohérence garantie) ; 100% tokens (accent/accent-fg/ink-muted/panel-muted/line), zéro hex, focus-visible:ring-accent trivial à câbler

**Faiblesses** : Idiome track+thumb ABSENT de la toolbar actuelle (qui ne connaît que des segmented pills à fond plein) : risque de légère dissonance visuelle s'il est mal dimensionné ; L'état indéterminé d'un vrai switch (thumb centré) est peu conventionnel et peut dérouter — à réserver au seul moment « première exécution, on demande » ; Le pulse animate-pulse permanent serait agressif dans une toolbar dense : doit être strictement borné (1-2 cycles) et respecter prefers-reduced-motion ; Nouveau primitive à créer/tester (vitest) alors qu'aucun Switch n'existe encore dans components/ui

**Pertinence** : Très bonne adéquation au besoin : le verbatim demande explicitement un switch ergonomique pour réactiver l'auto-prefill, et un vrai role=switch est l'expression la plus directe. Réutilisable pour le panneau Préférences (qui sérialise des booléens : showUnfairness, showBoundaries, displayLang, gutter…). La seule tension est stylistique : il introduit un idiome (thumb glissant) que la toolbar n'a pas, à harmoniser via les tokens et un dimensionnement compact (h-5 w-9).

### Option B — Pastille toggle homogène aux boutons toolbar (icône qui change d'état, pas de thumb)

Réutilise EXACTEMENT l'idiome existant des boutons toolbar (cf. toggle-inspector : inline-flex rounded-md border px-2 py-1 text-xs, actif = border-accent/40 bg-accent/10 text-ink). Le switch auto-prefill devient un bouton à icône lucide commutable : OFF = Wand2 + border-line text-ink-muted ; ON = WandSparkles (ou Wand2 plein) + border-accent/40 bg-accent/10 text-ink, avec aria-pressed (toggle button, pas role=switch). Confirmation = micro flash via transition-colors duration-150 + un point accent (animate-ping borné) une seule fois à l'activation. Le panneau Préférences reprend ces mêmes boutons en liste, groupés par section (Affichage / Overlays / Disposition).

**Forces** : Homogénéité MAXIMALE : c'est littéralement le pattern toggle-inspector déjà en prod (aria-pressed, border-accent/40 bg-accent/10), donc zéro dissonance et zéro nouveau primitive lourd ; Le moins coûteux à livrer : on duplique un className éprouvé, déjà testé visuellement et accessible ; Tokens stricts garantis car copiés du code existant (accent/line/ink/ink-muted) ; aria-pressed sur un <button> est le pattern toggle déjà adopté dans la toolbar : cohérence aussi côté tests/data-testid ; Icône lucide cohérente avec la batterie existante (History/PanelRight/ListChecks) : taille 14, gap-1.5

**Faiblesses** : Moins « switch » visuellement : un bouton qui change de couleur communique moins clairement un état persistant on/off binaire qu'un track/thumb — le verbatim parle de « switch » ; aria-pressed vs role=switch : débat a11y ; pour une préférence persistante stricte, role=switch est plus idiomatique (aria-pressed convient surtout aux actions) ; Animation de confirmation plus pauvre (juste transition-colors + un ping) : le « pulse de confirmation » demandé reste discret ; En panneau Préférences, une longue liste de boutons-pastilles identiques se lit moins bien qu'une colonne de switches alignés (scannabilité de l'état on/off)

**Pertinence** : Adéquation forte sur l'homogénéité et le coût, plus faible sur l'expressivité « switch ». C'est l'option la plus sûre pour la toolbar (réutilise toggle-inspector au pixel près) et la plus rapide. Mais pour un panneau Préférences listant 6-8 réglages persistés par compte, une grille de boutons-pastilles scanne moins bien qu'une colonne de vrais switches, et le terme « switch » du besoin oriente vers A. Convient si on privilégie risque minimal et délai.

### Option C — Système hybride : panneau Préférences en Popover avec switches A + icône-affordance contextuelle inline dans la toolbar

Deux niveaux. (1) Affordance inline minimale : à côté du segmented Pré-remplir, une petite icône lucide Wand2 cliquable (le « petit icône » du verbatim) qui, OFF, est en text-ink-muted, et ON (auto-prefill armé pour ce modèle) passe en text-accent avec un liseré accent/40 ; un tooltip rappelle le modèle armé. (2) Tout le reste vit dans un Popover « Préférences d'affichage » (bouton Settings/SlidersHorizontal lucide dans la toolbar) : sections Overlays / Langue / Disposition / Auto-pré-annotation, chaque ligne = label + description courte ink-muted + <PrefSwitch> (le track/thumb de l'option A). Micro-animations : entrée du popover (fade+translate-y 1, duration-150), thumbs animés, pulse accent une fois sur le switch auto-prefill quand on l'arme depuis la modale de première exécution. Le popover persiste son ouverture éventuellement, mais surtout sérialise les booléens dans useUiStore (claire.ui) / futur backend.

**Forces** : Sépare proprement les deux besoins : l'affordance toolbar reste minuscule (un icône, fidèle au verbatim « petit icône bien placé ») ET le gros des réglages persistés vit dans un panneau dédié, dégonflant une toolbar déjà très chargée ; Le Popover est l'endroit naturel pour matérialiser « sauvegarder par compte les préférences d'affichage » : un lieu unique, sectionné, scannable, idéal pour brancher la persistance serveur (MeView PATCH /me) plus tard ; Scalable : ajouter une préférence = une ligne dans le popover, sans encombrer la toolbar ; Réutilise <PrefSwitch> (option A) pour la cohérence des états on/off et garde l'icône inline homogène aux boutons toolbar (option B) : best-of-both ; Micro-animations riches mais cadrées (fade popover + pulse unique) → satisfait pleinement « transition d'état + pulse de confirmation » et reste sobre dans la barre

**Faiblesses** : Le plus de surface à construire/tester : popover (focus-trap, Esc, click-outside, aria-expanded/role=dialog ou menu), PrefSwitch, ET l'icône inline → coût et risque de régression supérieurs ; Deux points d'entrée pour l'auto-prefill (icône inline + ligne dans le popover) : risque d'incohérence d'état si mal synchronisés sur la même source (useUiStore) ; La toolbar n'a aucun popover de préférences aujourd'hui : nouvel idiome de navigation à introduire, à designer pour ne pas jurer avec le reste ; Sur-dimensionné si le besoin immédiat est juste « ne pas reconfigurer à chaque doc » + « réactiver l'auto-prefill » : peut retarder la valeur livrée

**Pertinence** : Meilleure adéquation au besoin COMPLET (les deux volets : préférences d'affichage persistées par compte + auto-prefill avec affordance discrète), et le seul à offrir un foyer naturel pour la persistance par compte côté MeView. C'est la cible produit. Mais c'est aussi le plus lourd : il introduit un popover et deux primitives, alors que la toolbar est déjà dense. Pertinent comme destination, à condition de livrer par incréments (d'abord PrefSwitch + icône inline, puis le popover).


**➜ Recommandation : Option C — Système hybride : Popover « Préférences d'affichage » à base de PrefSwitch (option A) + icône-affordance inline homogène (option B), branché sur useUiStore puis MeView**


> Le besoin a deux volets indissociables : (1) sauvegarder PAR COMPTE un ensemble de préférences d'affichage pour ne plus reconfigurer à chaque document (showUnfairness, showBoundaries, displayLang, gutterModels, inspectorOpen…), et (2) une affordance ergonomique discrète pour (ré)armer l'auto-prefill. A seul est un excellent switch mais n'offre pas de foyer pour gérer 6-8 préférences ; B seul est homogène et bon marché mais scanne mal en liste et son aria-pressed est moins idiomatique qu'un role=switch pour des préférences persistantes. C compose les deux : il réutilise le PrefSwitch (role=switch, aria-checked, focus-visible:ring-accent, thumb animé en transition-transform, pulse de confirmation borné et respectueux de prefers-reduced-motion, tokens accent/accent-fg/ink-muted/panel-muted/line — zéro hex) pour TOUTES les lignes du popover, tout en gardant dans la toolbar une simple icône Wand2 text-ink-muted→text-accent strictement alignée sur l'idiome toggle-inspector déjà en prod. Surtout, le popover est l'endroit unique et sectionné où matérialiser la persistance par compte : il se câble d'abord sur useUiStore (claire.ui, déjà persistant) puis, sans refonte UI, sur un futur champ preferences exposé par MeView (PATCH /api/v1/me) en camelCase. Pour maîtriser le coût et le risque (focus-trap, Esc, click-outside du popover ; nouveau primitive), livrer par incréments : d'abord PrefSwitch + l'icône inline auto-prefill (valeur immédiate sur le verbatim), puis le popover Préférences. Une seule source d'état (useUiStore) pour l'icône inline et la ligne du popover évite toute désynchronisation. On obtient l'homogénéité de B, l'expressivité on/off de A, et la seule trajectoire qui répond au besoin complet sans encombrer davantage une toolbar déjà dense.
