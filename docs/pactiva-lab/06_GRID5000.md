# Intégration Grid'5000 — exécution déportée des expériences

> Documentation officielle consultée le **11 août 2026** (sources en fin de document).
> Ce document décrit l'intégration, pas un tutoriel Grid'5000 : il retient ce qui contraint
> l'architecture.

---

## 1. Ce qu'est Grid'5000, du point de vue de Pactiva

Grid'5000 est une infrastructure française distribuée sur plusieurs **sites** (Nancy, Rennes,
Grenoble, Lyon, Lille, Sophia, Luxembourg…), chacun hébergeant des **clusters** de nœuds, dont
une partie avec **GPU**. On y **réserve** des ressources pour une durée bornée (*walltime*)
via l'ordonnanceur **OAR**, puis on y exécute un travail.

**Trois propriétés dictent la conception :**

1. **Les réservations sont bornées et peuvent attendre.** Un job passe par `waiting` avant
   `running`. Un run peut donc rester en file plusieurs heures → **le suivi doit être
   asynchrone, avec un état « en attente » distinct de « en cours »**, sinon l'utilisateur croit
   à un blocage.
2. **Le *walltime* est un couperet.** Au-delà, le job est tué sans ménagement. → **tout run doit
   écrire ses résultats de façon incrémentale** et supporter la reprise ; jamais « tout à la
   fin ».
3. **L'accès externe passe par une authentification et une passerelle.** L'API REST exige les
   identifiants Grid'5000 en HTTP Basic depuis l'extérieur ; le transfert de fichiers passe par
   `access.grid5000.fr`.

## 2. Les points d'entrée techniques

### 2.1 API REST
- **Racine :** `https://api.grid5000.fr/` — version **`stable`** (la seule à utiliser ;
  `sid` est une branche de développement).
- **Authentification externe : HTTP Basic** avec le couple identifiant/mot de passe Grid'5000.
  ```bash
  curl -u LOGIN:PASSWORD https://api.grid5000.fr/stable/sites
  ```
  Alternative : tunnel SSH via la passerelle, qui rend l'authentification transparente —
  `ssh -NL 3443:api.grid5000.fr:443 LOGIN@access.grid5000.fr`.
- **Sous-API utiles :** *reference* (sites/clusters/nodes), *status*, **jobs**, *deployments*,
  *storage*, *metrics*.

### 2.2 Soumission d'un job
```
POST /stable/sites/{site}/jobs
Content-Type: application/json

{"resources": "nodes=1,walltime=02:00", "command": "bash /home/LOGIN/pactiva/run.sh"}
```
Réponse **201 Created**, avec l'URI du job dans l'en-tête `Location`.

### 2.3 Suivi
```
GET /stable/sites/{site}/jobs/{job_id}
```
Le champ `state` vaut `waiting`, `running` ou `stopped`. C'est la seule information de suivi
fiable côté API → **la progression fine doit venir d'un fichier écrit par le job lui-même**
(`progress.json` sur le stockage partagé), relu au rapatriement.

### 2.4 Réservation de GPU (via OAR, dans le script ou en `resources`)
```bash
oarsub -l gpu=1,walltime=02:00 -p "cluster='<nom>'" -q production ./run.sh
```
- L'option `-q production` est requise pour les ressources « production » (Nancy, Rennes).
- Recommandation officielle : **ne pas réserver un seul GPU sur un nœud qui en compte ≥ 4** si
  un seul est utilisé.

### 2.5 Environnement logiciel
- **Conda est la voie recommandée** : `module load conda`, puis un environnement dédié.
- **Créer l'environnement sur un nœud, pas sur la frontale** (les frontales manquent de RAM
  pour ces opérations).
- ⚠️ **Piège documenté :** la version de `pytorch-cuda` doit correspondre au CUDA du nœud,
  sinon **PyTorch ne voit pas le GPU**. → le script de préparation doit `nvidia-smi` puis
  vérifier `torch.cuda.is_available()` et **échouer bruyamment** si faux (plutôt que de
  s'entraîner 6 h sur CPU sans rien dire).

### 2.6 Stockage et réseau
- **Home NFS** par site + **Group Storage** (`/srv/storage/<nom>@<serveur>`) pour les données
  partagées entre sites et durables.
- **Accès Internet depuis les nœuds : disponible** (IPv4 NATé). Le téléchargement des poids de
  modèles depuis un nœud est donc possible — mais **fragile** (dépend d'un service tiers pendant
  une réservation payée en heures). → **pré-télécharger les poids dans le Group Storage** et
  pointer `HF_HOME` dessus.
- Un **proxy inverse** expose un service web d'un nœud (`https://<nœud>.<site>.http.proxy.grid5000.fr/`),
  authentifié par les identifiants Grid'5000. Non nécessaire ici.

## 3. Le cycle d'un run déporté

```
Pactiva                          access.grid5000.fr            OAR / nœud
   │  1. build dataset                    │                        │
   │  2. rsync dataset + config ─────────▶│──▶ ~/pactiva/runs/<id>/│
   │  3. POST /jobs (Basic auth) ─────────┼───────────────────────▶│ waiting
   │                                      │                        │ running
   │  4. GET /jobs/{id}  (sondage) ◀──────┼────────────────────────│ (écrit progress.json)
   │  5. rsync ◀──────────────────────────│◀── results/            │ stopped
   │  6. validation JSON Schema + ingestion                        │
   │  7. artefacts + figures visibles dans l'UI                    │
```

**Sondage adaptatif** (même logique que l'export asynchrone déjà en place) : 5 s pendant la
première minute, puis 15 s, puis 60 s. Un job `waiting` depuis longtemps n'a pas besoin d'être
sondé toutes les 5 secondes.

**Reprise après incident.** L'`external_job_id` est persisté dès la réponse 201. Si le backend
redémarre, il retrouve les jobs en cours et reprend le sondage. Un job tué par le *walltime*
avec des résultats partiels est ingéré comme **`partial`**, pas comme `failed` — le travail
n'est pas perdu.

## 4. Sécurité des identifiants — la question centrale

**Trois options, évaluées :**

| Option | Fonctionnement | Verdict |
|---|---|---|
| **A — Variables d'environnement** `G5K_LOGIN` / `G5K_PASSWORD` | Un compte de service partagé | ✅ Simple, aucun secret en base. ❌ Mono-utilisateur ; l'usage de tous est imputé à un seul compte |
| **B — Par utilisateur, chiffré en base** | Chaque chercheur saisit ses identifiants dans l'UI ; chiffrement **Fernet** avec une clé dédiée `LAB_CREDENTIALS_KEY` | ✅ Multi-utilisateur, imputation correcte, révocable. ❌ Il faut gérer la clé |
| **C — Clé SSH déposée** | Pactiva détient une clé pour `access.grid5000.fr` | ❌ Une clé SSH donne bien plus que l'API ; disproportionné |

### Recommandation : **B, avec repli sur A**

```
Priorité de résolution des identifiants :
  1. Identifiants personnels de l'utilisateur (chiffrés en base)   ← nominal
  2. Variables d'environnement du serveur                          ← repli / mono-poste
  3. Aucun → la cible `g5k` est proposée mais désactivée, avec un message explicite
```

**Règles de mise en œuvre — non négociables :**

1. **Chiffrement au repos** par `cryptography.fernet`, clé dans `LAB_CREDENTIALS_KEY`
   (variable d'environnement, **jamais** dérivée de `DJANGO_SECRET_KEY` : la rotation de l'une
   ne doit pas détruire l'autre). Absence de clé ⇒ **refus d'enregistrer**, jamais de stockage
   en clair « en attendant ».
2. **Écriture seule.** L'API n'expose jamais le mot de passe, même à son propriétaire. Le
   `GET` renvoie `{login, hasPassword: true, lastTestedAt, lastTestOk}`. Pas de champ
   `password` en sortie, à aucun niveau de sérialisation.
3. **Test de connexion explicite** (`POST …/test`) → `GET /stable/sites` en Basic auth. Le
   résultat est horodaté et affiché. On ne découvre pas un mot de passe faux au bout d'une
   réservation.
4. **Jamais dans les journaux.** Filtre de journalisation qui masque `Authorization`,
   `password`, et les URL contenant `login:password@`. **Testé** (§`05`).
5. **Portée stricte** : un identifiant appartient à un utilisateur, n'est utilisable que par
   lui, et est supprimé avec son compte.
6. **Pas de secret dans les artefacts** : le script généré lit les identifiants depuis
   l'environnement du processus, jamais depuis un fichier déposé sur le stockage partagé.

```python
# backend/claire/lab/crypto.py — esquisse
def encrypt_secret(raw: str) -> str:
    key = os.environ.get("LAB_CREDENTIALS_KEY")
    if not key:
        raise ImproperlyConfigured(
            "LAB_CREDENTIALS_KEY absente : refus de stocker un identifiant Grid'5000. "
            "Générer avec `python -c \"from cryptography.fernet import Fernet; "
            "print(Fernet.generate_key().decode())\"`."
        )
    return Fernet(key.encode()).encrypt(raw.encode()).decode()
```

## 5. Configuration d'une cible de calcul

```yaml
# exemple de ComputeTarget
kind: g5k
site: nancy                  # nancy | rennes | grenoble | lyon | lille | sophia | luxembourg
cluster: null                # null = laisser OAR choisir
resources: "gpu=1,walltime=04:00"
queue: production            # requis pour les ressources production de Nancy/Rennes
besteffort: false            # true = passe devant en file mais peut être préempté
env_setup: conda             # conda | module | apptainer
env_name: pactiva-lab
workdir: "~/pactiva"
hf_home: "/srv/storage/pactiva@storage1.nancy.grid5000.fr/hf-cache"
```

**`besteffort` mérite d'être proposé dans l'UI** : pour un criblage de prétraitements (des
dizaines de petits runs interruptibles et rejouables), c'est le bon mode — files d'attente
courtes, et une préemption ne coûte qu'un redémarrage. Pour un *fine-tuning* de 4 h, non.

## 6. Le script d'exécution généré

```bash
#!/usr/bin/env bash
set -euo pipefail                      # échec bruyant, jamais de dérive silencieuse
RUN_DIR="$HOME/pactiva/runs/${RUN_ID}"
cd "$RUN_DIR"

module load conda
source activate pactiva-lab
export HF_HOME="${HF_HOME:-$RUN_DIR/.hf}"

# Garde-fou GPU : mieux vaut échouer en 3 s que d'entraîner 6 h sur CPU sans le savoir.
if [ "${REQUIRE_GPU}" = "1" ]; then
  nvidia-smi || { echo "FATAL: aucun GPU visible"; exit 64; }
  python -c "import torch,sys; sys.exit(0 if torch.cuda.is_available() else 65)" \
    || { echo "FATAL: torch ne voit pas le GPU (CUDA/pytorch-cuda désaccordés)"; exit 65; }
fi

python -m pactiva_lab run \
  --config config.json --data dataset/ --out results/ \
  --progress results/progress.json

echo "DONE" > results/_SENTINEL
```

Le fichier **`_SENTINEL`** distingue « job terminé normalement » de « job tué par le
*walltime* ». Sans lui, un rapatriement de résultats partiels serait pris pour un succès.

## 7. Dégradation maîtrisée

| Situation | Comportement |
|---|---|
| Aucun identifiant configuré | La cible `g5k` apparaît **désactivée** avec l'explication et un lien vers le formulaire |
| API Grid'5000 injoignable | Run en `failed` avec `error_code=g5k_unreachable` ; **le dataset reste valide** et le run est rejouable en local |
| Job tué par le *walltime* | Résultats partiels ingérés en `partial` ; l'UI propose de relancer avec un *walltime* plus grand |
| GPU absent alors qu'il est requis | Échec en quelques secondes (code 64/65), message explicite |
| Aucun quota / compte Grid'5000 | Tout le module reste **pleinement utilisable en `local`** — Grid'5000 est une accélération, jamais une dépendance |

> La dernière ligne est un choix d'architecture : **Grid'5000 ne doit jamais être sur le chemin
> critique de l'article.** Les baselines, les embeddings gelés et le criblage tournent en local ;
> Grid'5000 sert au *fine-tuning* et aux grilles.
